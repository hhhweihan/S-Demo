# C++ 社招能力路线：高性能后端与系统基础设施

## 目标与使用方式

面向 3–5 年经验层级的 C++ 后端／系统基础设施岗位，训练四类能力：独立交付组件、定位复杂故障、用测量解释性能、讲清系统设计与取舍。AI 推理服务作为加分方向，不替代基础，也不是开始投递的前置条件。

这是一份能力训练路线，不是特定岗位的招聘标准，也不保证职级、录用或薪资结果。具体范围要用目标岗位的公开职位描述校准。

- **不设固定期限**：按阶段验收推进，已经掌握的部分用诊断跳过，不必从 Day 1 重学。
- **不增加一串必须手写的库**：复用 [现有模块](Practice-Index.md)，先做深一个代表作。
- **必修 / 深化 / 加分分开**：基础、真实网络、可靠性、性能、交付与面试为必修；存储／分布式按方向二选一深化；AI、CUDA、真实 io_uring 等按需选修。
- **区分计划与实现**：下文新增能力、服务化与 AI 集成均为待训练目标，不表示仓库已经实现。
- **进度只记证据**：在 [Progress.md](./Progress.md) 中填写阶段状态、验证入口和遗留问题，不以代码生成量或阅读量判断掌握。
- **资料边界**：项目只使用公开或自造数据、可公开的代码和模型；不引入公司／客户代码、内部架构、凭证或业务数据，求职材料也遵守保密边界。

## 二、阶段路径与依赖

```text
S0 能力诊断
  -> S1 C++ / 并发基础补强
  -> S2 Linux 与真实网络
  -> S3 主线代表作：有界异步组件 + 网络服务
  -> S4 性能、可靠性与交付
  -> S5 存储 / 分布式二选一深化

求职准备从 S0 并行开展；S4 后可开始定向试投递，按反馈补 S5。
AI 加分阶段依赖 S4，不依赖 S5，也不阻塞投递。
```

### S0：诊断与目标校准

**任务**

1. 选取 5–10 份公开的目标岗位描述，归类语言、Linux、网络、存储、调试性能、系统设计等要求。区分反复出现的必需项和单个岗位的加分项。
2. 从现有工程独立完成四项诊断：解释一段对象生命周期；修改线程池关闭行为；分析一次拆包边界；定位一个公开／自造的崩溃或竞态。
3. 只把不会独立完成的部分纳入补课，不因现有代码标记“已实现”就认定已经掌握。
4. 建立脱离个人履历的技能缺口表：`能力 -> 当前证据 -> 缺口 -> 下一项任务`。

**验收**：能明确主攻岗位类别、三个优先缺口和一个代表作方向；每个缺口都有可执行的任务，而不是“继续学 C++”。

### S1：C++ 与并发基础补强

**复用**：[memory_pool](01-内存管理/practice/memory_pool)、[raii](01-内存管理/practice/raii)、[thread_pool](02-并发编程/practice/thread_pool)、[lock_free](02-并发编程/practice/lock_free)、[stl_sequence](04-STL-Sequence/practice/stl_sequence)。

**必修任务**

- 生命周期与接口：Rule of Zero/Five、拷贝／移动、异常安全、虚析构、所有权与非拥有视图、迭代器失效。
- 现代 C++：熟练使用 C++17/20 的 `optional`、`variant`、`string_view`、`span`、concepts；特别检查视图是否悬空。仓库根构建为 C++20，C++23 特性仅作选修，不默认升级标准。
- 并发：条件变量谓词、关闭与唤醒、任务异常传播、锁顺序、原子操作、happens-before、false sharing；理解 SPSC 的适用边界与内存回收问题。
- 在已有测试中补一个真正的边界问题，例如提交与关闭并发、容量耗尽、移动后状态或分配失败；测试应在修复前失败。
- 针对自造问题各做一次内存错误和竞态定位；复用现有 ASan/UBSan、TSan，不用“测试全绿”替代正确性推理。

**验收**

1. 不借助 AI 独立实现一个有界队列核心：容量约束、生产消费、关闭、等待者唤醒；测试覆盖满、空、关闭和并发交错。
2. 讲清一个容器的生命周期与异常保证，以及选择它而非另一种容器的理由。
3. 给出两份故障复盘：现象、最小复现、证据、根因、修复与回归测试。Sanitizer 无报告只说明已执行场景未发现问题。

### S2：Linux 系统与真实网络

**复用**：[network_reactor](08-网络编程/practice/network_reactor/README.md)；参考 [Raft 真实网络实现](12-RaftKV/practice/raft_kv/net) 的 OS 交互方式，不复制其分布式协议。

**必修任务**

- 系统：进程／线程、虚拟内存、页缓存、系统调用、文件描述符、信号、`mmap`、`write`/`fsync`/`rename` 的保证与限制。
- 网络：TCP 字节流、连接建立与关闭、半关闭、短读短写、`EINTR`/`EAGAIN`、非阻塞 IO、LT/ET、连接与空闲超时。
- 工具：GDB/core dump、`strace`、`ss`、`lsof`、`perf` 的基本使用；WSL2 可练习 Linux 接口，但注明它与原生部署环境的差别。
- 给现有 Reactor 增加真实 Linux 后端，保留 FakePoller 的单元测试。先完成 LT 模型，不以 ET 或 io_uring 为起点。
- 用长度前缀协议完成一个客户端／服务端：限制帧长、每连接缓冲与连接数；实现部分发送、断开清理和优雅退出。

**验收**

1. 两个独立进程通过真实 TCP 交换请求；拆分发送、合并发送与短写场景均不破坏协议。
2. 自动化验证至少包括：非法长度、慢接收端、发送中断开、连接超时、带未完成请求退出；每项都有明确结果和资源回收证据。
3. 能从系统调用或线程栈解释一次“CPU 高”或“请求卡住”，而非仅修改轮询间隔。

真实进程测试单独运行，不以 mock 代替。只在专用测试环境对自己启动的进程做故障注入，不修改共享机器的全局网络或内核配置。

### S3：主线代表作——有界异步组件与网络服务

**目标**：以 [async_logger](06-AsyncLogger/practice/async_logger/README.md) 为起点，将 S1 的队列／线程池与 S2 的网络接入组合成一个小型日志接收服务。先做单机闭环，不同时引入 Kafka、Raft、Kubernetes 或自研数据库。

**边界先写清楚**

- 输入：公开／自造日志事件，包含请求 ID、时间、级别和消息；定义编码、字段限制、帧长上限与非法输入响应。
- 接入：复用已验证的 TCP 协议，不把自研 HTTP 解析器默认当成完整 HTTP 服务。
- 处理：明确有界队列、连接缓冲、文件保留和线程数量；资源上限应能配置并被测试触发。
- 输出：文件 Sink 与基础状态／指标接口；明确计数器含义，避免将“入队成功”叫作“持久化成功”。
- 暂不实现：全文检索、跨机复制、exactly-once 或多租户平台。

**按以下顺序实现**

1. **容量与过载**：先选一种策略，如拒绝新请求并显式返回错误；列出阻塞、丢弃和降级的取舍。内部日志若允许丢弃，必须有独立计数，不能静默丢失。
2. **可靠性合同**：分别定义 accepted、written、durable 的确认点，以及 `flush` 与 `fsync` 的区别。若只保证入队确认，必须说明进程崩溃时可能丢失已接收数据，不声称持久化交付。
3. **错误与退出**：处理写入失败、磁盘容量限制、Sink 故障、关闭期间提交；定义排空、超时退出和未完成事件的报告方式。
4. **文件管理**：选择按大小或时间滚动，限制保留空间；测试滚动边界、打开失败和重启行为。
5. **可观测性**：先有请求数、拒绝数、失败数、队列水位、丢弃数、写入耗时；再按需要提供 Prometheus 格式。指标标签不使用请求 ID、原始消息等高基数字段。

**验收**

- 使用唯一事件 ID 核对接收、拒绝、完成与丢弃；静止并排空后，对接受事件满足 `accepted = completed + explicitly_failed_or_dropped`，拒绝事件单独核对。测试中无重复、无未解释缺口；这是测试证据，不是 exactly-once 承诺。
- 队列容量上限由测试断言；进程内存同时测量，不能用“队列有界”推导“整体内存有界”。
- 注入慢 Sink、写入失败、容量耗尽和退出竞争，客户端结果与指标符合合同。
- 如选择 durable 确认，验证确认后进程猝死恢复；进程 kill 测试不等价于断电安全验证。
- 提供最小运行示例、协议说明、结构图、关键取舍与已知限制，其他人能从干净构建启动服务。

### S4：性能、可靠性与交付

**性能任务**

1. 建立真实客户端／服务端基线，记录编译器、优化选项、硬件、OS、客户端位置、线程数、队列容量、提交版本和负载模型。必要时把压测端与服务端分开，确认客户端不是瓶颈。
2. 基础矩阵采用消息大小 `256 B / 1 KiB / 4 KiB`、并发连接 `1 / 8 / 32`；每组预热后测量至少 60 秒、重复 3 次。机器资源不足时先调低并记录理由，不在共享环境追求极限负载。
3. 分别测稳定负载、突发与持续过载；报告成功吞吐、请求延迟 P50/P95/P99、排队耗时、拒绝／超时／失败率、CPU、RSS、队列峰值。延迟要注明从哪里计时、哪些请求参与统计；闭环压测可能掩盖排队问题。
4. 先用 `perf` 与火焰图定位一个瓶颈，再只改一个变量，如批量写、分配次数、锁粒度或缓冲复用，复测正确性与性能。
5. 设置项目自己的可解释目标：例如在声明负载下满足队列上限、错误策略和延迟预算；不要要求所有机器达到某个 QPS 或“必快 5 倍”。

**交付任务**

- 复用根级 CMake、CTest、CI 和格式规则；检查 GCC/Clang 构建，依赖固定版本，构建能复现。
- 单元测试、真实进程集成测试、Sanitizer 与性能测试分开；不用 Sanitizer 构建结果作为 Release 性能指标。
- 用 Docker 或 systemd 选一种方式交付服务，提供启动、健康检查、优雅关闭、配置校验与资源限制说明。
- 能观察业务可用性与资源问题：指标趋势、错误日志、队列饱和告警；健康检查不能只证明进程还存在。
- 形成一份运维排障步骤：高 CPU、高 RSS、请求超时、写入失败各如何收集证据，如何安全止损和回滚。

**验收**

1. 有可复现的优化前后报告：原始结果、分位数、错误率、资源使用、瓶颈证据和取舍；无提升也要如实说明。
2. 做一次专用环境下至少 30 分钟的稳定负载测试与一次过载测试，记录资源趋势和结束后的回收情况；不把短测称为长期稳定性证明。
3. 另一台可控环境能按说明构建、启动、发请求并执行健康检查。没有第二环境时保持“待验证”，不宣称已复现。

### S5：深化专项——存储或分布式二选一

S1–S4 是主线；S5 用来建立第二个技术深度，不必把两个方向都做完才投递。

| 方向 | 学习与实现任务 | 验收 |
| --- | --- | --- |
| 存储 | 复用 [leveldb_mini](07-LevelDB/practice/leveldb_mini/README.md)；解释 WAL、SSTable、BloomFilter、compaction、读写空间放大；从 block cache 或 MANIFEST/VersionSet 中选一个专项 | 测试缓存一致性／文件集合恢复等所选不变量；在冷热读、读写混合负载下测量，说明影响与未实现边界 |
| 分布式 | 复用 [raft_kv](12-RaftKV/practice/raft_kv/README.md)；解释选举、提交、线性一致读、幂等与重试；优先验证真实多进程与恢复，成员变更按需选修 | 实跑集成测试；在隔离环境注入 leader 退出、节点重启和延迟，核对已确认写入与读语义；跨机结果与单机结果分开 |

共同要求：能从请求入口讲到磁盘／复制路径，解释至少两个故障场景和两个设计取舍，不背概念列表。已有 kill 测试不自动证明全部磁盘故障、一致性或生产可用性。

## 三、AI 推理服务加分阶段

**前置**：S4 已验收；这部分不阻塞求职，也不要求先学 CUDA 或训练模型。

1. **Python 最小工具能力**：虚拟环境、包依赖、HTTP 客户端、数据生成与分析；写压测／结果分析工具，不先扩展成另一条完整语言路线。
2. **理解推理链路**：张量、shape、dtype、预处理、推理、后处理、模型内存；理解 CPU/GPU 数据搬运、batch、量化的基本取舍。
3. **只选一个运行时**：通用模型可选 ONNX Runtime；生成式模型可选 llama.cpp。先跑官方最小例子，记录模型来源、许可证、版本、硬件需求与输出校验方式；资源有限先做 CPU 小模型。
4. **接入已有服务骨架**：保留日志事件协议，另定义推理请求／响应；接入有界调度、超时、过载拒绝、取消和指标。声明取消能否中断运行中的推理；若只能取消排队或停止返回，明确写出限制。
5. **测试与测量**：验证输入边界、输出形状／容差、模型加载失败、超时和并发；区分排队与推理耗时，测 batch 对延迟、吞吐、内存与输出质量的影响。生成式模型再加首 token 延迟与 tokens/s，不套用到所有模型。

**验收**：真实运行时与本地模型完成端到端请求；有可复现结果、错误场景和资源上限证据；能解释服务瓶颈，不将调用外部 API 或 mock 输出作为本地推理经验。

**后续选修**：CUDA、GPU profiler、SIMD、真实 liburing、推理运行时源码或算子优化。只有目标岗位需要，或测量证明相关瓶颈存在时再加入；不同时展开所有方向。

## 四、求职准备：从第一阶段并行开展

### 基础与编码

- C++：生命周期、移动与异常、容器失效、模板约束、并发内存模型；结合现有代码解释，不只背面试答案。
- 系统：进程线程、内存与缓存、IO、TCP、epoll、持久化、调试；能说明“何时不该这么设计”。
- 算法：数组／哈希、链表、二分、堆、树、图与常见动态规划。每次练习都要求独立编码、复杂度说明与边界用例；按目标岗位反馈调整范围，不以刷题数量代替能力。
- 做一次限时模拟：在约定的 30–45 分钟内完成目标岗位常见难度的问题，主动澄清约束并测试；记录卡点，复习后换题再测。

### 项目与设计

- 主线代表作准备 3 分钟概览和 15 分钟深挖：需求、约束、结构、独立完成的改动、验证、故障、性能与局限。
- 准备两个证据充分的排障案例和一个优化案例。学习项目如实标为学习项目，不编造线上规模、业务收益或故障经历。
- 练习三个设计题：有界任务执行服务、日志接收与持久化、带超时重试的 RPC；先定义流量与可靠性合同，再谈存储、扩容与成本。
- 用一个陌生公开代码库做小改动，补回归测试并解释影响范围，检验读代码和协作能力，而非只会讲自研项目。

## 五、每次学习怎么执行

一次学习只推进一个可验收任务，不同时打开多个新方向：

1. **定义**：用几句话写输入、输出、不变量、失败语义和完成条件。
2. **实现**：先做最小正确版本，复用既有模块与成熟依赖，避免为抽象而抽象。
3. **验证**：运行最小相关测试；涉及网络、磁盘与性能时补对应真实实验。
4. **复盘**：记录证据、一个关键取舍、遗留问题与下一步，更新 [进度](./Progress.md)。

建议每完成 2–3 个任务做一次闭卷回顾，每通过一个阶段做一次模拟面试；这里的节奏是反馈机制，不是固定排期。

### AI 辅助学习的边界

- 自己先定接口、约束与验收条件，再让 AI 协助查资料、生成局部实现或分析报错。
- 对 AI 给出的同步、生命周期、持久化与性能结论逐项核对；生成代码通过测试不代表结论被证明。
- 阶段验收中的关键实现、排障解释和模拟面试独立完成，不借助 AI；其余工程工作可以合理使用辅助工具。
- 不将非公开资料输入外部服务，不把不能解释的代码或生成的指标当作自己的能力证据。
