# 嵌入式 C/C++ 社招能力路线：MCU、RTOS、BSP 与驱动

配套阅读：[教学课程](Embedded/README.md) · [知识地图](Embedded/Knowledge-Map.md)。本页负责阶段与验收，课程正文负责概念、分步练习、检查点和回看。

## 目标与边界

面向 3–5 年经验层级的传统嵌入式软件岗位，建立从手册、启动、外设驱动到实时任务、故障定位与交付的能力。**主线先选 Cortex-M + FreeRTOS，深化时再选择 MCU/BSP 或 Linux BSP/驱动，不同时学习所有芯片与操作系统。**

这不是特定岗位的招聘标准，也不保证薪资或录用结果。学习路线以公开职位描述校准，以独立完成任务与真板证据验收，不设固定期限。

- 当前 [01–12 模块](./README.md#路线总览) 是 C++ 系统编程素材库，不是完整嵌入式课程；不要求先全部重写再开始硬件实践。
- 新增外设、RTOS、BSP、驱动与固件项目均为**待训练目标**，不表示仓库已经实现。
- [后端能力路线](./Career-Roadmap.md) 保留为备选；Linux 用户态服务不等于 Linux 内核驱动，车载诊断协议不等于 BSP，RTOS 任务也不等于桌面线程。
- 只使用公开手册、公开／自造代码和实验数据。不写个人履历，不引入公司／客户代码、内部架构、凭证或业务数据。
- 仅在自己的低压开发板与隔离实验环境测试，不连接真实车辆、生产设备或公共总线；故障注入只影响自己控制的设备。

## 一、能力优先级

| 层级 | 必修内容 | 不需要一开始做的事 |
| --- | --- | --- |
| C 与受限 C++ | 指针、整数与位操作、布局对齐、生命周期、静态内存、编译链接、资源上限 | 反复实现完整 STL、复杂元编程 |
| Cortex-M 与硬件基础 | 时钟、复位、向量表、中断、栈、GPIO、电平与总线、读手册与原理图 | 同时学习多种 MCU、设计复杂电路板 |
| 外设与驱动 | UART、定时器、I2C/SPI 至少一种、DMA、超时与错误恢复 | 只调用 HAL，或反过来把所有 HAL 全部重写 |
| RTOS | 调度、同步、ISR 边界、优先级反转、栈与堆、实时测量 | 照搬 `std::thread` / `future` 或先自研操作系统 |
| BSP 与交付 | 启动、链接脚本、板级配置、固件构建烧录、版本与故障诊断 | 学习阶段就宣称功能安全认证或量产可靠性 |
| 深化分支 | MCU/BSP 或 Linux BSP/驱动二选一，形成第二个深度专项 | 同时要求 AUTOSAR、Linux 内核、CUDA、AI 推理 |

### 现有模块怎么复用

- [内存管理](./01-内存管理/README.md)：保留生命周期、RAII、对齐、分配器原理；增加 Flash/RAM、静态池与堆碎片约束。分配器性能倍率不是 MCU 通用验收标准。
- [并发](./02-并发编程/README.md)：保留队列、同步与所有权；RTOS 版必须重新说明 ISR/任务共享、阻塞与调度语义，不能认为 host 版线程池已证明板上正确性。
- [模板](./03-模板泛型/README.md) 与 [容器](./04-STL-Sequence/README.md)：重点是固定容量容器、无悬空视图、可解释的代码尺寸与分配行为；容器算法核心可在 host 测试。
- [异步日志](06-AsyncLogger/practice/async_logger/README.md)：参考有界缓冲、错误报告与后台输出设计；MCU 版使用自己的 BSP/RTOS 接口，不把桌面文件 Sink 和线程模型直接搬到固件。
- [网络](08-网络编程/practice/network_reactor/README.md) / [RPC](11-RPC/practice/rpc_framework/README.md)：复用帧边界、超时、非法输入和重试概念；epoll 不是 FreeRTOS 外设驱动。
- [LSM](07-LevelDB/practice/leveldb_mini/README.md) / [Raft](12-RaftKV/practice/raft_kv/README.md)：留作系统知识选修，不作为嵌入式主线前置。
- [C++20 协程](10-Coroutine/practice/coroutine_lib/README.md)、真实 io_uring 与 AI 推理：后置选修，不挤占启动、驱动、RTOS 与调试训练。

```text
E0 岗位校准、诊断与实验环境
  -> E1 C / 受限 C++、Cortex-M 启动与调试
  -> E2 外设、DMA 与驱动边界
  -> E3 FreeRTOS 与实时性
  -> E4 真板代表作：有界数据采集与诊断固件

编码、手册阅读、项目深挖从 E0 并行开展。

```

### E0：岗位校准与实验环境

执行入口：[E0 起步任务](./00-Embedded-Start/README.md) 与 [host 练习骨架](00-Embedded-Start/practice/embedded_basics/README.md)。骨架不提供实现答案，初始测试预期红色；真板验收不能由 host 测试替代。

教学：[环形缓冲](00-Embedded-Start/Byte-Ring-Guide.md) → [有界帧解析](00-Embedded-Start/Frame-Parser-Guide.md)。

**任务**

1. 收集 5–10 份公开岗位描述，分清 MCU 应用、RTOS 固件、MCU BSP、Linux BSP、Linux 驱动；各标出必需技能与加分项。先选一种主投岗位，不用“嵌入式”笼统代替目标。
2. 做四个独立诊断：实现长度字段有界帧解析；解释指针／整数边界；分析 ISR 与任务共享数据；从一份公开手册找到时钟、引脚与 UART 配置约束。
3. 在 [Progress.md](./Progress.md) 记录三个优先缺口与下一项任务；已有工程“已实现”不等于这些能力已验收。
4. 选一块资料完整、带板载 SWD 调试器的 STM32 Nucleo 或同类 Cortex-M 板；确认 UART、定时器、I2C/SPI、DMA、看门狗资源。记录具体型号、Flash/RAM、时钟、电平与调试接口后再制定引脚表。
5. 先使用官方最小工程，配好 Arm 交叉工具链、烧录与调试工具。GPIO、UART 可先练；后续再按需要添加低压传感器／SPI Flash 与逻辑分析仪。CAN 不作首块板必需项，做该专项时另确认控制器、收发器和实验总线。

**验收**：能在真实板上构建、烧录、下断点、单步并查看寄存器；能说明主攻岗位、板卡资源和三个缺口。没有硬件时可先做 host 测试或仿真，但真板项保持待验证。

### E1：C、受限 C++、启动与调试

教学正文：[E1 语言与启动](Embedded/E1-Language-Startup/README.md)。

**语言与构建**

- C：数组／指针、函数指针、符号与无符号转换、整数溢出、位运算、结构布局、大小端、严格别名与未定义行为。
- 区分 `const`、`volatile`、原子与临界区：`volatile` 不是线程／中断同步机制；共享状态要分析访问宽度、原子性、编译器与硬件顺序。
- C++：RAII、构造析构、所有权、模板与虚函数的成本；明确所用标准库实现是否分配、是否依赖异常与运行时，不能把全部 STL 一概视为不可用或零成本。
- 对当前项目制定异常、RTTI、动态分配和日志的规则；优先静态／固定容量资源，初始化后是否允许分配必须有明确合同与证据。
- 读懂预处理、编译、汇编、链接、ELF、map、符号与反汇编；使用交叉工具链的 `size`、`nm`、`objdump`。
- MCU 工程按所选工具链和运行时确定 C/C++ 标准，不为了固件修改现有 host 根构建的 C++20 设置。

**启动与硬件**

- 从 reset handler 追踪向量表、初始栈、`.data` 拷贝、`.bss` 清零、时钟初始化、C++ 初始化到 `main`。
- 理解 Flash/RAM、栈／堆、链接脚本、NVIC、SysTick、异常入口与返回；架构特性以实际芯片为准。
- 读原理图中的供电、电平、上拉、复用引脚；遵守板卡额定条件，不把开发板接口直接接到高电压设备。

**验收**

1. 对定长缓冲解析代码做 host 单元测试：空、截断、非法长度、边界和溢出；核心实现独立完成。
2. 在板上解释一个变量的地址与所在段，读 map 文件并给出 Flash/RAM 使用基线。
3. 对自造 fault 用调试器查看异常寄存器、现场栈和 PC/LR，给出根因与修复；不能只“复位后恢复”。
4. 能解释启动过程，完成一项小型链接／板级配置修改，并验证没有破坏启动与内存布局。

### E2：外设、DMA 与驱动

教学正文：[E2 外设与 DMA](Embedded/E2-Peripherals-DMA/README.md)。

**按顺序做**

1. GPIO 与定时器：输入、输出、复用、周期中断；用逻辑分析仪或示波器核对周期与电平。
2. UART：从轮询到中断收发，再到 DMA + 固定容量环形缓冲；明确缓冲所有权、溢出策略、帧边界与错误恢复。
3. I2C 或 SPI 二选一：接一个有公开手册的真实器件；实现读写、超时、设备缺失和错误报告。
4. 从 HAL 的一个 UART／定时器调用追到寄存器配置，独立实现一条最小寄存器操作路径；复用 CMSIS/厂商定义，不为“底层”而重写全部支持库。
5. 驱动接口区分初始化、启动、完成、超时、取消／停止和恢复；ISR 只做必要工作，不做无界阻塞或重处理。
6. DMA 要分析缓冲生命周期、对齐与并发可见性；有数据缓存的芯片再补 cache 一致性维护，不假定所有 Cortex-M 都有 D-cache。

**验收**

- 真板验证：连续数据、任意分片、环形回绕、超时、设备断连／缺失、输入超速；每项有结果、错误计数与恢复方式。
- 至少保存一份总线／时序捕获，能把手册、配置、波形和数据对应起来；串口打印“成功”不能替代波形证据。
- 解释至少三个真实接口问题的排查路径，例如错误时钟、引脚复用、帧丢失或 DMA 缓冲覆盖。
- 数据解析与策略保留 host 测试，寄存器、中断、DMA 和电气行为必须有板上验证。

### E3：FreeRTOS 与实时性

教学正文：[E3 同步与实时性](Embedded/E3-FreeRTOS-Realtime/README.md)。

**任务**

- 理解任务状态、抢占、时间片、tick、阻塞与唤醒；周期任务避免累积漂移，tick 延时不当作高精度硬件时序。
- 对比队列、任务通知、信号量、互斥锁、事件组、stream/message buffer 的语义；检查所选 API 的生产者／消费者约束。
- 区分任务 API 与 `FromISR` API；按官方 Cortex-M 移植说明配置中断优先级与 RTOS API 调用边界，不能只凭优先级数字大小猜测。
- 构造并解释优先级反转，理解互斥锁的优先级继承及其限制；明确锁顺序和最大持锁时间，不把关中断当作万能锁。
- 记录每个任务的周期、优先级、数据来源、截止时间预算、栈和阻塞条件；检查栈水位、分配失败与栈溢出检测。
- 对驱动回调、ISR 和任务交互给出所有权规则，避免持锁等待 IO、ISR 中阻塞或重复释放资源。

**验收**

1. 将 E2 采集链路拆成采集、解析、输出任务；用固定容量队列／通知连接，有明确过载策略。
2. 用 GPIO 翻转或合适的硬件计时记录 ISR 响应、任务执行、队列等待和周期抖动；注明测量开销。
3. 在声明负载和干扰条件下统计超期、队列峰值与栈水位。实测最大值是观测结果，不冒充严格 WCET 或硬实时证明。
4. 独立定位一次自造的死锁、优先级反转或任务饥饿，并用压力场景与回归测试验证修复。

### E4：真板代表作——有界数据采集与诊断固件

教学正文：[E4 采集与诊断固件](Embedded/E4-Data-Acquisition/README.md)。

**最小范围**

- 输入：E2 的真实传感器，或另一实验设备产生的带序号串口帧；先一种输入，不同时做全部总线。
- 处理：固定容量采集／解析缓冲、RTOS 任务调度、明确丢弃／拒绝策略与错误计数。
- 输出：UART 状态与数据导出；若已具备可验证的 Flash 器件，再加入持久化环形记录。
- 诊断：固件版本、复位原因、队列水位、错误数、栈水位与最小 fault 现场；明确捕获失败的处理。
- 非目标：量产 ECU、功能安全认证、完整 AUTOSAR、复杂 UI、云平台或 AI 模型。

**实现顺序**

1. 先定义协议、容量、采样周期、超时和交付合同：接收成功、处理成功、写入完成分别意味着什么。
2. 再串起驱动、任务与输出，加入唯一序号核对，不让串口调试日志改变被测链路的主要时序。
3. 触发输入超速、慢输出、器件缺失、任务超期和复位，核对结果与可观测性。
4. 如加入 Flash，读取擦除粒度、写入约束与寿命参数；明确校验、提交标记、断写恢复和磨损分布。CRC 是损坏检测，不是安全认证。

**验收**

- 排空后核对接收事件满足 `accepted = completed + explicitly_failed_or_dropped`，拒绝事件另计；有序号核查，无未解释丢失或重复。这不是 exactly-once 保证。
- 缓冲容量由测试断言；用 map、栈水位与运行测量核对资源预算，说明堆和运行时库的额外开销。
- 对每个错误场景说明能否自动恢复、何时返回错误、何时复位；禁止静默成功和无条件无限重试。
- Flash 若未实装／未测恢复，标为选修待验证，不把 RAM 模拟当作真实持久化。
- 提供结构图、任务表、引脚表、协议、构建烧录入口、测试步骤和已知限制。

### E5：BSP、可靠性与交付

教学正文：[E5 BSP 与交付](Embedded/E5-BSP-Delivery/README.md)。

**任务**

- 分离可 host 测试的协议／策略、RTOS 适配和板级驱动；形成小而明确的 BSP，不为可移植性创建大量空抽象。
- 固定工具链、CMSIS、厂商支持包、FreeRTOS 和器件驱动版本；记录链接与优化选项、map、固件尺寸和烧录方式。
- 理解复位源、看门狗、brown-out 与异常恢复。看门狗喂狗要反映关键任务进展，不能由无条件周期中断掩盖业务卡死。
- 自动化 host 回归与固件构建；板上集成、fault 与时序测试单独执行。host Sanitizer 不能证明 ISR、DMA 或 RTOS 调度正确。
- 制定专用板卡测试矩阵：空闲、正常满负载、持续过载、器件失败、任务停滞、软件／看门狗复位；存储断写使用可控测试，供电操作遵守器件规格。
- 模拟升级前先写镜像大小、分区与失败语义；Bootloader 与升级回滚放入 E6 深化，不把普通跳转代码称为可靠升级。

**验收**

1. 至少一次 2 小时真板稳定负载测试与一次过载测试，记录版本、输入速率、运行错误、超期、队列和栈趋势；这是阶段测试，不是量产稳定性证明。
2. 验证关键任务停滞能被检测，复位后可说明复位原因与丢失边界；不能仅展示“看门狗会重启”。
3. 在另一份干净构建环境按说明生成并烧录同一版本；无第二环境证据时保持待验证。
4. 输出两个定位案例和一个资源／时序优化案例，包含修复前后测量和代价，不强求所有指标都改善。

### E6：按岗位选择一个深化分支

教学正文：[E6 分支选择](Embedded/E6-Specialization/README.md)；分别阅读 [MCU/BSP](Embedded/E6-Specialization/MCU-BSP.md) 或 [Linux BSP/驱动](Embedded/E6-Specialization/Linux-BSP-Drivers.md)。

| 分支 | 学习与实现范围 | 必须留下的证据 |
| --- | --- | --- |
| MCU/BSP（主线延伸） | 为第二种板级配置移植一个驱动／BSP；或做最小 Bootloader、镜像校验与失败恢复，先定义分区和可用存储约束 | 真板启动与驱动验证；若选升级，测试截断／损坏镜像、失败后的可启动路径与恢复，不声称 CRC 能防恶意镜像 |
| Linux BSP/驱动（独立分支） | 选择有官方 BSP 的 ARM Linux 板；QEMU 先练启动，之后用真板验证。理解 BootROM/U-Boot/kernel/rootfs、设备树、交叉编译；Buildroot 或 Yocto 先选一种；实现一个简单 I2C/SPI 设备驱动并复用内核子系统 | 真板启动日志、设备树绑定、probe/remove、错误清理、实际器件读写、用户态访问和回归；字符设备 hello-world 或用户态串口程序不足以证明驱动能力 |

Linux 分支补充：内核 C、设备／总线／驱动模型、睡眠上下文、锁与中断、资源生命周期、设备树 binding、用户接口。内核 API 以选定版本官方文档为准，不使用陈旧教程硬套新内核。

根据岗位再选 CAN/CAN FD、UDS/DoIP、AUTOSAR Classic、低功耗或特定芯片；协议熟悉、架构理解、实际移植与实测证据分开描述。功能安全、实时保证与安全启动只学习原则，不声称完成认证。

## 三、社招准备与试投递条件

从 E0 并行训练，不等课程全部完成：

- **编码**：C 指针／数组、位操作、定长缓冲、环形队列、状态机、帧解析、超时／回绕、链表与常用算法。独立实现，解释复杂度、容量和失败行为。
- **手册阅读**：限时找到一项外设配置，说明时钟／引脚依赖、寄存器与验证方法；遇到未知芯片能提出查证步骤。
- **调试**：准备 fault、中断／DMA、RTOS 调度各一个案例；使用自造或公开实验，不编造线上故障与量产收益。
- **设计**：练习采集系统、通信驱动、看门狗与升级方案，先说明资源和实时预算，再说架构。
- **项目深挖**：准备 3 分钟概览与 15 分钟技术追问，说明独立完成的部分、证据、设计取舍与未实现边界。
- **陌生代码**：阅读一个公开驱动／BSP，独立做小改动并验证，证明不是只会复述自己的工程。

**MCU/RTOS 岗位试投递门槛**：E1–E5 有证据，能独立编码与板上排障，完成编码、手册阅读和项目深挖模拟。BSP／驱动岗位还需匹配的 E6 深度；按公开岗位要求定向小批量试投递，以技术反馈补缺口，不等所有选修学完。

## 四、每次学习与 AI 辅助

一次只推进一个可验收任务：

1. 先写输入／输出、资源、时序与失败语义。
2. 查当前芯片手册／官方文档，最小实现，必要时再读 HAL 或内核源码。
3. 做 host 回归与对应真板测试，保存版本、配置、波形／测量和异常结果。
4. 在 [Progress.md](./Progress.md) 更新证据、遗留问题和下一步；无硬件验证的项保持待验证。

AI 可以辅助解释手册、分析报错、生成局部代码与测试候选；寄存器、ISR 优先级、DMA/cache、链接地址和实时结论必须核对原始资料与板上证据。核心实现、阶段排障与模拟面试独立完成，不把 AI 生成的驱动当成已掌握。

## 五、参考入口

- 芯片资料：从所选器件的厂商页面获取 datasheet、reference manual、errata、板卡原理图与用户手册；版本与型号要对应。
- Cortex-M：[CMSIS-Core](https://arm-software.github.io/CMSIS_6/latest/Core/index.html)，配合所选核心官方架构资料。
- RTOS：[FreeRTOS 文档](https://www.freertos.org/Documentation/00-Overview)、[Cortex-M 移植与中断说明](https://www.freertos.org/Documentation/02-Kernel/03-Supported-devices/04-Demos/ARM-Cortex/RTOS-Cortex-M3-M4)。
- 构建调试：[GNU Arm 工具链](https://developer.arm.com/Tools%20and%20Software/GNU%20Toolchain)、[OpenOCD 文档](https://openocd.org/doc/html/index.html)；可先使用板卡官方调试工具。
- Linux 选修：[内核驱动模型](https://docs.kernel.org/driver-api/driver-model/overview.html)、[Buildroot 手册](https://buildroot.org/downloads/manual/manual.html)、[Yocto 文档](https://docs.yoctoproject.org/)。
