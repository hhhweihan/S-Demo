## 本周结果（完成后填写）

**Benchmark（分配/释放 100 万次）：**
| 方案 | 耗时 |
|------|------|
| new/delete | 22.543 ms |
| malloc/free | 22.225 ms |
| FixedAllocator | 2.121 ms |

**读源码笔记：**

1. nginx 大小块区分：`size <= pool->max` 走小块分配，`size > pool->max` 走大块分配；`pool->max = min(size - sizeof(ngx_pool_t), ngx_pagesize - 1)`。
2. 结构体字段含义：`d.last` 是当前 block 的下一个可分配位置，`d.end` 是当前 block 末尾边界，`d.next` 是下一个 pool block 指针。
3. 不支持单块释放的原因：小块分配采用 bump-pointer 线性推进，只追求快速申请与生命周期末端批量回收，不维护单对象回收元数据；只有 large 链支持单块 `pfree`。
4. 与我的实现的差异：我的 `FixedAllocator` 是固定大小 block + free list，支持 O(1) 单块回收；nginx pool 是“小块顺序切分 + 大块单独挂链”，更偏向请求级内存批量释放。

**本周遇到的最难问题：**

1. `deallocate()` 的边界合法性检查。只是把指针塞回 free list 很容易写，但如果传入的不是 allocator 管理的地址，或者地址没有按 `block_size_` 对齐，就会破坏整个空闲链表，所以需要逐个 chunk 做范围判断和对齐断言。
2. benchmark 的结果可信度。若直接测 `FixedAllocator` 且同时包含扩容过程，就会把初始化成本混进热路径；这次通过预分配 `1,000,000` 个 block，把测试重点收敛到 allocate/deallocate 本身，结果更能反映 free list 方案的真实优势。
