**读文档笔记：**

1. arena 解决的问题：
	arena 的核心作用是把多线程下对同一套 allocator 元数据的竞争拆散。jemalloc 不是只做“每个 free list 一把锁”，而是让线程优先命中各自 arena，减少锁冲突和缓存行在多核之间来回迁移。

2. size class 划分：
	jemalloc 比我现在的 15 档 size class 更精细。早期论文里就分成 `small / large / huge`，其中 `small` 又拆成 `tiny`、`quantum-spaced`、`sub-page`；后续版本进一步做成“每次容量翻倍之间有 4 个档位”，内部碎片控制明显更成熟。

3. tcache 作用：
	tcache 是线程局部缓存。线程可以直接从本地缓存满足大量小对象分配/释放，不需要每次都拿 arena 的锁；只有缓存耗尽或批量回收时才进入共享路径，因此能显著减少锁竞争。代价是额外内存占用和一定的碎片。

4. 与我的实现的差距：
	我现在的 PoolAllocator 仍然是教学版实现：单实例、静态 size class、header 标记、每个 class 一把锁。jemalloc 则是完整体系：多 arena、thread cache、更细粒度 size class、slab/extent/page 管理、purge 与统计接口、以及更成熟的碎片与并发控制策略。下一步如果要继续逼近 jemalloc，优先级最高的是做 TLS cache 或 per-thread/per-cpu arena。

**TLS cache 最小原型（已实现）：**

- 已在 `PoolAllocator` 上方增加线程本地缓存层：每个线程、每个 size class 都有一个轻量 freelist。
- 小对象分配优先命中 `thread_local` cache；cache miss 时再从共享 `FixedAllocator` 批量 refill。
- 小对象释放优先回到当前线程 cache；当缓存超过上限时，再批量 flush 回共享池。
- 为支持这条路径，`FixedAllocator` 新增了批量 `allocate_batch / deallocate_batch` 接口。
- 新增了 Day-014 原型测试：同一线程回收后再次申请同一 class，会优先复用线程本地缓存中的地址。

**如果要实现 TLS（线程局部）cache，需要改哪里？**

1. **先增加一个线程本地缓存层，而不是直接改 `FixedAllocator` 的 free list。**
	当前 `FixedAllocator` 已经负责真正的块管理和扩容，TLS cache 更适合放在 `PoolAllocator` 之上。也就是：线程先访问自己的本地 cache，只有本地 cache miss 时，才回退到共享的 `FixedAllocator`。

2. **为每个线程维护“按 size class 分桶”的本地 freelist。**
	可以设计成：
	```cpp
	struct ThreadCacheBin {
		 void* head;
		 std::size_t count;
	};

	struct ThreadCache {
		 ThreadCacheBin bins[15];
	};

	thread_local ThreadCache tls_cache;
	```
	这样 15 个小对象 class 都有各自的线程局部缓存，大对象仍然直接走 `malloc/free`。

3. **改 `PoolAllocator::allocate(size_t)` 的顺序。**
	新流程应该是：
	- 先做 `size_to_class(n)`
	- 如果是大对象，继续走现有 `malloc + header`
	- 如果是小对象，先看 `tls_cache.bins[class_index]`
	- 本地 bin 非空：直接弹出一个块返回，不加锁
	- 本地 bin 为空：从共享 `FixedAllocator` 批量拉一小批块到本地 cache，再返回一个

4. **改 `PoolAllocator::deallocate(void*)` 的顺序。**
	回收时先读 header 拿到 class index：
	- 大对象直接 `free`
	- 小对象优先放回当前线程的 `tls_cache.bins[class_index]`
	- 如果本地 bin 超过上限，例如 32 或 64 个块，就批量归还一部分给共享 `FixedAllocator`
	这样热路径上的 allocate/deallocate 大多数都可以不进锁。

5. **要新增“批量 refill / flush”接口。**
	目前 `FixedAllocator` 只有单块 `allocate/deallocate`。如果要让 TLS cache 真正划算，最好给它增加批量接口，例如：
	- `allocate_batch(void** out, size_t count)`
	- `deallocate_batch(void** blocks, size_t count)`
	否则本地 cache miss 时还得循环拿锁多次，收益会被吃掉。

6. **线程退出时要把缓存刷回共享池。**
	因为 `thread_local` 缓存会在每个线程里囤对象，所以线程结束时要把这些对象批量 flush 回 `FixedAllocator`。否则对象会跟着线程生命周期长期滞留，放大内存占用。

7. **统计接口也要分两层看。**
	现在 `stats_for_class()` 只看共享 `FixedAllocator` 的 `used`。加了 TLS cache 后，这个统计会失真，因为有一部分块停在线程本地。后续最好拆成：
	- shared stats
	- thread cache stats
	- merged stats

8. **这一步的收益点和风险点很明确。**
	收益：
	- 小对象热路径可以绕开锁
	- 多线程竞争会显著下降
	- 更接近 jemalloc 的实际思路

	风险：
	- 内存占用会上升，因为每个线程都囤一批对象
	- 线程退出和 cache flush 的实现更复杂
	- 统计、调试和错误定位都会比当前版本麻烦

**建议的实现顺序：**

1. 先只给 `PoolAllocator` 的 15 个小对象 class 加 `thread_local` 单链表缓存。
2. 每个 class 先设一个很小的上限，比如 `max_cached = 32`。
3. 先不做 per-thread arena，只做“单共享池 + TLS cache”。
4. 待 TLS cache 跑通后，再考虑批量接口、线程退出 flush、以及更细的统计信息。

**Week 02 总结：**

1. 这一周从单一 `FixedAllocator` 扩展到了通用 `PoolAllocator`，完成了 `size class` 映射、小对象池化、大对象 fallback、header 标记、`deallocate(ptr)`、`std::allocator` 适配、线程安全和 TLS cache 原型。
2. 功能上已经能支持 `std::vector<int, MyAllocator<int>>` 正常扩容和读取，也能处理多线程下的小对象分配/释放。
3. 性能上，本周后半段的关键转折点不是“继续调锁”，而是引入 TLS cache：Release 下 32 字节对象单线程路径从之前约 `19.597 ms` 进一步降到 `5.624 ms`，相对 `new/delete` 达到约 `4.916x`。
4. 与 jemalloc 对照后，本周最大的认知收获是：真正决定并发分配器上限的，不是单个 free list 写得多快，而是 `arena + 更细粒度 size class + thread cache + 更系统的页/extent 管理` 这一整套结构设计。
