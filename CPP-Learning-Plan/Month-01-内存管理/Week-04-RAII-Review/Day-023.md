## 今日目标

昨天的 `scope_guard` 已经把“退出作用域时自动执行清理”这个模型搭起来了。今天要做的是把它往工程使用方式上再推进两步：

1. **先做语法糖。** 用 `DEFER` 宏把 `make_scope_guard([&]{ ... })` 压缩成一行，降低使用成本。
2. **再做具象封装。** 把 `FILE*` 这种真实资源包进 `FileGuard`，让“打开即拥有、析构即关闭”真正落地。

如果昨天解决的是“思想”，今天解决的就是“怎么把这个思想变成顺手可用的工具”。

---

## 为什么先做 `DEFER` 宏

虽然昨天已经能这样写：

```cpp
auto guard = make_scope_guard([&] {
  fclose(f);
});
```

但在工程里，很多清理动作其实只是一次性的小收尾。每次都显式写一个变量名，会让代码显得偏重。

所以常见做法是再封一层：

```cpp
DEFER(fclose(f));
```

这样读代码的人一眼就知道：

> 这里登记了一段“离开当前作用域时执行”的收尾逻辑。

`DEFER` 没有引入新机制，它只是把昨天的 `scope_guard` 包装成更接近 Go `defer` 的写法。

---

## `DEFER` 宏的关键问题是什么

看起来宏只有一行：

```cpp
#define DEFER(code) auto _defer_##__LINE__ = make_scope_guard([&] { code; })
```

但它实际上解决了两个小问题：

### 1. 自动生成唯一变量名

宏里必须创建一个局部变量，否则 guard 会在这一行末尾立刻析构，根本活不到作用域结束。

所以我们通常用 `__LINE__` 拼一个变量名，避免同一作用域里多个 `DEFER(...)` 冲突。

### 2. 默认按引用捕获

```cpp
[&] { fclose(f); }
```

这里选择引用捕获，是因为大多数 `defer` 场景都希望看到当前作用域里资源句柄的最新状态。

但这也意味着：如果被捕获变量在后面改成了别的资源，清理动作作用的对象也会跟着变化。所以 `DEFER` 好用，但使用者必须清楚闭包捕获语义。

---

## 为什么还需要 `FileGuard`

`DEFER` 很灵活，但它有一个现实问题：

```cpp
FILE* f = fopen(path, "w");
if (!f) {
  throw ...;
}
DEFER(fclose(f));
```

这种写法本质上还是两段式：

1. 先拿到裸资源
2. 再手动登记清理动作

而更彻底的 RAII 写法应该是：

> 资源一旦构造成功，就立刻进入对象托管状态。

所以 `FileGuard` 的价值不在于“少写一个 `fclose`”，而在于它把文件句柄的所有权和对象生命周期彻底绑定起来。

---

## `FileGuard` 该具备哪些语义

最小教学版只需要这几个行为：

### 1. 构造时打开文件

```cpp
FileGuard file("demo.txt", "w");
```

如果 `fopen` 失败，构造函数应立即抛异常，让对象根本不进入“半有效状态”。

### 2. 析构时关闭文件

```cpp
~FileGuard() {
  if (file_ != nullptr) {
    std::fclose(file_);
  }
}
```

这样无论正常返回还是异常展开，文件都能被关闭。

### 3. 禁止拷贝

两个 `FileGuard` 不能共同声称自己拥有同一个 `FILE*`，否则析构时就会 double-close。

### 4. 支持移动

移动语义允许你把文件所有权从一个 guard 转给另一个 guard，这和前几天 `unique_ptr` 的模型完全一致。

## 参考实现

下面这个版本已经足够覆盖今天需要掌握的核心行为：

```cpp
#pragma once

#include <cstdio>
#include <stdexcept>
#include <string>
#include <utility>

class FileGuard {
  FILE* file_ = nullptr;
  std::string path_;

  void close_current() noexcept {
    if (file_ != nullptr) {
      std::fclose(file_);
      file_ = nullptr;
    }
  }

public:
  FileGuard(const char* path, const char* mode) : path_(path) {
    file_ = std::fopen(path, mode);
    if (file_ == nullptr) {
      throw std::runtime_error("failed to open file: " + path_);
    }
  }

  ~FileGuard() noexcept {
    close_current();
  }

  FileGuard(const FileGuard&) = delete;
  FileGuard& operator=(const FileGuard&) = delete;

  FileGuard(FileGuard&& other) noexcept
    : file_(other.file_), path_(std::move(other.path_)) {
    other.file_ = nullptr;
  }

  FileGuard& operator=(FileGuard&& other) noexcept {
    if (this != &other) {
      close_current();
      file_ = other.file_;
      path_ = std::move(other.path_);
      other.file_ = nullptr;
    }
    return *this;
  }

  FILE* get() const noexcept {
    return file_;
  }

  explicit operator bool() const noexcept {
    return file_ != nullptr;
  }

  const std::string& path() const noexcept {
    return path_;
  }
};
```

这里特意保留了 `close_current()`，因为它把“析构关闭”和“移动赋值前先关闭旧资源”统一到了同一个局部逻辑里，后面写 socket guard、mutex guard 时也会反复用到这种结构。

## 三条测试分别在验证什么

### 1. `DEFER` 正常关闭

```cpp
{
  FILE* file = std::fopen(path, "w");
  DEFER(std::fclose(file));
  std::fputs("hello\n", file);
}
```

验证宏能正确把清理动作延迟到作用域结束时执行。

### 2. `FileGuard` 成功路径和移动语义

```cpp
FileGuard file(path, "w");
FileGuard moved(std::move(file));
```

验证：

- 原对象被移空
- 新对象继续持有资源
- 最终文件只关闭一次

### 3. 构造失败路径

```cpp
try {
  FileGuard missing("not-exist/file.txt", "r");
} catch (const std::runtime_error&) {
}
```

验证构造失败时会直接抛异常，而不是留下一个内部 `FILE* == nullptr` 的半残对象。

## 最容易犯的错

### 1. `DEFER` 宏没有持有局部变量

如果只是展开出一个临时对象，它会在语句结束时立刻析构，完全不是“作用域退出执行”。

### 2. `FileGuard` 允许拷贝

这会让两个对象都在析构时关闭同一个 `FILE*`，属于典型 double-close。

### 3. 移动后忘记把源对象置空

本质上还是 double-close，只不过这次是“移动语义写坏了”。

### 4. 构造失败不抛异常，只留下空句柄

这种设计会让对象处于“看起来构造成功，实际上内部没资源”的状态，后面每个调用点都得补额外判空，RAII 的价值会被削弱很多。

---

## `DEFER` 和 `FileGuard` 的分工

可以这样记：

- `DEFER`：适合一次性、局部的小清理动作
- `FileGuard`：适合明确的资源所有权封装

也就是说：

> `DEFER` 更像是轻量级的“作用域收尾登记”；`FileGuard` 更像是领域明确的资源拥有者对象。

两者都基于 RAII，但抽象层次不同。

---

## 今日总结（完成后填写）

1. `DEFER` 宏没有改变 `scope_guard` 的本质，只是把“登记退出清理动作”的写法压缩成了更顺手的语法糖。
2. `FileGuard` 让 `FILE*` 从“裸资源 + 手动关闭”变成“构造即接管、析构即释放”的 RAII 对象。
3. 禁止拷贝、允许移动，是这类资源句柄封装最重要的所有权约束。
4. 构造失败直接抛异常，比留下半有效对象更符合 RAII 思路，也更能减少后续分支复杂度。
