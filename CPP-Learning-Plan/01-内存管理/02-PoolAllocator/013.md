**阅读范围：**
- 以 2006 年 BSDCan 论文前 10 页为主。
- 第 3 问的 `tcache` 在这篇早期论文里还没有今天这么完整的形态，因此额外参考了 jemalloc 官方手册对 thread-specific cache 的说明。

**答案整理：**

1. **arena 解决了什么问题？**
  jemalloc 引入多个 arena 的核心目标，是把原本所有线程都要争用的一套分配器全局数据结构拆散。这样不同线程通常只会命中自己所属的 arena，锁竞争和缓存行来回迁移都会显著减少。论文里明确提到，仅仅把一个全局锁拆成多个 free list 锁仍然不够，因为即使锁冲突下降，allocator 元数据在多核之间来回“sloshing”也会拖慢性能；多个 arena 才是更有效的并发扩展手段。

2. **jemalloc 的 size class 如何划分？比我的更精细还是更粗糙？**
  jemalloc 明显比我现在的 PoolAllocator 更精细。论文中的早期版本把分配分成 `small / large / huge` 三大类，其中 `small` 里又细分为 `tiny`、`quantum-spaced`、`sub-page`：
  - tiny: 2、4、8 字节
  - quantum-spaced: 16 到 512 字节，按 quantum 间隔增长
  - sub-page: 1 KiB、2 KiB
  - large: 4 KiB 到 1 MiB
  - huge: 2 MiB 及以上
  后续 jemalloc 的 size class 还进一步细化成“每次容量翻倍之间放 4 个档位”，把内部碎片控制在大约 20% 左右。相比之下，我现在只有 15 个小对象档位，粒度更粗，内部碎片更大，但实现简单很多。

3. **tcache 的作用是什么？为什么能减少锁竞争？**
  tcache 是线程局部缓存。它把一部分常用 size class 的空闲对象直接缓存在线程本地，线程做大多数小对象分配/释放时，不必立刻回到 arena 的共享数据结构上拿锁。这样常见路径可以完全绕开同步，只有本地缓存耗尽或需要批量归还对象时，才和 arena 交互。代价是每个线程都会囤一部分对象，内存占用和碎片会上升，但换来的是显著更低的锁竞争和更好的多线程吞吐。

4. **jemalloc 和我实现的 PoolAllocator 的核心差距在哪里？**
  差距主要不在“有没有 free list”，而在体系结构层面：
  - jemalloc 是多 arena 设计，我现在是单实例下每个 size class 一把锁，线程都会竞争同一组 allocator。
  - jemalloc 有 tcache，本地线程大部分请求可以不加锁；我现在每次小对象分配/释放都会进锁。
  - jemalloc 的 size class 更细，且围绕 quantum、page、slab、extent 设计，碎片控制更成熟；我现在是静态 size class + 简单 header。
  - jemalloc 把 metadata、slab、extent、purge、arena 绑定、stats、profiling、mallctl 调优接口都做成了完整系统；我当前实现还只是教学版的 pool allocator。
  - jemalloc 会系统性处理 cache locality、false sharing、页级管理和后台回收；我目前只做到基本可用和线程安全，还没有 TLS cache、arena 亲和、页回收等能力。

**结论：**
- jemalloc 真正解决并发扩展性的关键不是“更快的 free list”，而是 “arena + 更细粒度 size class + tcache + 页级/extent 级管理” 这套组合拳。
- 如果要继续优化当前实现，最直接的演进方向不是继续微调一把全局锁，而是先做 `TLS cache` 或 `per-thread / per-cpu arena`。
