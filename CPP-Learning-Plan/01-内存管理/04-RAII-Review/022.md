## 今日目标

前面三周主要在处理“谁拥有资源”。到了 RAII 这一周，要把视角再往上提一层：

> 资源管理不应该散落在函数的每个 return、每个 if、每个 catch 里，而应该和对象生命周期绑定。

`scope_guard` 就是这个思想最小、最纯粹的实现。

今天只抓住三件事：

1. **把清理动作封装成对象。** 构造时拿到一个可调用对象，析构时自动执行。
2. **把“是否执行清理”变成显式状态。** 默认执行，必要时可以 `dismiss()` 取消。
3. **让异常路径和正常路径统一。** 无论函数是正常返回还是抛异常，离开作用域时都走同一条清理逻辑。

如果这三个点真正想通，后面的 `DEFER` 宏、文件句柄封装、锁回滚、事务回滚，本质上都只是同一模型的不同外观。

## 为什么需要 `scope_guard`

先看最常见的一类代码：

```cpp
void process() {
  Resource* r = acquire();
  if (!r) {
    return;
  }

  if (!step1()) {
    release(r);
    return;
  }

  if (!step2()) {
    release(r);
    return;
  }

  release(r);
}
```

这段代码的问题不是“不会释放”，而是：

1. 清理逻辑重复
2. 新增返回路径时很容易漏掉释放
3. 一旦中间改成抛异常，`release(r)` 可能直接被绕过

`scope_guard` 的思路是把“离开作用域时要执行的动作”提前登记：

```cpp
void process() {
  Resource* r = acquire();
  if (!r) {
    return;
  }

  auto guard = make_scope_guard([&] {
    release(r);
  });

  if (!step1()) {
    return;
  }

  if (!step2()) {
    return;
  }
}
```

这样函数里不需要在每个出口重复写释放动作，控制流一下就干净了。

## `scope_guard` 的本质

可以把它理解成一个只做一件事的 RAII 对象：

- 构造时接收一个清理函数
- 析构时执行这个清理函数
- 如果调用了 `dismiss()`，析构时跳过执行

和智能指针相比，`scope_guard` 没有“管理哪块内存”的语义，它管理的是一个更抽象的东西：

> 作用域退出时必须发生的一段收尾动作。

这也是为什么它非常适合：

- 解锁
- 回滚临时状态
- 关闭句柄
- 删除临时文件
- 统计埋点或日志收尾

## 最小实现要解决什么问题

教学版 `ScopeGuard<F>` 其实只需要解决四个点：

### 1. 保存回调

```cpp
F func_;
```

它可以是 lambda、函数对象，甚至是 `std::function`。教学版最适合直接模板化存储，避免额外类型擦除成本。

### 2. 记录是否取消执行

```cpp
bool dismissed_ = false;
```

默认构造完成后，guard 就应该在析构时执行；只有显式调用 `dismiss()` 才取消。

### 3. 析构时执行清理

```cpp
~ScopeGuard() {
  if (!dismissed_) {
    func_();
  }
}
```

这一步才是真正把“清理逻辑绑定到对象生命周期”上。

### 4. 禁止拷贝，支持移动

如果一个 guard 能被随意拷贝，就会出现两个对象都认为自己应该在析构时执行同一份清理动作，导致重复执行。

所以教学版至少应该：

- 禁止拷贝构造和拷贝赋值
- 支持移动语义，把执行责任转移给新对象

这一点和 `unique_ptr` 的所有权转移非常像，只不过今天转移的不是堆对象，而是“收尾责任”。

## 参考实现

下面这个版本已经覆盖今天最关键的语义：

```cpp
#pragma once

#include <exception>
#include <type_traits>
#include <utility>

template<typename F>
class ScopeGuard {
  F func_;
  bool dismissed_ = false;
  int uncaught_on_create_ = std::uncaught_exceptions();

public:
  explicit ScopeGuard(F&& f) noexcept(std::is_nothrow_move_constructible_v<F>)
    : func_(std::forward<F>(f)) {}

  explicit ScopeGuard(const F& f) noexcept(std::is_nothrow_copy_constructible_v<F>)
    : func_(f) {}

  ScopeGuard(const ScopeGuard&) = delete;
  ScopeGuard& operator=(const ScopeGuard&) = delete;

  ScopeGuard(ScopeGuard&& other) noexcept(std::is_nothrow_move_constructible_v<F>)
    : func_(std::move(other.func_)),
      dismissed_(other.dismissed_),
      uncaught_on_create_(other.uncaught_on_create_) {
    other.dismiss();
  }

  ScopeGuard& operator=(ScopeGuard&& other) = delete;

  ~ScopeGuard() noexcept {
    if (!dismissed_) {
      func_();
    }
  }

  void dismiss() noexcept {
    dismissed_ = true;
  }

  bool active() const noexcept {
    return !dismissed_;
  }

  bool created_during_unwind() const noexcept {
    return std::uncaught_exceptions() > uncaught_on_create_;
  }
};

template<typename F>
auto make_scope_guard(F&& f) {
  using GuardFunc = std::decay_t<F>;
  return ScopeGuard<GuardFunc>(std::forward<F>(f));
}
```

这里多留了一个 `uncaught_on_create_`，不是因为今天必须做异常专用 guard，而是为了让你顺手建立一个概念：

标准库和工业实现里经常会继续分出：

- `scope_exit`：无论正常返回还是异常都执行
- `scope_fail`：只在异常展开时执行
- `scope_success`：只在正常路径执行

今天先实现最基础的 `scope_exit` 语义就够了。

## 为什么要支持移动而不是只禁止拷贝

如果只写最小版，很多教程会直接把移动也禁掉，因为“局部变量本来也够用了”。

但从语义上看，支持移动更完整，因为：

```cpp
auto guard = make_scope_guard([&] { cleanup(); });
auto next = std::move(guard);
```

这应该表示“把清理责任交给 `next`”。

所以移动构造的正确动作是：

1. 把回调和状态转移到新对象
2. 把旧对象 `dismiss()` 掉，避免析构时重复执行

这和 `unique_ptr` 的 move after nulling 是同一类问题。

## 三条测试路径分别在验证什么

### 1. 正常路径

```cpp
{
  auto guard = make_scope_guard([&] {
    std::cout << "cleanup\n";
  });
}
```

验证 guard 离开作用域时，析构函数确实会调用回调。

### 2. `dismiss()` 路径

```cpp
{
  auto guard = make_scope_guard([&] {
    std::cout << "cleanup\n";
  });
  guard.dismiss();
}
```

验证“默认执行，但允许显式取消”这个状态切换是否正确。

### 3. 异常路径

```cpp
try {
  auto guard = make_scope_guard([&] {
    std::cout << "cleanup on exception\n";
  });
  throw std::runtime_error("boom");
} catch (...) {
}
```

验证异常展开时，栈上对象照样会析构，所以 guard 仍然会执行清理。

这一条是今天最关键的价值点，因为 RAII 真正强的地方从来不是“少写几行释放代码”，而是：

> 它让异常路径不需要单独维护另一套资源清理逻辑。

## 最容易犯的错

### 1. 忘记禁止拷贝

这样两个 guard 会在析构时重复执行同一个清理动作，轻则日志重复，重则 double close、double unlock。

### 2. 支持移动但没有让源对象失效

这会导致移动后新旧两个对象都执行清理，问题本质和重复拷贝一样。

### 3. 析构函数里让异常继续往外抛

如果析构发生在栈展开期间，再抛新异常会直接触发 `std::terminate()`。所以教学版至少要默认回调不抛异常，或者把析构函数声明成 `noexcept`。

### 4. 捕获方式写错

比如：

```cpp
auto ptr = acquire();
auto guard = make_scope_guard([=] { release(ptr); });
```

这里值捕获和引用捕获都可能是对的，但必须清楚资源句柄后续是否会变化。不是 guard 本身难，而是闭包捕获语义必须想清楚。

## 和智能指针的关系

可以这样对照：

| 工具 | 管理对象 | 触发时机 | 解决的问题 |
|------|----------|----------|------------|
| `unique_ptr` | 堆对象 | 智能指针析构 | 独占所有权 |
| `shared_ptr` | 堆对象 + 控制块 | 最后一个拥有者析构 | 共享所有权 |
| `scope_guard` | 任意清理动作 | 当前作用域结束 | 统一收尾逻辑 |

所以 `scope_guard` 不是智能指针的替代品，而是把 RAII 从“堆内存”推广到了“任意资源收尾动作”。

## 今日总结（完成后填写）

1. `scope_guard` 的本质是把“退出作用域时要执行的动作”封装成一个栈对象。
2. 默认执行、显式 `dismiss()` 取消，是它最核心的状态模型。
3. 异常路径之所以也能清理，不是因为做了特殊分支，而是因为 C++ 栈展开时照样会调用析构函数。
4. `scope_guard` 让资源释放、回滚、解锁这类收尾逻辑从控制流分支里抽离出来，代码更短，也更不容易漏。
