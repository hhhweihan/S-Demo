## 查阅结论总览

结合 libc++ 中 `__memory/shared_ptr.h` 的实现，可以先记住三件事：

1. `shared_ptr` 仍然是“对象指针 + 控制块”模型，这一点和教学版完全一致。
2. libc++ 至少有两类重要控制块：
   - `__shared_ptr_pointer`
   - `__shared_ptr_emplace`
3. 它们最大的区别，不是“功能名不一样”，而是**对象和控制块是不是放在同一块分配内存里**。

---

## 问题 1：libc++ 的两种控制块分别是什么？

### `__shared_ptr_pointer`

这类控制块用于处理：

- `shared_ptr<T>(new T)`
- 带自定义 deleter 的构造
- 带 allocator 的 shared_ptr 构造
- 从 `unique_ptr` 转 `shared_ptr` 的路径

它的典型职责是：

1. 存储对象指针 `__ptr_`
2. 存储删除器 `__deleter_`
3. 存储控制块自身使用的 allocator `__alloc_`
4. 当共享计数归零时，用 deleter 处理对象
5. 当共享计数和弱计数都归零时，释放控制块本身

从 libc++ 代码可以看到，它本质上是一个“**控制块 + 外部对象指针 + 删除器/分配器**”的组合。

### `__shared_ptr_emplace`

这类控制块用于：

- `allocate_shared`
- `make_shared`

它的关键点在于：

> 对象不是在外面 `new` 出来再塞进控制块，而是直接构造在控制块内部预留的存储区里。

也就是说，`__shared_ptr_emplace` 既是控制块，又在内部直接放对象存储。

### 本质区别

可以直接记成一句话：

- `__shared_ptr_pointer`：**对象在外面，控制块单独管它**
- `__shared_ptr_emplace`：**对象就在控制块里面，一起分配，一起管理**

## 问题 2：为什么 `make_shared` 少一次分配？

### 普通写法：`shared_ptr<T>(new T)`

这条路径通常至少有两次分配：

1. `new T` 分配对象本体
2. `shared_ptr` 再分配一块控制块

所以对象和控制块是分开的。

### `make_shared<T>(args...)`

这条路径通常只做一次更大的分配：

1. 一次性分配“控制块 + 对象存储”这整块内存
2. 在这块内存里构造对象

libc++ 的 `allocate_shared`/`make_shared` 就是通过 `__shared_ptr_emplace` 走这条路径。

### 这样做的收益

1. **少一次堆分配**，通常更快
2. **对象和控制块更局部**，缓存友好
3. **异常安全更容易收束**，因为资源集中在一处管理

### 代价和限制

1. 对象和控制块生命周期绑定更紧
2. 如果还有 `weak_ptr` 留着，控制块不能释放，意味着那整块内存会比对象析构时间活得更久
3. 并不是所有场景都适合 `make_shared`，尤其是需要自定义删除策略时要具体看设计

## 问题 3：libc++ 如何处理 deleter？

在 `__shared_ptr_pointer` 路径里，deleter 是控制块的一部分。

从实现上看，它会把：

- 对象指针
- 删除器类型 `_Dp`
- allocator `_Alloc`

一起放进控制块。

当共享计数归零时，控制块调用的不是固定的 `delete ptr`，而是：

```cpp
__deleter_(__ptr_)
```

这说明标准库从设计上就支持“资源释放策略可替换”。

这件事很重要，因为工程里很多资源根本不是用 `delete` 释放的，例如：

- `FILE*` 需要 `fclose`
- socket 需要 `close` / `closesocket`
- 某些对象需要回到对象池，而不是直接 `delete`

### 我的教学版支持吗？

目前前几天的教学版 **不支持** 自定义 deleter。

我们写的是：

```cpp
delete ptr;
```

所以这版只能管理“默认 `delete` 即可回收”的对象。

如果要继续升级，可以把控制块改造成：

```cpp
template<typename T, typename Deleter>
struct ControlBlockPtr : ControlBlockBase {
    T* ptr;
    Deleter deleter;

    void destroy_object() override {
        deleter(ptr);
        ptr = nullptr;
    }
};
```

这就更接近 libc++ 的 `__shared_ptr_pointer` 设计了。

## 和教学版实现逐项对照

| 维度 | 教学版 | libc++ |
|------|--------|--------|
| 控制块模型 | 有 | 有 |
| `use_count` / `weak_count` | 有 | 有 |
| `make_shared` 单次分配 | 没有 | 有 |
| 自定义 deleter | 没有 | 有 |
| allocator 感知 | 几乎没有 | 完整支持 |
| `enable_shared_from_this` | 可做最小版 | 有完整集成 |
| 异常安全处理 | 简化版 | 很严谨 |

可以看到，前几天的学习并没有偏题。基础模型是对的，只是标准库把“真实工程所需的复杂性”全部补上了。

## 今天最重要的收获

### 1. 教学版和标准库的核心架构是一致的

本质仍然是：

> 指向对象的句柄 + 一个独立管理生命周期的控制块

### 2. `make_shared` 的关键不是“少写点代码”

它的真正价值是对象与控制块的一次性分配，这是一种布局优化。

### 3. deleter 是控制块职责的一部分

标准库不是在 `shared_ptr` 外面“临时记住一个函数”，而是把 deleter 作为控制块状态认真保存下来。

---

## 今日总结（完成后填写）

1. libc++ 中，`__shared_ptr_pointer` 主要负责“外部对象 + 控制块 + deleter/allocator”；`__shared_ptr_emplace` 主要负责 `make_shared/allocate_shared` 的“对象内嵌控制块”路径。
2. `make_shared` 比 `shared_ptr<T>(new T)` 少一次分配，是因为它把对象和控制块放进同一块内存里统一分配。
3. libc++ 通过在控制块里保存 deleter 和 allocator 来支持自定义回收策略，这比教学版固定写死 `delete` 更接近真实工程。
4. 标准库的复杂度并不是“概念变了”，而是把教学版模型工程化、泛化并做了异常安全收口。
