## 今日目标

很多人会说一句模糊的话：

> `shared_ptr` 是线程安全的。

这句话不够精确，甚至在很多语境下是误导性的。

今天真正要搞清楚的是三层问题：

1. **控制块的引用计数是不是线程安全？**
2. **多个 `shared_ptr` 句柄并发操作时，哪些情况安全？**
3. **被管理对象本身是不是因为用了 `shared_ptr` 就自动线程安全？**

结论先给出来：

- 控制块的引用计数增减是线程安全的
- 多个线程并发操作“不同的 `shared_ptr` 对象”但共享同一控制块，通常是安全的
- 多个线程并发读写“同一个 `shared_ptr` 变量对象”，不是线程安全的
- `shared_ptr` 不会替你保证被管理对象本身线程安全

---

## 先把术语说清楚

### 场景 A：同一个 `shared_ptr` 对象

例如所有线程都直接操作同一个变量：

```cpp
std::shared_ptr<int> sp;
```

如果多个线程同时对这个变量做赋值、reset、swap 等修改，这是在并发读写**同一个对象本身**。

### 场景 B：不同 `shared_ptr` 对象，但共享同一个控制块

例如：

```cpp
auto sp1 = std::make_shared<int>(42);
auto sp2 = sp1;
```

`sp1` 和 `sp2` 是两个不同的智能指针对象，但它们连到同一个控制块。

很多资料里“shared_ptr 线程安全”的说法，真正指的是这个场景下对控制块计数的增减是线程安全的。

---

## 三个结论分别怎么理解

### 结论 1：多线程同时只读同一个 `shared_ptr`，安全

只读的意思是：

- 只调用不修改句柄状态的操作
- 例如拷贝一个稳定可见的值、读取 `get()`、判断是否为空

如果没有其他线程同时改这个同一个变量，那么只读没有竞争。

但更准确地说，这里真正安全的前提是：

> 没有线程在并发写这个 `shared_ptr` 对象本身。

### 结论 2：多线程同时对不同 `shared_ptr` 做拷贝/析构，安全

前提是它们共享同一控制块，但操作的是不同句柄对象。

例如：

```cpp
auto base = std::make_shared<BigObj>();

std::thread t1([base] {
  auto local = base;
});

std::thread t2([base] {
  auto local = base;
});
```

这里引用计数的加减发生在共享控制块上，标准库通过原子操作保证这类增减是安全的。

### 结论 3：多线程同时修改同一个 `shared_ptr`，不安全

例如：

```cpp
std::shared_ptr<int> sp = std::make_shared<int>(1);

std::thread t1([&] { sp = std::make_shared<int>(2); });
std::thread t2([&] { sp.reset(); });
```

这里竞争的不是控制块计数，而是 `sp` 这个变量对象自身的内部状态。

赋值操作涉及：

- 读取旧控制块
- 调整计数
- 写入新指针/新控制块

这不是一个原子整体，所以需要外部同步。

## 验证代码样例

### 场景 1：多线程只读同一个 `shared_ptr`

```cpp
#include <memory>
#include <thread>
#include <vector>
#include <iostream>

int main() {
  auto sp = std::make_shared<int>(42);
  std::vector<std::thread> threads;

  for (int i = 0; i < 8; ++i) {
    threads.emplace_back([sp] {
      for (int j = 0; j < 100000; ++j) {
        if (!sp || *sp != 42) {
          std::abort();
        }
      }
    });
  }

  for (auto& t : threads) {
    t.join();
  }
}
```

这里每个线程拿到的是自己的副本，虽然都共享同一控制块，但并没有并发改写同一个句柄对象。

### 场景 2：不同 `shared_ptr` 句柄并发拷贝/析构

```cpp
#include <memory>
#include <thread>
#include <vector>

struct BigObj {
  int data[256]{};
};

int main() {
  auto base = std::make_shared<BigObj>();
  std::vector<std::thread> threads;

  for (int i = 0; i < 8; ++i) {
    threads.emplace_back([base] {
      for (int j = 0; j < 100000; ++j) {
        std::shared_ptr<BigObj> local = base;
      }
    });
  }

  for (auto& t : threads) {
    t.join();
  }
}
```

这里会频繁增加和减少共享计数，但只要标准库实现正确，不应因为控制块竞争而崩溃或误释放。

### 场景 3：同一个 `shared_ptr` 变量并发写

```cpp
#include <memory>
#include <thread>

int main() {
  std::shared_ptr<int> sp = std::make_shared<int>(1);

  std::thread t1([&] {
    for (int i = 0; i < 100000; ++i) {
      sp = std::make_shared<int>(i);
    }
  });

  std::thread t2([&] {
    for (int i = 0; i < 100000; ++i) {
      sp.reset();
    }
  });

  t1.join();
  t2.join();
}
```

这段代码应视为数据竞争，TSan 理论上应报告 race。

如果在支持 ThreadSanitizer 的 Clang/GCC 环境中，可以这样编译：

```bash

```

### 预期观察

1. 场景 1：通常不报 race
2. 场景 2：通常不报控制块 race
3. 场景 3：应报对同一个 `shared_ptr` 变量对象并发写的 race

## 很容易混淆的第四个问题：对象本身安全吗？

例如：

```cpp
auto sp = std::make_shared<std::vector<int>>();
```

就算 `shared_ptr` 的控制块计数是线程安全的，也不意味着多个线程可以无锁同时对 `*sp` 做 `push_back()`。

因为：

- `shared_ptr` 只负责对象生命周期管理
- 它不负责对象内部状态同步

所以更准确的表达应该是：

> `shared_ptr` 的控制块引用计数是线程安全的；被管理对象是否线程安全，与 `shared_ptr` 本身无关。

---

## 今天最容易误解的点

### 1. “引用计数线程安全”不等于“shared_ptr 整体线程安全”

这是最常见的错误总结。

### 2. “同一个对象”和“同一个控制块”不是一回事

两个不同的 `shared_ptr` 句柄可以共享同一控制块，但它们本身仍然是两个不同变量对象。

### 3. “对象被多个线程共享”不等于“对象内部状态线程安全”

生命周期管理和业务状态同步是两套问题。

---

## 今日总结（完成后填写）

1. `shared_ptr` 线程安全真正安全的是控制块引用计数的增减，而不是所有针对智能指针对象本身的并发操作。
2. 多线程并发操作不同 `shared_ptr` 句柄但共享同一控制块，通常是安全的；并发修改同一个 `shared_ptr` 变量则不是。
3. `shared_ptr` 不会自动让被管理对象变成线程安全，对象内部状态仍需要锁或其他同步机制保护。
4. 用 TSan 最适合验证的，不是“shared_ptr 会不会加减计数”，而是“我有没有并发写同一个句柄对象”。
