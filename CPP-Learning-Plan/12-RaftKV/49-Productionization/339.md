## 编号 339 — ReadIndex 线性一致读：不写日志也能保证读到最新已提交值

**掌握标准：能说清「为什么直接读 Leader 状态机会读到陈旧值」，并复述 ReadIndex 的三步
（记 readIndex → 心跳确认仍是 Leader → 等 apply 追上）以及为什么确认必须来自「不同节点」的多数派。**

### 问题：直接读 Leader 也可能陈旧

朴素做法「读请求直接返回 Leader 状态机的值」是**不线性一致**的。因为一个已经被网络分区、丢掉领导权的旧 Leader，自己并不知道，仍会拿着过时的状态机回答——此时集群另一侧早已选出新 Leader 并提交了更新的写。读到旧 Leader 的值就违反了线性一致。

把读也走一遍日志复制能解决，但每个读都要一轮复制 + 落盘，太贵。**ReadIndex** 是标准优化：读不写日志，只做一次「我还是不是 Leader」的确认。

### 三步协议

```
1. readIndex = commitIndex                     // 快照当前提交位置
2. 发一轮心跳(AppendEntries)，收到「不同节点」的多数派确认后 → 确认自己此刻仍是 Leader
3. 等 lastApplied >= readIndex → 读状态机返回
```

- **第 1 步** 锁定一个提交位置：任何在此之前提交的写都必须被这次读看到。
- **第 2 步** 是关键——一次成功的心跳多数派证明「此刻没有更高任期的 Leader 存在」（否则那些节点会用更高 term 拒绝心跳）。这就排除了「我是被架空的旧 Leader」的情况。
- **第 3 步** 保证本地状态机确实已经 apply 到了 readIndex，才不会读到「已提交但还没 apply」的空洞。

### 确认必须来自「不同节点」的多数派

实现里最容易踩的坑：用一个整数 `readAcks++` 累计确认数。这会把**同一个 follower 在多轮心跳里的重复回复**也算进去——于是一个 2 节点少数派 Leader，靠反复收到那唯一 1 个 follower 的回复，也能慢慢「凑」到多数派计数，错误地判定自己仍是 Leader。

正确做法是按节点去重：

```cpp
std::vector<char> readAckedBy;   // 大小 = n_，每个 peer 一格
// 收到匹配 readId 的回复：
readAckedBy[from] = 1;
int acks = 0; for (char c : readAckedBy) if (c) ++acks;
if (acks >= majority()) readConfirmed = true;   // 必须是不同节点凑齐多数
```

一个被分区进 2 节点少数派的旧 Leader，永远凑不齐**不同节点**的多数派确认，于是 `linearizableGet` 超时返回 `nullopt`（读不可用）——这正是线性一致要的：宁可不可用，也不返回陈旧值。

### 验证

- `ReadIndexReturnsCommittedValue`（seed 1–10）：写入并提交若干键后，`linearizableGet` 在 Leader 上返回最新已提交值，且跨 Leader 更替不返回旧值。
- `StaleLeaderCannotServeLinearizableRead`（seed 1–10）：把在任 Leader 分区进 2 节点少数派，另一侧选出新 Leader 并写入；对旧 Leader 调 `linearizableGet` 必须返回 `nullopt`（拿不到不同节点的多数派确认），绝不返回它本地陈旧的 `v0`。
