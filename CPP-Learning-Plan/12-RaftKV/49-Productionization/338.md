## 编号 338 — 快照 + 日志压缩 + InstallSnapshot：snapshot-aware 索引与落后 follower 追赶

**掌握标准：能推导 snapshot 之后所有日志索引的偏移换算（firstIndex/lastLogIndex/entryAt/termAt），
并说清 Leader 何时该发 InstallSnapshot 而不是 AppendEntries、follower 收到后如何决定「保留后缀还是清空日志」。**

### 为什么需要快照

日志会无限增长。没有压缩，`log` 和状态机重放都会越来越慢、越来越占空间。快照把「到某个索引为止的状态机」序列化成一个 blob，然后**丢弃该索引及以前的所有日志条目**。被丢弃的前缀由 `(lastIncludedIndex, lastIncludedTerm)` 这对元信息代表。

### snapshot-aware 索引：核心是一次偏移换算

日志压缩后，`log[0]` 不再是逻辑索引 0，而是 `lastIncludedIndex + 1`。所有访问都要过这层换算，错一个就是越界或读错条目：

```cpp
int firstIndex()   const { return lastIncludedIndex + 1; }              // 内存 log 的第一条逻辑索引
int lastLogIndex() const { return lastIncludedIndex + (int)log.size(); }
bool hasEntry(int i) const { return i >= firstIndex() && i <= lastLogIndex(); }
const LogEntry& entryAt(int i) const { return log[i - firstIndex()]; }   // 逻辑索引 → 数组下标
int termAt(int i) const {
    if (i == lastIncludedIndex) return lastIncludedTerm;   // 快照边界：条目已丢，term 从元信息取
    if (hasEntry(i))            return entryAt(i).term;
    return 0;                                              // 边界外
}
```

关键点：`termAt(lastIncludedIndex)` 必须返回 `lastIncludedTerm`——AppendEntries 的一致性检查会问「你 prevLogIndex 处的 term 是多少」，而那个位置的条目可能正好落在快照边界上、已经被丢弃，只能从元信息回答。

### 何时快照：越过阈值就压缩前缀

`Config.snapshotThreshold > 0` 时，节点 apply 后若 `lastApplied - lastIncludedIndex >= threshold`，就 `maybeSnapshot()`：序列化状态机 → 记 `lastIncludedIndex/Term = 已 apply 的位置` → 丢弃 `log` 中该索引及以前的条目 → `Storage::saveSnapshot(...)`。默认阈值 0 = 关闭压缩，保证 5 个既有 chaos 测试行为不变。

### 何时发 InstallSnapshot 而不是 AppendEntries

Leader 给某 follower 补日志靠 `nextIndex[peer]`。但如果 Leader 已经把 `nextIndex[peer]` 需要的那条**压缩掉了**（`nextIndex[peer] <= lastIncludedIndex`），它手里根本没有那条日志可发——只能整包快照送过去：

```cpp
if (nextIndex[peer] <= lastIncludedIndex)
    sendInstallSnapshot(peer);   // 要的日志已被压缩，改发快照
else
    sendAppendEntries(peer);     // 常规增量复制
```

### Follower 收到 InstallSnapshot：保留一致后缀 or 清空

follower 装快照时不能盲目清空自己的日志——它可能已经有比快照更新的条目。规则：

- 若本地在 `lastIncludedIndex` 处存在且 term 匹配 `lastIncludedTerm`，说明本地日志与快照一致，**保留该索引之后的后缀**，只丢弃被快照覆盖的前缀；
- 否则本地日志与快照冲突或落后太多，**整个清空** log，状态完全以快照为准。

两种情况都：用快照 blob `deserialize` 重置状态机、更新 `lastIncludedIndex/Term`、`commitIndex/lastApplied` 至少推进到 `lastIncludedIndex`、`Storage::saveSnapshot(...)` 落盘。

### 验证

- `InstallSnapshotCatchesUpLaggingFollower`（seed 1–10，`snapshotThreshold=5`）：一个 follower 长期掉线，Leader 侧日志越过阈值触发压缩；follower 重新上线后 `nextIndex` 落在已压缩区间，Leader 发 InstallSnapshot，follower 追平且状态机与 Leader 一致，全程无安全不变量违反、日志长度有界。
