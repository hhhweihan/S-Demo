## 编号 341 — 生产化测试范式：确定性仿真 + 每步不变量校验，成员变更为何推迟

**掌握标准：能说清这套 Raft 仿真「凭什么可信」——确定性离散事件 + 种子化 RNG + 每步安全不变量校验，
以及为什么本轮把成员变更（joint consensus）明确划在范围外。**

### 为什么用确定性离散事件仿真

真实分布式系统的 bug 几乎都来自时序——丢包、乱序、重复、分区、崩溃的**特定交织**。多线程真网络下这些交织不可复现，测出来的失败难以调试。这套仿真反过来：

- **单线程 + 种子化 RNG**：给定 seed，整场运行完全确定、可逐字节复现。发现的失败换个 seed 也能稳定重跑。
- **虚拟时间网络**：消息在一条可编程「线」上传递，可注入丢弃 / 延迟 / 重复 / 乱序 / 分区。不依赖真实时钟或真实 socket。
- **逐节点真 RPC handler**：每个节点跑的是真正的 RequestVote / AppendEntries / InstallSnapshot 处理逻辑（不是上帝视角同步复制），所以它能表现真 Raft 必须存活的失败模式——这正是 `mini_raft_kv.h` 那个上帝视角基线做不到、因而被降级的原因。

多 seed（1–10）循环跑同一场景，就是在低成本地采样大量不同的时序交织。

### 每步安全不变量校验

仿真每推进一个事件，就检查 Raft 的核心安全性质是否仍然成立——一旦违反立刻在那一步失败，把问题钉死在最小复现上：

- **选举安全**：任一 term 至多一个 Leader。
- **日志匹配**：若两节点的日志在某 `(index, term)` 相同，则其之前所有条目都相同。
- **状态机安全**：所有节点在同一 index 上 apply 的是同一条目（已 apply 的历史绝不分叉）。
- **提交单调 / commitIndex 不超过本地 log**。

这些不变量把「测试恰好没撞上 bug」的运气成分降到最低：不是只断言最终结果，而是断言**每一步都合法**。

### crash/restart 的 RNG 消费必须稳定

改造成真磁盘重载后仍要保持种子稳定：`crash()` 不消费 RNG（纯丢弃活对象），`restart()` 只在 `resetElectionTimer` 处消费——保持既有 seeded 测试的时序不漂移。这是「重构不回归」的一个隐形约束。

### 成员变更（joint consensus）为何推迟

动态增删节点（single-server change 或 joint consensus）是 Raft 里独立且复杂的一大块：要处理配置条目本身走日志复制、新旧配置多数派重叠、变更期间的选举与提交规则。它与本轮四个持久化 / 读一致性 / 防扰动主题正交，强行塞进来会显著拉长且难以在本机充分验证。因此**明确划在本轮范围外**，作为后续独立旗舰。当前实现假定集群成员固定。
