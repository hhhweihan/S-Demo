## 编号 345 — 单节点真实状态机：连接去重、ReadIndex 延迟响应

**掌握标准：能说清"低 id 拨高 id"这条连接去重约定为什么足够、为什么每条帧自带 `from`
之后拨号方向不影响路由，以及真实网络下 ReadIndex 为什么必须变成"延迟响应"而不能像仿真版
那样同步返回。**

### 连接去重：低 id 拨高 id

一个 N 节点集群里，任意两个节点之间只需要**一条** TCP 连接就够承载双向的 RPC 流量
（帧里的 `type` 已经区分了是 RequestVote 还是 AppendEntries，是 Args 还是 Reply）。但如果
不做任何约定，两个节点会同时互相 `connect()` 对方，导致同一对节点之间建出两条冗余连接，
需要额外逻辑去检测和关闭多余的一条。这里用最简单的静态规则解决：**id 较小的节点主动拨号
id 较大的节点**；id 较大的节点只监听、accept，不主动向 id 较小的节点发起连接。三个节点
的集群里，节点 0 拨节点 1 和节点 2，节点 1 拨节点 2，节点 2 只 accept——每一对节点之间
恰好一条连接，且这个决定在集群配置给定时就是静态的，不需要运行时协商。

### 为什么拨号方向不影响回复路由

关键前提是 [[343|编号 343]] 里"每条帧自带 `from` 字段"。`RaftServer` 维护一个
`peerIdToFd_: peer id -> fd` 的映射，每收到一条帧就用帧里的 `from` 刷新这个映射（不管这条
连接最初是本节点拨出去的还是被拨进来的）。`SendTo(peerId, ...)` 只是查这个映射、往对应 fd
写数据——回复一条 RequestVote 该发到哪个 fd，完全由"最近一次收到这个 peer 的帧是从哪条 fd
来的"决定，不需要知道、也不关心当初是谁主动发起了这条连接。这让"谁拨谁"这个问题被完全
限制在连接建立阶段，不会渗透进后续任何 RPC 处理逻辑里。

### RaftServer 的骨架

`net/raft_server.h` 按用途拆成几组：连接生命周期（`ConnectToPeer`/`OnConnectComplete`/
`EstablishConn`/`ScheduleReconnect`/`CloseConn`，处理 accept、断线重连+退避）、管理协议
（`OnAdminReadable`/`HandleAdminLine` 处理 `PUT`/`GET`/`STATUS`/`NOT_LEADER`）、选举与复制
（`StartPreVote`/`StartElection`/`BecomeLeader`/`BroadcastAppendEntries`/`SendInstallSnapshot`
及六种 RPC 的 `Handle(...)` 重载）、日志索引换算（`FirstIndex`/`LastLogIndex`/`HasEntry`/
`EntryAt`/`TermAt`，snapshot-aware，逻辑与 [[338|编号 338]] 一致）。这些状态转移逻辑是针对
"单节点、真实异步、真实时钟"重新写的一份，不是 `raft_sim.h::Cluster` 的改造，理由见
[[342|编号 342]]。

一个和仿真版不同的真实性来源：election timeout 的随机化用 `std::random_device`（真实熵源）
而不是仿真版里可复现的种子化 RNG——真实节点的随机化必须在每次进程重启、每个进程之间真的
不一样，否则多个节点的定时器可能真的对齐，制造不必要的选举冲突。

### ReadIndex 为什么必须是延迟响应

仿真版的 `linearizableGet()` 能同步返回，因为它可以"把虚拟时钟往前拨"，在一次函数调用里
走完"记 readIndex → 广播确认 → 等多数派确认 → 等 apply 追上 → 返回值"整个流程——这是仿真器
的特权，真实世界的时间不能被同步拨快。真实网络版收到一条 `GET` 请求时，连接的"确认领导权"
心跳往返需要真实的网络 RTT，不能阻塞事件循环等它完成（会卡住其他所有连接的处理）。

于是 `RaftServer` 把每个尚未满足条件的读请求存进 `pendingReads_`（记住 `adminFd`、要读的
`key`、这次读需要等到的 `readIndex`、这次读用来去重确认的 `readId`），函数立即返回，事件循环
继续处理别的事。真正的回复推迟到两个时机之一触发 `TryServePendingReads()`：每次
`ApplyCommitted()`（状态机往前推进，可能追上了某个 pending read 需要的 `readIndex`）之后，
或者每次收到一条确认了本轮读的 `AppendEntriesReply`（`readAckedBy_` 按**不同节点**计数满足
多数派，与 [[339|编号 339]] 的去重要求一致）之后。此外还有一道与 [[339|编号 339]] 一致的闸门：
只有本任期的选举 no-op 已提交（`commitIndex_ >= firstIndexOfCurrentTerm_`）才服务读——
刚当选或刚重启的 Leader 在此之前状态机尚未覆盖此前所有已提交条目，不能应答。这个"提交请求 → 记住上下文 → 由后续某个
异步事件触发响应"的模式，是所有真实异步服务器处理"逻辑上同步、物理上要等别的东西"的请求
时的标准写法，仿真版的同步调用完全掩盖了这一层复杂度。

### 验证

3 个 `RaftServer` 实例在同一进程内、各自跑在独立线程上的烟雾测试：等选举收敛后用 `STATUS`
找到 leader，`PUT foo bar` 确认本地立即 append 成功（不等 commit，和 `raft_sim::Cluster::submit()`
的约定一致），`GET foo` 走完整 ReadIndex 流程拿到 `VALUE bar`，对 follower 发 `PUT` 确认收到
`NOT_LEADER <id>`。跑了 4 次，无 flaky，不同轮次选出的 leader 不同（node0、node1 两次）——
证明真实熵源确实在起作用，不是巧合的固定结果。
