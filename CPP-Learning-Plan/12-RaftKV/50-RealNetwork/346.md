## 编号 346 — 真进程 kill -9 验证了什么，仿真版验证不了什么

**掌握标准：能说清 `SIGKILL` 真进程测试比仿真版的 `crash()` 方法调用多验证了哪几层东西，
并解释为什么这类测试要用 CTest `LABELS` 排除在默认 CI 之外，而不是干脆不写。**

### `crash()` 方法调用 vs `kill -9` 真进程

`raft_sim.h::Cluster::crash(id)` 在 [[337|编号 337]] 的实现里就是 `node = Node(id, storage)`——
构造一个新对象换掉旧的，`storage` 指向的 blob（`MemStorage` 场景下就是内存里的一份数据）
安然无恙。这验证的是"如果易失状态确实被丢弃、持久状态确实只能从 `Storage::load()` 读回来，
状态机重建逻辑对不对"，这一层协议正确性完全可以在同一个进程里用一次方法调用验证。

它验证不了的：真实操作系统把一个进程杀死（`SIGKILL`）时到底发生了什么。`SIGKILL` 不能被
捕获、不能被忽略、不会走任何用户态清理路径——没有析构函数运行、没有 `atexit` 回调、没有
"来得及" `flush` 的缓冲区，唯一在崩溃后幸存的东西是已经真正 `fsync` 到磁盘的字节。TCP 连接
对端会立刻观察到连接被内核异常关闭（不是四次挥手的优雅关闭），进程真正从进程表里消失需要
父进程 `waitpid()` 回收（否则留下僵尸进程）。这些都是"进程真的死了"这件事在操作系统层面
展开的全部后果，`Node` 对象的重新构造完全模拟不出来。

`tests/raft_net_integration_test.cpp` 因此用真正的 `fork()`+`execl()` 启动三个真实
`raft_kv_net_demo` 子进程，走真实 TCP 提交一条写请求并确认已提交可读，然后对**当前 leader
的真实 PID** 调用 `kill(pid, SIGKILL)`，用 `waitpid()` + `WIFSIGNALED`/`WTERMSIG(status) ==
SIGKILL` 确认这确实是一次真正的信号杀死（不是进程自己正常退出）。之后轮询剩余两个节点的
`STATUS`，确认它们在真实时间尺度内（一个 election timeout 量级）选出了新 leader、term 真的
递增了；再重启被杀的节点、指向**同一个** `FileStorage` 存储目录，确认它的 `term`/`applied`
追上集群——这一步验证的是恢复完全来自磁盘上真正 `fsync` 过的字节，而不是任何还残留在内存
里的状态（因为进程都不在了，没有残留状态可言）。

### 为什么要打 CTest `integration` label 排除出默认 CI

这类测试有两个和仓库里其余测试不一样的特征：真实 wall-clock（真实 election timeout 量级的
睡眠/轮询，而不是仿真器里瞬间推进的虚拟时钟）和真实进程调度（`fork`/`exec`/信号/`waitpid`
的时序理论上比纯内存的确定性仿真更容易受机器负载影响而偶发抖动）。这两点意味着它在 CI 的
矩阵作业（ASan/UBSan/TSan 三个 sanitizer job 各跑一遍）里会显著拖慢反馈速度，且理论上的
抖动概率非零——不代表它没有价值，只代表它不该挡在"每次 push 都要等的默认路径"上。

`CMakeLists.txt` 里用 `set_tests_properties(raft_kv_net_integration PROPERTIES LABELS
integration)` 打标签，`.github/workflows/ci.yml` 的三个 `ctest ... -j2` 调用都加上
`-LE integration`（排除该 label）。这和 `leveldb_mini` 模块现有的 fork/kill-9 崩溃测试
"走普通 Debug、不进 sanitizer 矩阵"是同一个处理思路——手动、按需触发，而不是让它成为
CI 里一个偶尔变红却和这次改动毫无关系的噪音源。手动单独运行：

```bash
cmake --build build --target raft_kv_net_integration_test -j
ctest --test-dir build -L integration --output-on-failure
```

### 验证

用 Python 脚本剥掉 GTest 宏、换成手写 `ASSERT_*` 宏（支持 `<<` 消息链式调用的
`NullStream` 兜底写法）编译出的独立可执行文件，跑了 4 次：全部通过，无 flaky，
每一次都真实走完"选举 → 写入 → kill -9 → 重选 → 重启 → 恢复"全链路。
