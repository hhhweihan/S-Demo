## 为什么需要 hazard pointer

前面三个教学栈（`LockFreeStack` / `ReclaimingLockFreeStack` / `TaggedPointerStack`）都卡在同一处：pop 摘下一个节点后**不敢立即 `delete`**——别的线程可能正持有这个指针准备解引用，或正拿它做 CAS 比较。它们的妥协是把节点塞进 `retired_` 列表，拖到析构才统一释放。代价是运行期 `retired_` **无界增长**，长跑大量 pop 会持续吃内存。

Day 48 读书笔记里就点出了这个分裂：CAS 只保证"更新 head_ 的动作原子"，但**回收时机**是另一套问题。hazard pointer 就是回收这一侧的生产级答案。

## 三段协议

**核心思想**：读者在解引用一个指针前，先把它"公开登记"到一个全局可见的槽位（hazard slot）；回收方 `delete` 前先扫描所有槽位，只回收"当前无人登记"的节点，其余留到下次扫描。于是 retired 列表长度被扫描阈值 R 卡住——**有界回收**。

1. **publish + load-verify（`protect`）**：把 `head_` 的当前值写进本线程槽位，然后**重读 `head_` 校验它没变**。若变了（有人先摘走），拿新值重登记再校验。返回时该指针已被本槽位"护住"，解引用安全。

   ```cpp
   value = src.load(seq_cst);
   while (true) {
       slot->pointer.store(value, seq_cst);   // 发布
       T* again = src.load(seq_cst);           // 重读校验
       if (again == value) return value;       // 未变 → 已护住
       value = again;                          // 变了 → 重登记
   }
   ```

2. **retire**：pop 用完节点后，不 `delete`，挂进全局 retire 链；链长越过阈值 `R = 2*H`（H=最大线程数）就触发 `scan()`。

3. **scan**：取走整条 retire 链，快照所有 hazard 槽；对每个 retired 节点，若它出现在快照里就重新挂回链（下次再判），否则真正 `delete`。阈值 R=2H 保证每次扫描至少能回收一半，均摊 O(1)、retired 长度恒有界。

## 这次真正学到的东西：scan 的顺序 + seq_cst 全序

初版在 macOS(arm64) 上跑 `HazardStack` 的并发压测，TSan 报出 use-after-free：一个被 protect 保护的节点被回收、又被另一个 push 复用。根因**不是**协议写错，而是**内存序不够强**外加 **scan 里两步的顺序错了**。

**正确的 scan 顺序：必须先取走 retire 链，再快照 hazard 槽——顺序不可颠倒。**

seq_cst 全序论证（`<ₛ` 表示 seq_cst 全序中的先后）：

```
reader 在 protect 里：发布 hp  <ₛ  校验 head==N（读到 N 可达 ⇒ 此读 <ₛ 摘除 N）
reclaimer：摘除 N  <ₛ  retire 入链  <ₛ  scan 取链（读到了 N）  <ₛ  scan 快照槽位
```

把两条链接起来：`hp 发布 <ₛ 摘除 <ₛ 取链 <ₛ 快照`。既然 hp 发布严格早于快照，快照就**必然看见** reader 的 hp，绝不会误删仍被引用的节点。

反过来，若 scan **先快照再取链**，快照可能发生在 reader 发布 hp 之前而漏看它 → 误判"无人保护" → 回收 → use-after-free。这就是初版的 bug。

**代价**：这条推理要求参与的每个操作都在**同一个 seq_cst 全序**里——`protect` 的发布与校验、`HazardStack` 摘除节点的 CAS、retire 入链的 CAS、scan 的取链与快照，**全部用 `memory_order_seq_cst`**。任何一处降级成 acquire/acq_rel，全序就断了，弱序机上二者可能互相看不见。x86 因为本身近似全序不会暴露，ARM 会——这正是"本机能编能过 ≠ 到处正确"的又一例。
