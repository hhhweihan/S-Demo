## 为什么单全局队列不够

Day 36–42 的线程池是一个 `BlockingQueue<Task>` + N 个 worker：所有 worker 抢同一把锁、同一个队列头。任务少时没问题，但**任务本身会派生子任务**（如并行分治）时，这个设计有两个痛点：

1. 所有提交都挤在一个锁上，worker 数越多争用越凶。
2. 刚提交的子任务和它的父任务在缓存上是热的，却被丢进全局队列尾巴，可能被另一个 CPU 捞走，缓存全冷。

work-stealing 的思路：**每个 worker 一个私有 deque**，自己提交的子任务进自己的 deque（LIFO，缓存最热），自己干；干完了再去偷别人的（FIFO，从最老一端，尽量不碰对方热点）。全局队列退化为两个角色：外部线程提交的入口、以及 worker 无活可干时的**阻塞停泊点**。

## Chase-Lev deque 的两端分工

- **owner**（deque 的属主 worker）在 **bottom** 端 push/pop，**LIFO**。常路完全无 CAS——只有当 deque 只剩最后一个元素、可能与 thief 撞车时，才需要一次 CAS 裁决归属。
- **thief**（其它 worker）在 **top** 端 steal，**FIFO**，一次 CAS 认领。

owner 动 bottom、thief 动 top，两端各据一方，常态**不争用同一个原子量**。这是它比单锁队列吞吐高的根本原因。

正确性最微妙处：deque 只剩一个元素时，owner 的 pop 和某 thief 的 steal 会争抢同一个。解法是 pop 里放一个 `seq_cst` 全栅，与 steal 里 top 的 `seq_cst` CAS 排成同一全序，保证这最后一个元素**要么 owner 拿要么某个 thief 拿，绝不两取也不漏取**。

## 这次踩到的坑：槽位投机读是数据竞争

初版 deque 直接把任务 `T` 存进环形数组。TSan 立刻报 `push` 写槽位与 `steal` 读同一槽位的数据竞争。

根因：**steal 在 CAS 认领 top 之前就投机读取了槽位内容**。哪怕算法上"读了也可能因 CAS 失败而作废"，这个读与 owner 的 push 写在 C++ 内存模型下就是数据竞争——UB，TSan 如实报告（x86 上可能"看起来没事"，ARM 上会真出问题）。

Lê et al. 2013《Correct and Efficient Work-Stealing for Weak Memory Models》给的修法是让槽位访问本身原子化。但线程池的任务是 `std::function`，非平凡类型，塞不进 `std::atomic<T>`。于是改存**持有所有权的指针** `std::atomic<T*>`：

- 投机读的是**指针**（原子加载，无竞态），赢下 CAS 前不解引用、不删除。
- 真正 `std::move(*node)` + `delete node` 只在赢得 CAS 之后。
- 析构时只删 `[top, bottom)` 区间内未被取走的节点；区间外是已取走的悬垂指针，不能删。

代价是每个任务一次 `new/delete`——换来对任意 `T` 的无数据竞争正确性。这是通用 Chase-Lev 的教科书做法。

## worker 取活顺序与关闭语义保留

worker 循环：**① 掏自己 deque(LIFO) → ② 随机 victim steal(FIFO) → ③ 阻塞在全局队列上**（顺带接收关闭哨兵）。

关键：走到 ③ 时本地 deque 必然是空的（这才轮到阻塞），所以 worker 领到退出哨兵而退出时，**绝不会遗留未执行的本地任务**。既有的哨兵关闭、退出令牌 CAS、`pending_latch_`、`completion_cv_` 语义因此**原样保留**——work-stealing 只是插在取活的前两步，没动关闭骨架。

deque 用固定 `kMaxWorkers` 槽位池 + 认领标志实现，deque 对象活到线程池析构，thief 读到的槽位内存永远有效，**无需 hazard pointer 那套回收**（对照 Day 50）。

## 热点计数器的 false sharing

`active_count_ / pending_tasks_ / completed_tasks_` 三个计数器被每个 worker 每完成一个任务就更新一次。若它们挤在同一条 cache line 上，一个核更新 pending 会让另一个核缓存的 completed 整行失效（false sharing），高频下明显拖慢。给三者各套 `alignas(kCacheLine)`（本地 `constexpr 64`，不用 `std::hardware_destructive_interference_size`）分到独立 cache line 即可。更新频率低的 target/exit_tokens/submitted/rejected 不单独隔离。
