## 今天学到了什么

### 1. relaxed 只保证原子性，不保证跨线程可见顺序

`memory_order_relaxed` 只承诺单次读写不会被撕裂，不会自动建立线程 A 与线程 B 之间的“先发生”关系。

这意味着下面这类逻辑在理论上是允许失败的：

```cpp
std::atomic<int> x{0}, y{0};

// A
x.store(1, std::memory_order_relaxed);
y.store(1, std::memory_order_relaxed);

// B
while (!y.load(std::memory_order_relaxed)) {}
assert(x.load(std::memory_order_relaxed) == 1);
```

线程 B 看见 `y == 1`，并不等价于也必须看见 `x == 1`。原子变量没数据竞争，但同步语义仍然不足。

### 2. release/acquire 的价值是把“发布”和“观察到发布”绑定起来

如果线程 A 在写完共享数据后，对“门铃变量”做 `release store`，线程 B 用 `acquire load` 读到这个门铃，就会得到一条可靠的同步边：

```cpp
// A
x.store(1, std::memory_order_relaxed);
y.store(1, std::memory_order_release);

// B
while (!y.load(std::memory_order_acquire)) {}
assert(x.load(std::memory_order_relaxed) == 1);
```

关键点不在于 `x` 用了 relaxed，而在于 `y` 这对 release/acquire 建立了“先发布，再观察”的关系，进而把之前对 `x` 的写入也一并发布出去。

### 3. TSan 不会替你发现 memory_order 级别的逻辑错误

今天最重要的纠偏是这件事：

- TSan 主要抓“数据竞争”
- 原子变量上的读写本身通常不会被判定为数据竞争
- 但“没有同步语义导致读到旧值”依然可能是程序逻辑错误

也就是说，实验 1 即使语义上有风险，TSan 也未必报错，因为它不是未同步的普通内存访问。

### 4. 6 种 memory_order 先抓住一句话定义，再谈细节

今天的目标不是死背标准措辞，而是先把每个 order 的使用边界记清楚：

- relaxed：只保原子，不保顺序
- consume：依赖传播，实践里几乎等同 acquire 看待
- acquire：后续读写不能越过这次读
- release：之前读写不能越过这次写
- acq_rel：读改写同时承担 acquire 和 release
- seq_cst：在 acquire/release 之上再提供全局单一总顺序

## 今日结论

1. 是否“原子”与是否“同步”是两件不同的事。
2. release/acquire 是无锁结构里最常见、性价比最高的同步组合。
3. 看到 TSan 无报错，不能直接推出 memory_order 设计正确。
