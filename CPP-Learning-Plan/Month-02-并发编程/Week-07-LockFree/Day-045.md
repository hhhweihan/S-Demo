## 设计骨架

今天把 SPSC 队列的关键前提彻底想清楚了：

- `head_` 只由消费者推进
- `tail_` 只由生产者推进
- 双方都可以读对方索引，但不会同时写同一个索引

这就是它能比通用无锁队列简单很多的根本原因。

```cpp
template<typename T, std::size_t N>
class SPSCQueue {
public:
    bool push(const T& value) {
        auto tail = tail_.load(std::memory_order_relaxed);
        auto next = increment(tail);
        if (next == head_.load(std::memory_order_acquire)) {
            return false;
        }

        buffer_[tail] = value;
        tail_.store(next, std::memory_order_release);
        return true;
    }

    bool pop(T& out) {
        auto head = head_.load(std::memory_order_relaxed);
        if (head == tail_.load(std::memory_order_acquire)) {
            return false;
        }

        out = buffer_[head];
        head_.store(increment(head), std::memory_order_release);
        return true;
    }

private:
    std::size_t increment(std::size_t index) const {
        return (index + 1) % N;
    }

    T buffer_[N];
    std::atomic<std::size_t> head_{0};
    std::atomic<std::size_t> tail_{0};
};
```

## 为什么这套 memory_order 足够

### 1. 本线程自己维护的游标可以 relaxed 读

生产者对 `tail_` 有唯一写权，消费者对 `head_` 有唯一写权，所以各自读取自己负责的索引时，用 relaxed 就够了。

### 2. 读对方索引要 acquire

生产者要判断“队列满不满”，必须读取消费者发布出来的 `head_`；消费者要判断“队列空不空”，必须读取生产者发布出来的 `tail_`。

这里使用 acquire，目的是在看到索引更新时，也一并看到对方在线程内先发生的数据写入。

### 3. 发布新索引要 release

生产者先写 `buffer_[tail]`，再 `release store` 新的 `tail_`；消费者先读 `buffer_[head]`，再 `release store` 新的 `head_`。这样另一侧只要 acquire 读到索引变化，就能安全观察到对应槽位的数据状态。

## 测试思路

如果后续在代码目录里落实现，测试我会用下面这条主线：

1. 生产者顺序 push `0..999999`
2. 消费者顺序 pop，并累加计数
3. 校验：
   - 总消费数等于 1000000
   - 序列严格递增，无重复、无丢失
4. 用 TSan 检查是否存在非原子共享访问

今天的关键不是把代码写长，而是先把“为什么这套顺序正确”说清楚。

## 今日结论

1. SPSC 队列之所以容易做对，是因为每个共享索引都有唯一写者。
2. release/acquire 负责发布槽位状态，relaxed 负责降低本地读写成本。
3. 只要保持单生产者单消费者前提，SPSC 的正确性明显好证明。
