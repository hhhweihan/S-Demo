# Day 33（Fri）— 队列性能测试

## 预计时间

1 小时

## 今天要解决什么问题

前面三天你已经做了两类队列：

- `BlockingQueue<T>`：无界、有锁、空时等待
- `BoundedQueue<T>`：有界、有锁、支持背压

接下来要做的不是继续加接口，而是回答一个更工程化的问题：

- 这些同步语义到底值多少钱

也就是说，今天你要量化：

- 阻塞语义带来了多少额外开销
- 有界队列和无界队列谁更慢，慢在哪里
- 多线程并发是否真的带来了吞吐提升

如果你不做这一步，后面看到“无锁队列更快”时，理解会非常空泛。性能测试的作用就是把这种直觉变成数据。

## 你需要掌握的点

### 1. benchmark 不是“跑一下时间”这么简单

如果你只是随便写个 `main()` 然后打印一次耗时，结论通常没有太大价值。

最低限度要保证：

- 每个方案做相同数量的工作
- 避免把 `cout`、日志等额外开销混进测量区间
- 测量的是队列交换成本，而不是别的杂音

今天先不追求严谨到论文级别，但至少要做到“可复现”和“可解释”。

### 2. 单线程基准为什么仍然重要

很多人看到并发就只测多线程版本，但没有单线程基准，你根本不知道：

- 同步原语本身到底多贵
- 上下文切换和锁竞争到底吃掉了多少预算

`std::queue` 单线程基准的作用不是拿来比较功能，而是回答：

- 在没有锁、没有线程切换、没有条件变量时，纯入队出队有多快

这个数字能给你一个下界参考。

### 3. 为什么 4P4C 可能反而更慢

很多初学者会默认认为：

- 线程更多 = 吞吐更高

但对有锁队列来说，线程变多可能带来：

- 更多锁竞争
- 更多唤醒和调度开销
- 更多 cache line 抖动
- 更频繁的上下文切换

所以 4P4C 有三种可能：

- 比 1P1C 快一些
- 和 1P1C 差不多
- 甚至更慢

这都不奇怪，关键是你能不能解释原因。

### 4. BoundedQueue 的额外成本来自哪里

`BoundedQueue` 比 `BlockingQueue` 多出来的不是很多代码，但多了几类额外成本：

- 每次 `push()` 要检查是否已满
- 满时会出现生产者阻塞和唤醒
- 两个条件变量带来更多同步路径

如果容量设置太小，生产者和消费者会频繁“你等我、我等你”，吞吐可能明显下降。

## 推荐 benchmark 结构

### 基础计时框架

建议统一使用：

```cpp
auto start = std::chrono::steady_clock::now();
// run benchmark
auto end = std::chrono::steady_clock::now();
auto elapsed_ms = std::chrono::duration_cast<std::chrono::milliseconds>(
    end - start).count();
```

不要用系统时间，`steady_clock` 更适合做耗时测量。

### 单线程基准

单线程版本不要引入任何锁：

```cpp
std::queue<int> q;
long long checksum = 0;

for (int i = 0; i < kCount; ++i) {
    q.push(i);
}

for (int i = 0; i < kCount; ++i) {
    checksum += q.front();
    q.pop();
}
```

这里的 `checksum` 很重要，它能防止编译器把你的循环过度优化掉。

### 1P1C 基准

建议用两个线程：

- 生产者 push `0..kCount-1`
- 消费者 pop 并累加

这样最容易和 Day 31 的正确性测试共用逻辑。

### 4P4C 基准

建议仍然用原子发号器：

- 4 个生产者共享 `next_value`
- 4 个消费者共享 `popped_count`
- 最后统一校验总数和总和

这样 workload 一致，便于横向比较。

## 建议输出格式

推荐打印成这种表格风格，后续方便粘贴回周总结：

```text
Case                         Time(ms)   Throughput(ops/s)
std::queue-single-thread     12         83333333
BlockingQueue-1P1C           140        7142857
BoundedQueue-1P1C            155        6451612
BlockingQueue-4P4C           210        4761904
BoundedQueue-4P4C            260        3846153
```

绝对值不重要，关键是：

- 相对差距是否稳定
- 重跑几次是否趋势一致

## 实现步骤

### 第一步：先做正确性校验，再做计时

不要边写边测性能。先确保：

- 总数正确
- 总和正确
- 没有死锁

性能数据建立在正确结果之上，错误程序跑得再快也没有意义。

### 第二步：统一测量规模

建议统一常量：

```cpp
constexpr int kCount = 1'000'000;
```

不要让每个 case 用不同负载，否则结论没有可比性。

### 第三步：把日志和断言移出计时区间

计时区间里只放核心工作：

- push
- pop
- 线程 join

打印、表格格式化、字符串拼接都放到外面。

### 第四步：每个 case 至少跑 3 次

今天不要求你做完整统计学分析，但建议至少观察：

- 是否有明显抖动
- 最慢和最快是否差很多

如果某个 case 每次都差异很大，先别急着下结论，看看是不是测试本身还不稳定。

## 分析时应该关注什么

### 1. 锁竞争

线程越多，对同一把互斥锁的争用越严重。即使临界区很短，也会有排队和调度成本。

### 2. 条件变量唤醒成本

阻塞并不是“免费等待”。线程睡眠和唤醒都要经过调度器，成本远高于单线程下的普通函数调用。

### 3. cache locality

单线程访问 `std::queue` 时，访问模式简单连续。

多线程共享一个队列时，元数据和同步对象会频繁在多个核心之间迁移，cache 命中率会明显变差。

### 4. 有界队列的背压影响

如果容量较小，生产者和消费者会频繁形成“交替等待”，吞吐通常不如无界队列平滑。

但这不是坏事。它说明你真的把压力控制住了。

## 常见坑

### 1. 在 benchmark 里打印每个元素

这会让你测到的主要是 I/O，而不是队列性能。

### 2. 把线程创建成本和队列成本混在一起

今天可以接受把线程创建算在总耗时里，因为你测的是一个完整运行场景。但你要明确：

- 这不是纯粹的“单次 push/pop 开销”
- 它更接近“这个方案在真实运行中的整体成本”

### 3. 只看绝对值，不看趋势

不同机器的数字差很多很正常。真正有价值的是：

- 同一机器上各方案的相对顺序
- 重复运行后的稳定性
