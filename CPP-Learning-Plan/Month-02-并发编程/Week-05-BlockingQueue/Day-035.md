## 本周必须真正掌握的结论

### 1. `condition_variable` 等待必须绑定谓词

这周最重要的一条规则就是：

```cpp
cv.wait(lock, predicate);
```

而不是：

```cpp
cv.wait(lock);
```

原因不是代码风格，而是行为正确性：

- 条件变量可能发生伪唤醒
- 被唤醒不代表条件已经成立
- 共享状态可能在你醒来前又被别的线程改掉

所以本质上你等待的不是“通知”，而是“共享状态满足条件”。

### 2. `if` 不够，语义上要按 `while` 理解

即使你用了谓词版 `wait`，脑子里也要始终按下面这个模型理解：

```cpp
while (!condition) {
    cv.wait(lock);
}
```

这能帮助你避免一个很常见的误区：

- 把 `notify_*()` 当成事件本身

实际上真正决定行为的是共享状态，不是通知动作。

### 3. `notify_one` 和 `notify_all` 的边界

这一周最常见的使用原则可以总结成：

- 单个元素到达，通常 `notify_one()`
- 全局状态改变，通常 `notify_all()`

对应到本周代码就是：

- `push()` 后通常只需要叫醒一个等待消费者
- `shutdown()` 后必须叫醒所有等待线程

因为 `shutdown()` 改变的是系统级退出条件，不是局部数据变化。

### 4. 队列关闭语义必须先于实现细节被定义

这周你应该已经体会到：

- 真正难的不是把元素放进 `std::queue`
- 难的是在“队列空、队列满、队列关闭”三种状态交错时，所有线程如何有序退出

一个成熟的并发组件，必须先定义：

- 谁负责关闭
- 阻塞中的线程如何被唤醒
- 唤醒后如何判断继续工作还是退出

这套协议如果模糊，代码越写越乱。

## 本周最容易出错的点

建议你至少记住下面 3 个：

1. 只盯着队列数据，不把 `shutdown_` 当共享状态处理。
2. `notify_*()` 用对了函数，但用错了时机或唤醒对象。
3. 测试只验证“程序没崩”，却没有验证数量、总和和退出路径。

如果这三点你已经建立清晰意识，本周目标就算真正达成。
