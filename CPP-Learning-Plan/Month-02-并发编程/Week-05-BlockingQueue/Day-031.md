## 今天要解决什么问题

昨天你已经把 `BlockingQueue<T>` 的基本接口写出来了，但“能编译”不等于“并发语义是对的”。

阻塞队列最容易藏 bug 的地方，不在单线程下的 `push/pop`，而在多线程交错时：

- 会不会少消费或多消费
- 多个生产者会不会把编号打乱、重复或者漏掉
- 队列关闭后，消费者能不能正常退出
- 在高并发下，锁和条件变量的配合是否存在竞态

所以今天不扩功能，只做一件事：

- 用一个足够明确的生产者消费者测试，把 `BlockingQueue` 的行为钉死

这一步非常关键。后面的线程池会直接把任务塞进这个队列，如果这里语义模糊，后面所有问题都会放大。

## 你需要掌握的点

### 1. 为什么不要让每个生产者写固定区间

最直接的写法是：

- 线程 1 负责 `[0, 24999]`
- 线程 2 负责 `[25000, 49999]`
- ...

这样当然可以测出一部分问题，但它没法验证“多线程同时争抢生产权”这件事。

更好的测试方式是让所有生产者共享一个原子计数器：

```cpp
std::atomic<int> next_value{0};

while (true) {
  int value = next_value.fetch_add(1, std::memory_order_relaxed);
  if (value >= kTotalCount) {
    break;
  }
  queue.push(value);
}
```

这样更接近真实并发场景：

- 多个生产者同时抢任务编号
- 能直接验证是否有重复编号或漏编号
- 不需要手动拆分区间

### 2. 为什么消费者退出不能靠“猜测什么时候结束”

错误思路通常是：

```cpp
while (popped_count < total_count) {
  auto value = queue.pop();
  ...
}
```

这个写法的问题是：

- `popped_count` 是所有消费者共享的
- 某个线程看到计数还没到，但下一次 `pop()` 时队列可能已经空了
- 如果没有明确关闭机制，它就可能永久阻塞

正确思路是：

- 生产者全部结束后，由主线程调用 `queue.shutdown()`
- 所有阻塞中的 `pop()` 被唤醒
- `pop()` 在“队列已关闭且为空”时抛异常或返回关闭信号
- 消费者据此退出循环

这才是一个完整、可结束的并发协议。

### 3. 为什么要同时校验“数量”和“总和”

只校验总数不够，因为可能出现：

- 有数字重复
- 有数字丢失
- 但碰巧 `pop` 次数还是 100000

只校验总和也不够，因为理论上不同数据组合也可能凑出相同和。

最稳妥的低成本校验是同时验证：

- push 次数
- pop 次数
- 最终总和

如果你愿意再严一点，还可以额外记录一个 `std::vector<std::atomic<int>> seen`，验证每个值只出现一次。但今天先把主校验做稳就够了。

### 4. `memory_order_relaxed` 为什么够用

这里的原子变量只负责“发号”，不承担线程间数据发布语义，因此：

```cpp
next_value.fetch_add(1, std::memory_order_relaxed)
```

就已经足够。

你需要的是：

- 不重复
- 不丢号
- 每次递增是原子的

这些由原子读改写本身保证，不需要额外的 acquire/release 成本。

## 推荐测试结构

下面是一版和 Day 30 的 `BlockingQueue` 语义兼容的测试框架。假设你的 `pop()` 在关闭且为空时会抛异常：

```cpp
#include <atomic>
#include <cstdint>
#include <exception>
#include <thread>
#include <vector>

#include "concurrent/blocking_queue.h"
#include "concurrent/joining_thread.h"

int main() {
  constexpr int kProducerCount = 4;
  constexpr int kConsumerCount = 4;
  constexpr int kTotalCount = 100000;

  BlockingQueue<int> queue;
  std::atomic<int> next_value{0};
  std::atomic<int> pushed_count{0};
  std::atomic<int> popped_count{0};
  std::atomic<long long> sum{0};

  std::vector<JoiningThread> producers;
  std::vector<JoiningThread> consumers;

  for (int i = 0; i < kProducerCount; ++i) {
    producers.emplace_back([&] {
      while (true) {
        int value = next_value.fetch_add(1, std::memory_order_relaxed);
        if (value >= kTotalCount) {
          break;
        }
        queue.push(value);
        pushed_count.fetch_add(1, std::memory_order_relaxed);
      }
    });
  }

  for (int i = 0; i < kConsumerCount; ++i) {
    consumers.emplace_back([&] {
      while (true) {
        try {
          int value = queue.pop();
          sum.fetch_add(value, std::memory_order_relaxed);
          popped_count.fetch_add(1, std::memory_order_relaxed);
        } catch (const std::exception&) {
          break;
        }
      }
    });
  }

  producers.clear();
  queue.shutdown();
  consumers.clear();

  const long long expected_sum =
    1LL * (kTotalCount - 1) * kTotalCount / 2;

  return pushed_count == kTotalCount &&
           popped_count == kTotalCount &&
           sum == expected_sum
         ? 0
         : 1;
}
```

这段代码里最值得你注意的不是“怎么写线程”，而是整个退出顺序：

1. 生产者全部结束
2. 主线程调用 `shutdown()`
3. 消费者从阻塞中醒来并退出
4. 校验结果

退出顺序写错，比队列实现错还常见。

## 实现步骤

### 第一步：先把测试指标定死

不要一上来就开很多线程。先写常量：

```cpp
constexpr int kProducerCount = 4;
constexpr int kConsumerCount = 4;
constexpr int kTotalCount = 100000;
```

这样后面排查问题时，你能快速调整规模，而不是到处改魔法数字。

### 第二步：先写消费者退出协议

很多人会先写生产循环，但真正容易写错的是退出协议。

你应该先明确：

- `queue.shutdown()` 由谁调用
- `pop()` 关闭后如何返回
- 消费者拿到关闭信号后如何退出

先把这三件事说清楚，再写剩余代码。

### 第三步：再把生产逻辑接上

发号器模式是今天的重点：

```cpp
int value = next_value.fetch_add(1, std::memory_order_relaxed);
if (value >= kTotalCount) break;
queue.push(value);
```

你可以把它理解成一个并发版本的 for 循环分发器。

### 第四步：最后补断言和输出

推荐至少打印：

- 实际 push 数
- 实际 pop 数
- 实际总和
- 期望总和

一旦出错，你第一眼就知道是“数量不对”还是“值不对”。

## 建议验证方式

### 验证 1：正常多线程跑通

预期现象：

- 程序稳定退出
- 无死锁
- 计数和总和全部正确

### 验证 2：把 `shutdown()` 注释掉

如果你的消费者是阻塞 `pop()`，那么非常可能出现：

- 部分消费者永久卡住
- 程序无法结束

这一步能帮助你真正理解：

- `shutdown()` 不是“可选优化”
- 它是阻塞队列生命周期协议的一部分

### 验证 3：在支持的编译器下跑 sanitizer

如果你的环境支持，优先开：

- ASan：查越界、悬空引用
- TSan：查数据竞争

注意：不同平台和编译器对 TSan 支持差异很大。今天的重点不是必须把 sanitizer 配置成功，而是有意识地尝试用工具验证并发代码。

## 常见坑

### 1. 用普通 `int` 代替原子计数器

多个生产者同时做：

```cpp
++counter;
```

如果不是原子操作，就会发生数据竞争，结果不可预测。

### 2. 在消费者里捕获过宽异常却不排查来源

今天为了快速退出，`catch (const std::exception&)` 是可以接受的。但你要明确：

- 它应该只用于接收“队列关闭”语义
- 如果将来 `pop()` 里还会抛别的异常，测试就会把真实 bug 吃掉

长期来看，更稳妥的设计是把 `pop()` 改成返回 `std::optional<T>` 或 `bool pop(T&)`。

### 3. 过早追求复杂校验

第一次验证先抓主链路：

- 不死锁
- 不丢数据
- 不重复消费

不要一开始就加入过多额外统计，否则测试本身会先变复杂。
