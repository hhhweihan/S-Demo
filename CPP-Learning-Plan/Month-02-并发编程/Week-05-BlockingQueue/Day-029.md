# Day 29（Mon）— joining_thread（RAII 封装）

## 预计时间

1 小时

## 今天要解决什么问题

`std::thread` 的析构函数有一个很容易踩坑的行为：

- 如果线程对象在析构时仍然是 `joinable()` 状态，程序会直接触发 `std::terminate`
- 这意味着“忘记调用 `join()` 或 `detach()`”不是普通 bug，而是直接崩溃

在后面的阻塞队列、线程池、生产者消费者测试里，线程数量会变多。继续裸用 `std::thread`，管理成本和漏掉 `join()` 的风险都会明显上升。

今天先做一个最小但非常实用的 RAII 封装：`JoiningThread`。

目标只有一个：

- 对象离开作用域时，如果内部线程还没被回收，就自动 `join()`

这一步不是为了“造轮子”，而是为了让后续并发代码先具备一个安全默认值。

## 任务

- [x] 创建 `concurrent/joining_thread.h`
- [x] 实现 `JoiningThread`：

  ```cpp
  class JoiningThread {
      std::thread t_;
  public:
      template<typename F, typename... Args>
      explicit JoiningThread(F&& f, Args&&... args)
          : t_(std::forward<F>(f), std::forward<Args>(args)...) {}
      ~JoiningThread() { if (t_.joinable()) t_.join(); }  // 析构时自动 join
      JoiningThread(JoiningThread&&) = default;
      JoiningThread(const JoiningThread&) = delete;
  };
  ```

- [x] 对比：直接用 `std::thread` 但忘记 join 会发生什么（`std::terminate`）

## 你需要掌握的点

### 1. 为什么 RAII 适合线程管理

RAII 的核心思想是：

- 资源在对象构造时获取
- 资源在对象析构时释放

线程句柄本质上也是一种资源。把“线程回收责任”绑定到对象生命周期上，比靠调用者手动记忆更稳。

这里的“释放”不是销毁线程本身，而是保证线程对象在退出前完成 `join()`，避免悬空线程状态导致进程异常结束。

### 2. 为什么析构里必须先判断 `joinable()`

`std::thread` 在以下情况下可能不可 join：

- 默认构造出来，没有实际线程
- 已经被 `join()` 过
- 已经被 `detach()` 过
- 资源已经被移动走

因此析构里必须这样写：

```cpp
~JoiningThread() {
    if (t_.joinable()) {
        t_.join();
    }
}
```

### 3. 为什么只能移动，不能拷贝

线程对象代表唯一的执行实体所有权，所以：

- 应当支持移动构造 / 移动赋值
- 必须禁用拷贝构造 / 拷贝赋值

否则会出现“两个对象都以为自己拥有同一个线程”的语义错误。

## 推荐实现

先做最小可用版本，不追求一次加太多接口。你今天只需要把“默认安全”做到位。

```cpp
#pragma once

#include <thread>
#include <utility>

class JoiningThread {
public:
    JoiningThread() noexcept = default;

    template <typename F, typename... Args>
    explicit JoiningThread(F&& func, Args&&... args)
        : t_(std::forward<F>(func), std::forward<Args>(args)...) {}

    JoiningThread(JoiningThread&&) noexcept = default;
    JoiningThread& operator=(JoiningThread&&) noexcept = default;

    JoiningThread(const JoiningThread&) = delete;
    JoiningThread& operator=(const JoiningThread&) = delete;

    ~JoiningThread() {
        if (t_.joinable()) {
            t_.join();
        }
    }

    bool joinable() const noexcept {
        return t_.joinable();
    }

    void join() {
        t_.join();
    }

    std::thread::id get_id() const noexcept {
        return t_.get_id();
    }

    std::thread& as_thread() noexcept {
        return t_;
    }

private:
    std::thread t_;
};
```

## 实现步骤

### 第一步：先写头文件骨架

- 包含 `thread` 和 `utility`
- 放一个成员 `std::thread t_`
- 默认构造先保留，便于后面放入容器或延迟启动

### 第二步：实现模板构造函数

关键点是完美转发：

```cpp
template <typename F, typename... Args>
explicit JoiningThread(F&& func, Args&&... args)
    : t_(std::forward<F>(func), std::forward<Args>(args)...) {}
```

这里本质上只是把参数原样转交给内部的 `std::thread`。

### 第三步：实现析构自动 join

今天最关键的一行代码就是：

```cpp
if (t_.joinable()) t_.join();
```

这保证了调用方即使忘记手动回收，也不会在作用域结束时直接崩掉。

### 第四步：补齐移动语义，禁用拷贝

建议显式写出来，不要只靠你脑子记：

- `JoiningThread(JoiningThread&&) noexcept = default;`
- `JoiningThread& operator=(JoiningThread&&) noexcept = default;`
- `JoiningThread(const JoiningThread&) = delete;`
- `JoiningThread& operator=(const JoiningThread&) = delete;`

## 建议测试

### 测试 1：作用域退出时自动 join

```cpp
#include <chrono>
#include <iostream>
#include <thread>

#include "concurrent/joining_thread.h"

int main() {
    using namespace std::chrono_literals;

    {
        JoiningThread t([] {
            std::this_thread::sleep_for(200ms);
            std::cout << "worker done\n";
        });

        std::cout << "leaving scope\n";
    }

    std::cout << "main done\n";
}
```

预期现象：

- 不需要手动 `join()`
- 程序不会崩溃
- `main done` 一定在子线程结束之后输出

### 测试 2：对比裸 `std::thread`

把上面的 `JoiningThread` 换成裸 `std::thread`，并且故意不写 `join()`：

```cpp
{
    std::thread t([] {
        std::this_thread::sleep_for(std::chrono::milliseconds(200));
    });
}
```

预期现象：

- 程序在离开作用域时直接触发 `std::terminate`

这一步非常重要。你只有亲手看过一次，后面才会真正记住：线程回收不是“代码整洁问题”，而是进程生死问题。

## 常见坑

### 1. 不要在析构里无脑 `join()`

如果线程对象已经不可 join，再调 `join()` 是未定义使用方式，通常会抛异常或终止。因此必须先做 `joinable()` 判断。

### 2. 析构自动 join 可能带来阻塞

这是 `JoiningThread` 的优势，也是代价。

- 优势：不会忘记回收线程
- 代价：如果子线程执行很久，析构时主线程会被阻塞

这不是 bug，而是语义选择。今天我们的目标是“安全优先”，所以接受这个代价。

### 3. 先不要暴露 `detach()`

`detach()` 会让线程与对象生命周期脱钩，管理复杂度会迅速上升。对当前学习阶段，不建议给封装加这个接口。

### 4. 移动赋值要谨慎

如果后面你自己扩展 `operator=(JoiningThread&&)`，要先处理当前对象里已有线程是否需要回收。今天先用默认版本即可，不要过度设计。

## 和本周主题的关系

明天开始写阻塞队列时，你会频繁创建生产者线程和消费者线程。先把线程生命周期管理好，有两个直接好处：

- 测试代码更短，不容易漏掉 `join()`
