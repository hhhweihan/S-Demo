# Day 32（Thu）— 有界阻塞队列

## 预计时间

1 小时

## 今天要解决什么问题

昨天的 `BlockingQueue<T>` 解决了“空时等待”的问题，但它默认是无界的：

- 生产者只要愿意，可以一直 `push`
- 消费者如果跟不上，队列会无限增长
- 最终问题会从“线程同步”变成“内存膨胀”

真实系统里，这通常是不能接受的。

所以今天要实现一个更接近工程实践的版本：`BoundedQueue<T>`。

它比无界队列多了一层重要语义：

- 队列满时，生产者也必须阻塞等待

这就是背压。没有背压，系统只是在把压力从 CPU 转移到内存。

## 你需要掌握的点

### 1. 有界队列和无界队列的本质差别是什么

无界队列只关心一个条件：

- 队列是不是空

有界队列要同时关心两个方向：

- 消费者关心：队列是不是空
- 生产者关心：队列是不是满

这意味着状态机更复杂了，因为你不仅要决定“谁该睡”，还要决定“谁该被唤醒”。

### 2. 为什么通常需要两个 `condition_variable`

理论上也可以只用一个条件变量，但会带来两个问题：

- 唤醒粒度粗，容易唤醒错对象
- 代码读起来不清楚，后续排查状态问题会很痛苦

分成两个条件变量后，语义更直接：

- 生产者等待 `not_full_`
- 消费者等待 `not_empty_`

这不是“为了优雅”，而是为了让同步协议更容易写对。

### 3. 背压为什么是系统稳定性的关键

如果一个模块的上游生产速度始终大于下游消费速度，而你又不给它任何限制，那么结果只会是：

- 队列越来越长
- 内存越来越大
- 延迟越来越高
- 最终系统整体失控

有界队列的价值不是“限制功能”，而是强制系统暴露真实处理能力。

一旦生产者被阻塞，你就会立刻看到：

- 下游处理不过来
- 当前容量设置是否合理
- 是否需要增加消费者或优化处理逻辑

### 4. 为什么 `shutdown()` 现在更重要了

在无界队列里，主要是消费者会阻塞在空队列上。

在有界队列里，两边都可能阻塞：

- 消费者卡在“队列空”
- 生产者卡在“队列满”

如果 `shutdown()` 只唤醒消费者，不唤醒生产者，就会出现一半线程退出、一半线程永久卡住的情况。

所以今天的关闭语义必须覆盖两种等待。

## 推荐接口

建议延续 Day 30 的风格，先做一个简单稳定版本：

```cpp
template <typename T>
class BoundedQueue {
public:
  explicit BoundedQueue(std::size_t capacity);

  void push(T value);
  T pop();
  bool try_pop(T& out);
  bool try_push(T value);

  std::size_t size() const;
  bool empty() const;
  void shutdown();

private:
  std::size_t capacity_;
  std::queue<T> queue_;
  mutable std::mutex mtx_;
  std::condition_variable not_empty_;
  std::condition_variable not_full_;
  bool shutdown_ = false;
};
```

其中：

- `push()` 在满时阻塞
- `pop()` 在空时阻塞
- `try_push/try_pop()` 保留非阻塞接口，方便以后写 benchmark

## 推荐实现

下面是一版适合今天练习的最小实现。关闭时仍然沿用“抛异常表示退出”这一语义：

```cpp
#pragma once

#include <condition_variable>
#include <cstddef>
#include <mutex>
#include <queue>
#include <stdexcept>
#include <utility>

template <typename T>
class BoundedQueue {
public:
  explicit BoundedQueue(std::size_t capacity)
    : capacity_(capacity) {
    if (capacity_ == 0) {
      throw std::invalid_argument("capacity must be > 0");
    }
  }

  void push(T value) {
    std::unique_lock<std::mutex> lock(mtx_);
    not_full_.wait(lock, [this] {
      return queue_.size() < capacity_ || shutdown_;
    });

    if (shutdown_) {
      throw std::runtime_error("push on shutdown BoundedQueue");
    }

    queue_.push(std::move(value));
    lock.unlock();
    not_empty_.notify_one();
  }

  T pop() {
    std::unique_lock<std::mutex> lock(mtx_);
    not_empty_.wait(lock, [this] {
      return !queue_.empty() || shutdown_;
    });

    if (queue_.empty()) {
      throw std::runtime_error("pop from shutdown BoundedQueue");
    }

    T value = std::move(queue_.front());
    queue_.pop();
    lock.unlock();
    not_full_.notify_one();
    return value;
  }

  bool try_push(T value) {
    std::lock_guard<std::mutex> lock(mtx_);
    if (shutdown_ || queue_.size() >= capacity_) {
      return false;
    }
    queue_.push(std::move(value));
    not_empty_.notify_one();
    return true;
  }

  bool try_pop(T& out) {
    std::lock_guard<std::mutex> lock(mtx_);
    if (queue_.empty()) {
      return false;
    }
    out = std::move(queue_.front());
    queue_.pop();
    not_full_.notify_one();
    return true;
  }

  void shutdown() {
    {
      std::lock_guard<std::mutex> lock(mtx_);
      shutdown_ = true;
    }
    not_empty_.notify_all();
    not_full_.notify_all();
  }

private:
  std::size_t capacity_;
  std::queue<T> queue_;
  mutable std::mutex mtx_;
  std::condition_variable not_empty_;
  std::condition_variable not_full_;
  bool shutdown_ = false;
};
```

## 实现步骤

### 第一步：先写好不变量

今天最关键的不变量只有两个：

- `0 <= queue_.size() <= capacity_`
- `shutdown_` 和 `queue_` 必须受同一把锁保护

后面的所有等待条件，都是围绕这两个不变量展开的。

### 第二步：先写 `push()` 的等待谓词

生产者等待条件不是“队列不满”这么简单，而是：

- 队列不满，可以继续 push
- 或者队列已关闭，需要立刻醒来退出

因此谓词应写成：

```cpp
queue_.size() < capacity_ || shutdown_
```

### 第三步：再写 `pop()` 的等待谓词

消费者和昨天一样，等待：

```cpp
!queue_.empty() || shutdown_
```

两边的模式是一致的。你会开始发现：

- 条件变量本质上是在等待“共享状态满足某个布尔表达式”

### 第四步：注意谁该通知谁

这里最容易写反：

- `push()` 成功放入元素后，应通知 `not_empty_`
- `pop()` 成功取走元素后，应通知 `not_full_`

你可以简单理解为：

- 你改变了哪个方向的阻塞条件，就通知哪一侧

## 建议测试

### 测试 1：容量 10，生产快于消费

可以这样构造：

- 1 个生产者快速 push 100 个整数
- 1 个消费者每次 `pop()` 后 `sleep_for(1ms)`

预期现象：

- 程序能够正常完成
- 不会死锁
- 生产者总耗时明显大于“纯 for 循环 push 100 次”的时间

这说明它确实被背压限制住了。

### 测试 2：把容量改成 1

容量为 1 时，系统行为最容易观察：

- 生产一个
- 消费一个
- 生产一个
- 消费一个

如果你的同步逻辑有问题，这种最紧绷的场景往往最容易暴露。

### 测试 3：关闭时双向唤醒

你可以分别构造：

- 消费者阻塞在空队列上
- 生产者阻塞在满队列上

然后调用 `shutdown()`，确认两边都能退出。

## 常见坑

### 1. 在持锁状态下做过多工作

队列操作本身必须持锁，但：

- 不要在锁内打印日志
- 不要在锁内做耗时计算
- 不要在锁内执行用户回调

锁持有时间越长，阻塞和竞争就越严重。

### 2. 唤醒顺序写反

常见错误是：

- `push()` 后通知 `not_full_`
- `pop()` 后通知 `not_empty_`

这在逻辑上是错位的，会导致线程被错误唤醒，甚至出现长期卡顿。

### 3. `shutdown()` 只 `notify_one()`

关闭是全局状态变化，不是单个元素变化。

所以必须：

```cpp
not_empty_.notify_all();
not_full_.notify_all();
```

## 和后续主题的关系

有界队列的价值，不只是“多一个容量参数”，而是你第一次真正接触到背压机制。

后面的线程池、异步日志、网络发送队列，都会遇到同一个问题：

- 当下游处理不过来时，上游应该怎么办

今天这一步是后面所有限流、削峰、排队策略的基础。

## 完成标志

- `BoundedQueue<T>` 能正确阻塞生产者和消费者
- 满时 `push()` 不会忙等
- 空时 `pop()` 不会忙等
- `shutdown()` 能唤醒两侧等待线程
- 测试中能观察到明确的背压行为且无死锁
