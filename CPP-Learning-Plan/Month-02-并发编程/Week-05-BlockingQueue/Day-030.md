# Day 30（Tue）— 有锁阻塞队列

## 预计时间

1 小时

## 今天要解决什么问题

昨天的 `JoiningThread` 解决了“线程对象如何安全回收”的问题，今天开始进入并发模块的第一个核心数据结构：阻塞队列。

它要解决的是这类场景：

- 生产者线程持续往队列里塞任务
- 消费者线程持续从队列里取任务
- 当队列为空时，消费者不应该忙等占满 CPU，而应该阻塞等待

如果没有阻塞队列，线程池、日志队列、任务分发器这些结构都只能靠轮询或者手搓同步逻辑，代码会很快失控。

今天先实现最小可用版本：

- 用 `std::mutex` 保护共享队列
- 用 `std::condition_variable` 在“队列空”时挂起消费者
- 用 `shutdown()` 让所有阻塞中的消费者安全退出

这一版先不追求无锁和极致性能，重点是把并发语义写对。

## 任务

- [ ] 创建 `concurrent/blocking_queue.h`
- [ ] 实现 `BlockingQueue<T>`：

  ```cpp
  template<typename T>
  class BlockingQueue {
    std::queue<T> queue_;
    std::mutex mtx_;
    std::condition_variable cv_;
    bool shutdown_ = false;
  public:
    void push(T value);        // 加锁，push，notify_one
    T pop();                   // 加锁，等待非空，pop 并返回
    bool try_pop(T& out);      // 非阻塞，失败返回 false
    size_t size() const;
    bool empty() const;
    void shutdown();           // 标记关闭，所有阻塞的 pop 返回
  };
  ```

- [ ] 注意 `pop()` 里 `condition_variable` 必须等待“队列非空或已经关闭”这两个条件之一：

  ```cpp
  std::unique_lock<std::mutex> lock(mtx_);
  cv_.wait(lock, [this] { return !queue_.empty() || shutdown_; });
  ```

- [ ] 明确约定：`shutdown()` 后，已经阻塞的 `pop()` 必须能尽快返回，不能永久卡住

## 你需要掌握的点

### 1. 为什么不能用忙等

最差的写法通常是：

```cpp
while (queue.empty()) {
  // 什么也不做
}
```

或者：

```cpp
while (queue.empty()) {
  std::this_thread::sleep_for(1ms);
}
```

这两种都不理想：

- 第一种会白白烧 CPU
- 第二种虽然少烧一点 CPU，但仍然有延迟，而且语义很粗糙

阻塞队列的正确思路是：

- 没数据时让线程睡眠
- 有数据时由生产者主动唤醒消费者

这就是 `condition_variable` 的职责。

### 2. 共享状态不只是队列，还有关闭标志

很多人第一次写阻塞队列，只盯着 `queue_`，但真正的共享状态至少有两份：

- 队列里是否有数据
- 队列是否已经关闭

如果只判断“队列空不空”，那么当系统准备退出时，消费者可能永远睡死在 `wait()` 里。

因此 `shutdown_` 必须和 `queue_` 一样，受同一把锁保护，并进入 `wait` 的谓词条件中。

### 3. 为什么 `wait()` 要写谓词版本

标准库允许 `condition_variable` 发生伪唤醒，也就是线程被唤醒后，条件其实并没有成立。

所以不要写成：

```cpp
cv_.wait(lock);
```

然后醒来后就默认队列一定非空。正确写法是：

```cpp
cv_.wait(lock, [this] { return !queue_.empty() || shutdown_; });
```

等价于“循环检查条件，条件不满足就继续睡”。

### 4. `notify_one()` 和 `notify_all()` 的使用场景不同

- 普通 `push()` 后一般只需要唤醒一个等待消费者，所以用 `notify_one()`
- `shutdown()` 时可能有很多消费者都在阻塞，此时应该用 `notify_all()`

这不是性能优化细节，而是行为正确性要求。

## 推荐接口语义

今天先用一套简单、稳定、好测试的语义，不要过度设计。

### `push(T value)`

- 获取锁
- 如果队列已关闭，直接拒绝插入，常见做法是抛异常或返回
- 正常情况下把元素放入队列
- 解锁后 `notify_one()`

### `pop()`

- 获取 `unique_lock`
- 等待直到“队列非空”或“队列关闭”
- 如果醒来后队列非空，就取出一个元素并返回
- 如果队列为空且已经关闭，说明不会再有新数据，此时应当返回一个“关闭信号”

这里有一个设计分歧：

- 若函数签名坚持是 `T pop()`，则通常需要在关闭且为空时抛异常
- 若改成 `bool pop(T& out)` 或 `std::optional<T> pop()`，关闭语义会更自然

今天任务单里给的是 `T pop()`，你可以先用“关闭时抛异常”这个最直白的版本，后面再重构。

### `try_pop(T& out)`

- 只做一次加锁检查
- 队列为空直接返回 `false`
- 不阻塞，不等待

### `shutdown()`

- 加锁把 `shutdown_` 设为 `true`
- 释放锁后 `notify_all()`

注意：`shutdown()` 不是清空队列，也不是强行中断正在执行的消费者；它的含义是“不会再有新的等待意义了，阻塞者都该醒来检查退出条件”。

## 推荐实现

下面是一版适合今天练习的最小实现。为了让 `T pop()` 能表达“关闭且为空”，这里用抛异常的方式处理：

```cpp
#pragma once

#include <condition_variable>
#include <cstddef>
#include <mutex>
#include <queue>
#include <stdexcept>
#include <utility>

template <typename T>
class BlockingQueue {
public:
  void push(T value) {
    {
      std::lock_guard<std::mutex> lock(mtx_);
      if (shutdown_) {
        throw std::runtime_error("push on shutdown BlockingQueue");
      }
      queue_.push(std::move(value));
    }
    cv_.notify_one();
  }

  T pop() {
    std::unique_lock<std::mutex> lock(mtx_);
    cv_.wait(lock, [this] { return !queue_.empty() || shutdown_; });

    if (queue_.empty()) {
      throw std::runtime_error("pop from shutdown BlockingQueue");
    }

    T value = std::move(queue_.front());
    queue_.pop();
    return value;
  }

  bool try_pop(T& out) {
    std::lock_guard<std::mutex> lock(mtx_);
    if (queue_.empty()) {
      return false;
    }
    out = std::move(queue_.front());
    queue_.pop();
    return true;
  }

  bool empty() const {
    std::lock_guard<std::mutex> lock(mtx_);
    return queue_.empty();
  }

  std::size_t size() const {
    std::lock_guard<std::mutex> lock(mtx_);
    return queue_.size();
  }

  void shutdown() {
    {
      std::lock_guard<std::mutex> lock(mtx_);
      shutdown_ = true;
    }
    cv_.notify_all();
  }

private:
  mutable std::mutex mtx_;
  std::condition_variable cv_;
  std::queue<T> queue_;
  bool shutdown_ = false;
};
```

## 实现步骤

### 第一步：先把共享状态定义完整

不要只写：

- `std::queue<T> queue_`
- `std::mutex mtx_`
- `std::condition_variable cv_`

还要补上：

- `bool shutdown_ = false`

否则后面 `pop()` 不知道什么时候该退出等待。

### 第二步：先写最简单的 `push()`

顺序要清楚：

- 加锁
- 修改队列
- 解锁
- 唤醒一个等待者

常见写法是把锁作用域单独包起来，让 `notify_one()` 发生在解锁之后，这样更稳妥。

### 第三步：实现 `pop()` 的等待逻辑

这是今天最关键的部分：

```cpp
std::unique_lock<std::mutex> lock(mtx_);
cv_.wait(lock, [this] { return !queue_.empty() || shutdown_; });
```

醒来以后一定要二次分支：

- 队列非空，取数据
- 队列为空但已关闭，退出

不要把“被唤醒”误当成“必然有数据”。

### 第四步：补 `try_pop()`、`size()`、`empty()`

这几个接口逻辑都不复杂，但要保持一致：

- 都在锁保护下访问共享状态
- 不要在无锁状态下直接读 `queue_`

### 第五步：实现 `shutdown()`

这一步经常被低估，但其实决定了你的阻塞队列能不能优雅退出。

如果没有 `shutdown()`：

- 测试结束时消费者线程可能还卡在 `pop()` 里
- 主线程 `join()` 时会永久等待

## 建议测试

### 测试 1：单线程 push / pop

```cpp
BlockingQueue<int> q;
q.push(1);
q.push(2);

assert(q.pop() == 1);
assert(q.pop() == 2);
assert(q.empty());
```

目标：验证 FIFO 语义没有写错。

### 测试 2：消费者先阻塞，生产者后唤醒

```cpp
BlockingQueue<int> q;

std::thread consumer([&] {
  int value = q.pop();
  std::cout << value << '\n';
});

std::this_thread::sleep_for(std::chrono::milliseconds(100));
q.push(42);
consumer.join();
```

目标：验证 `pop()` 会阻塞等待，并在 `push()` 后被唤醒。

### 测试 3：`shutdown()` 能唤醒阻塞中的消费者

```cpp
BlockingQueue<int> q;

std::thread consumer([&] {
  try {
    q.pop();
  } catch (const std::runtime_error&) {
    std::cout << "shutdown observed\n";
  }
});

std::this_thread::sleep_for(std::chrono::milliseconds(100));
q.shutdown();
consumer.join();
```

目标：验证没有数据时，消费者不会永久卡死。

## 常见坑

### 1. 忘了把 `shutdown_` 放进等待条件

这是最常见的死锁来源之一。

如果 `wait()` 只看 `!queue_.empty()`，那关闭时线程根本醒不过来。

### 2. 用 `lock_guard` 写 `wait()`

`condition_variable::wait()` 需要能解锁再上锁，因此必须配 `std::unique_lock<std::mutex>`，不能用 `lock_guard`。

### 3. 被唤醒后直接 `pop()`

唤醒不代表条件一定成立，尤其在多消费者场景下，可能另一个线程先一步取走数据。

所以一定要通过谓词或循环重新检查条件。

### 4. `notify_all()` 乱用在每次 `push()` 上

功能上不一定错，但会导致无意义的惊群唤醒。普通入队只唤醒一个消费者即可。

### 5. `size()` / `empty()` 忘记加锁

哪怕只是“读一下状态”，在并发环境里也属于访问共享数据，同样需要同步保护。
