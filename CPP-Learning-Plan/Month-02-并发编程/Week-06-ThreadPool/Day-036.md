# Day 36（Mon）— 基础线程池

## 预计时间

1 小时

## 今天要解决什么问题

Week 05 已经把线程池最难踩坑的底层能力铺好了：

- `JoiningThread` 解决线程对象回收
- `BlockingQueue` 解决任务的阻塞式交接
- `shutdown()` 语义解决阻塞线程退出

所以 Day 36 的目标非常明确：

- 把这些零件真正组装成一个最小可用线程池

这里的“最小可用”有两个关键词：

- **固定线程数**：先不做扩缩容
- **只接收 `std::function<void()>`**：先不处理返回值

这一步很重要，因为线程池真正的核心并不是 `submit()` 的模板技巧，而是下面这条工作流：

```text
主线程提交任务
  -> 任务进入阻塞队列
  -> worker 线程被唤醒
  -> worker 执行任务
  -> 线程池关闭时，worker 平稳退出
```

如果 Day 36 这条主线还不稳，Day 37 再加 `future` 只会把复杂度叠上去，而不会让线程池更可靠。

## 你需要掌握的点

### 1. 线程池的本质不是“很多线程”，而是“复用线程执行离散任务”

如果每来一个任务就创建一个新线程，那么系统会不断支付：

- 线程创建成本
- 线程销毁成本
- 更高的调度压力

线程池的核心价值就是把线程变成长期驻留的 worker：

- 线程先创建好
- 空闲时阻塞等待任务
- 有任务时被唤醒执行
- 任务执行完继续等待下一批任务

所以线程池解决的不是“能不能并发”，而是“如何更稳定地重复利用并发资源”。

### 2. Day 36 先不要上 `future`，是为了把控制面和数据面拆开

今天的线程池只有两件事：

- 接收任务
- 执行任务

先不处理：

- 返回值
- 异常跨线程传播
- 任意模板参数转发

这样做不是保守，而是在刻意拆复杂度。

你可以把 Day 36 理解成线程池的“控制面”版本：

- worker 怎么启动
- queue 怎么连接 worker 和调用方
- shutdown 怎么结束线程

等这部分语义稳定了，Day 37 再把 `future/promise` 这层“结果面”接上去，结构会清晰很多。

### 3. worker 循环最重要的不是 `task()`，而是退出条件

新手最容易把重点放在：

```cpp
auto task = queue_.pop();
task();
```

但线程池真正容易写错的是：

- 什么时候停
- 怎么停
- 停的时候队列里剩余任务怎么处理

对 Day 36 这种最小版，推荐先定义一个简单且稳定的语义：

- 线程池处于 `running_ == true` 时允许提交任务
- `shutdown()` 后不再接受新任务
- `shutdown()` 会触发 `queue_.shutdown()`，唤醒阻塞中的 worker
- worker 在收到“队列关闭且无任务”信号后退出循环

这条退出协议必须先写清楚，再写实现。

### 4. `JoiningThread` 在这里不是锦上添花，而是默认安全策略

线程池内部通常会保存很多线程对象。如果继续裸用 `std::thread`，风险会被放大：

- 某个构造路径异常
- 某个 shutdown 路径少了 `join`
- 某个容器清理分支遗漏线程回收

`JoiningThread` 在这里的价值非常直接：

- 把 worker 线程回收默认做对
- 减少线程池析构路径里的管理负担

这也是 Week 05 和 Week 06 的自然衔接点之一。

## 推荐接口

Day 36 建议先把接口压到最小：

```cpp
class ThreadPool {
public:
  explicit ThreadPool(std::size_t worker_count);
  ~ThreadPool();

  void submit(std::function<void()> task);
  void shutdown();

private:
  void worker_loop();

  std::vector<JoiningThread> workers_;
  BlockingQueue<std::function<void()>> queue_;
  std::atomic<bool> running_{true};
};
```

这里故意不一次塞太多接口：

- 不做 `submit` 模板化
- 不做 `size()`、`pending_tasks()` 等附加查询
- 不做 resize

先保证一条主链路顺畅：创建、投递、执行、关闭。

## 推荐实现

下面是一版适合 Day 36 的最小实现思路。假设你的 `BlockingQueue::pop()` 在关闭且为空时会抛异常：

```cpp
#pragma once

#include <atomic>
#include <cstddef>
#include <functional>
#include <stdexcept>
#include <vector>

#include "concurrent/blocking_queue.h"
#include "concurrent/joining_thread.h"

class ThreadPool {
public:
  explicit ThreadPool(std::size_t worker_count) {
    if (worker_count == 0) {
      throw std::invalid_argument("worker_count must be > 0");
    }

    workers_.reserve(worker_count);
    for (std::size_t i = 0; i < worker_count; ++i) {
      workers_.emplace_back([this] { worker_loop(); });
    }
  }

  ~ThreadPool() {
    shutdown();
  }

  void submit(std::function<void()> task) {
    if (!running_.load(std::memory_order_acquire)) {
      throw std::runtime_error("submit on stopped ThreadPool");
    }
    queue_.push(std::move(task));
  }

  void shutdown() {
    bool expected = true;
    if (running_.compare_exchange_strong(
        expected, false, std::memory_order_acq_rel)) {
      queue_.shutdown();
    }
  }

private:
  void worker_loop() {
    while (true) {
      try {
        auto task = queue_.pop();
        if (task) {
          task();
        }
      } catch (const std::exception&) {
        break;
      }
    }
  }

  std::vector<JoiningThread> workers_;
  BlockingQueue<std::function<void()>> queue_;
  std::atomic<bool> running_{true};
};
```

这版实现最大的优点是：

- 结构足够小
- 退出路径清楚
- 可以直接进入测试

最大的限制也很明确：

- 只能接 `void()` 任务
- 不能返回结果
- 对异常语义依赖 `BlockingQueue::pop()` 的实现方式

但这些限制都是 Day 37 以后再解决的事。

## 实现步骤

### 第一步：先把 worker 线程启动逻辑写出来

构造函数里最重要的是这件事：

```cpp
for (std::size_t i = 0; i < worker_count; ++i) {
  workers_.emplace_back([this] { worker_loop(); });
}
```

不要一上来就把 `submit()` 写复杂。线程池的本体首先是 worker 集合。

### 第二步：单独写 `worker_loop()`

把 worker 行为抽成私有成员函数，能明显提高可读性。

它的职责只有三件事：

- 从队列取任务
- 执行任务
- 在关闭信号到达时退出

如果把这些逻辑散在 lambda 里，后面改 `future` 版本时会比较乱。

### 第三步：再实现 `submit()`

Day 36 的 `submit()` 非常朴素：

- 检查线程池是否还在运行
- 把任务压入队列

这里真正要注意的是关闭态：

- `shutdown()` 后继续提交任务，应该显式失败

不要让这种调用悄悄成功或悄悄丢弃。

### 第四步：最后写 `shutdown()` 和析构路径

推荐让析构函数直接调用 `shutdown()`，把停止逻辑集中到一个地方。

这样能保证：

- 手动关闭和自动析构的行为一致
- 不需要维护两份退出逻辑

## 建议测试

### 测试 1：提交 100 个简单任务

最小测试可以这样设计：

- 创建 4 个 worker 的线程池
- 提交 100 个 lambda

- 主线程销毁线程池后检查计数器是否等于 100

这种测试比打印更可靠，因为输出顺序本身受调度影响，不适合当主要断言。

### 测试 2：任务里故意 `sleep_for`

你可以让每个任务休眠几毫秒，确认：

- 多个 worker 确实在并发消费任务
- 线程池销毁时会等待 worker 完成

这一步有助于直观看到 `JoiningThread` 的价值。

### 测试 3：关闭后继续提交任务

这一步要确认你的接口语义清晰：

- `shutdown()` 后再 `submit()`，应抛异常或以明确方式失败

如果这个边界行为不稳定，后面加 `future` 时会更难排查。

## 常见坑

### 1. 用 `while (running_)` 作为 worker 主条件但忽略队列里剩余任务

这是 Day 36 最容易出现的设计错误之一。

如果 worker 写成：

```cpp
while (running_) {
  auto task = queue_.pop();
  task();
}
```

那么当 `running_` 被设为 `false` 时，可能出现：

- 队列里还有任务
- 但 worker 已经提前退出

因此更稳妥的做法是让退出语义由 `queue_.pop()` 的关闭行为驱动，而不是只看一个原子标志。

### 2. 在析构前不先触发 `shutdown()`

如果 worker 正阻塞在 `pop()`，单纯等待线程对象析构并不能让它们自己醒来。必须先通过队列关闭把它们唤醒。

### 3. `submit()` 不检查停止状态

如果线程池已经关闭，而任务仍然能被提交：

- 任务可能永远没人执行
- 或者直接和关闭路径打架

这是一个必须明确拦住的接口边界。

## 和 Day 37 的关系

Day 36 搭的是最小线程池骨架：

- worker 生命周期
- 任务队列
- 基本 shutdown 协议

Day 37 要做的事情，本质上只是给这个骨架加“结果返回能力”：

- `submit()` 不再只接收 `std::function<void()>`
- 任意可调用对象会被打包成 `packaged_task`
- 调用方通过 `future.get()` 取回结果

所以你可以把两天的关系理解成：

```text
Day 36: 线程池先跑起来
Day 37: 线程池开始带结果返回
```
