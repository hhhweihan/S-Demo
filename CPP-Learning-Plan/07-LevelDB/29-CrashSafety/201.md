## 编号 201 — kill-9 持久性测试范式：fork/_exit 猝死后 Recover

**掌握标准：能说清「为什么用 fork 子进程而不是在本进程测」「为什么必须 `_exit` 而不是 `exit`」，并解释
这个范式验证的到底是什么保证。**

### 要验证的保证

崩溃安全的核心承诺：**已确认（acked）的写，在进程被强杀 / 掉电后不丢**。要真正验证它，测试必须制造一次
「不给任何清理机会」的猝死——析构函数、`atexit`、缓冲区 flush **统统不执行**——然后重开库看数据还在不在。
普通的 `return` / 抛异常都会走正常栈展开与析构，测不出这个保证。

### 范式：fork 子进程猝死

```cpp
pid_t pid = fork();
if (pid == 0) {
    // 子进程：开库，Put N 条（每条 WAL fsync 后才返回 = acked）
    MiniDB db(dir); db.Recover();
    for (int i = 0; i < 50; ++i) db.Put(key(i), val(i));
    _exit(0);            // 猝死：跳过析构 / atexit / gtest 清理
}
// 父进程：等子进程死透，重开同一目录 Recover，断言 50 条 acked 写全在
int status = 0; waitpid(pid, &status, 0);
MiniDB db(dir); db.Recover();
for (int i = 0; i < 50; ++i) EXPECT_EQ(db.Get(key(i)), val(i));
```

### 两个关键点

1. **必须 `_exit` 不是 `exit`。** `exit()` 会跑 `atexit` 注册的钩子和 C++ 静态析构——gtest 正是用这些收尾。
   子进程若 `exit`，会**在子进程里重新触发 gtest 的收尾逻辑**（重复输出/重复统计/句柄错乱）。`_exit`（或
   `_Exit`）直接终止进程、只关文件描述符，最接近「掉电」。这也是为什么子进程里不 `ASSERT`（断言在父进程做）。

2. **acked 的定义。** 子进程的每次 `Put` 在 `wal_.Append` 里 `fsync` 成功后才返回（见 [[197|编号 197]]）。
   所以「子进程执行到 `_exit` 前完成的每一次 Put」都是 acked，父进程必须全部读到。至于崩溃瞬间可能没写完的
   那条尾部 record，回放时因 CRC/长度校验失败被干净丢弃——不算 acked，丢了也符合承诺。

### 为什么不进 TSan

fork 在 ThreadSanitizer 下噪声极大（运行时状态跨 fork 不可靠），此类崩溃测试固定跑普通 Debug；
块/footer 解析的缓冲算术风险交给 ASan/UBSan 覆盖。

### 验证

- `Kill9DurabilityAckedWritesSurvive`：父 fork 子；子 `Recover`+50 次 `Put` 后 `_exit(0)`；父 `waitpid`
  后重开库 `Recover`，断言 50 条全部命中——证明「fsync 返回即不丢」在真实猝死下成立。
