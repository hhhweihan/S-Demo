## 编号 199 — tombstone MemTable：二进制 internal key + 三态查找

**掌握标准：能默写 internal key = user_key + tag 的布局与比较器方向，并解释「为什么删除要写墓碑而不是
原地抹除」「为什么比较器要让新版本排在前」。**

### internal key 布局

MemTable 用 `SkipList<string,string,InternalKeyComparator>` 索引，键是编码后的 **internal key**：

```
internal_key = user_key + tag(8 LE)
tag          = (sequence << 8) | value_type    // value_type ∈ {kValue=1, kDeletion=0}
```

同一个 user_key 的多次写入产生**多条** internal key，靠 tag 里的 sequence 区分版本。

### 比较器方向（关键）

`InternalKeyComparator`：
- **user_key 升序**（字典序）；
- user_key 相同时 **tag 降序** → 因 sequence 在高位，等价于 **sequence 降序（新版本在前）**。

于是对某个 user_key 做 `lower_bound`，第一个命中的就是**最新版本**——查找天然拿到最新写/最新删除，不必
遍历所有版本。

### 三态查找

`Lookup(user_key, *value)` 返回 `LookupStatus`：
- `kFound`：最新版本是 `kValue` → 填 value；
- `kDeleted`：最新版本是 `kDeletion`（墓碑）→ 明确「已删除」，**不是**没找到；
- `kNotFound`：该 user_key 一条都没有。

三态的意义：跨层查找（MemTable→L0→L1）时，`kDeleted` 必须**立刻终止**并返回「不存在」，否则更底层的旧值
会把已删除的 key「复活」。二态（有/无）无法表达「这里明确删过，别再往下找了」。

### 为什么墓碑而非原地抹除

LSM 的 SSTable 一旦落盘就不可变（immutable），无法回头去某个旧文件里删掉一条记录。删除只能**向前追加**
一条墓碑，用「更新的版本」在查找时遮蔽旧值；真正的空间回收推迟到 compaction 把数据合并、且墓碑到达
**最底层**（其下不再有可能被遮蔽的旧值）时才丢弃。见 [[200|编号 200]]。

### 与落盘的衔接

`ExportSorted()` 按 internal key 顺序导出 `MemEntry{user_key, type, value}`，Flush 时原样交给
`SSTable::BuildFromEntries`——value 前缀的 `[type:1]` 把墓碑信息一并持久化（见 [[198|编号 198]]），
删除才能跨重启、跨层生效。

### 验证

- `MemTable*` 既有用例保持绿（API 未变）。
- `TombstoneShadowsFlushedValue`：Put 后 Flush，再 Delete，`Get` 返回空（墓碑在 MemTable 遮蔽了 L0 值）。
