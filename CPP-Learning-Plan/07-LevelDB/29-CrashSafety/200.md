## 编号 200 — 分层 compaction + 单调文件号 + MANIFEST-free 恢复

**掌握标准：能说清「归并顺序为什么从旧到新」「墓碑为什么只在最底层丢」「重开库怎么在没有 MANIFEST 的
情况下重建分层文件集」。**

### Flush → L0 → L1 的生命周期

- `Flush()`：MemTable 满或显式触发 → 导出有序 `MemEntry` → 写一个新 **L0** SSTable（`fsync`）→ 轮转 WAL。
  L0 文件彼此**范围可能重叠**（各自是某段时间的 MemTable 快照）。
- L0 文件数达 `kL0CompactionTrigger=4` → `CompactToBottom()`：把 L0（+现有 L1）归并成新的 **L1**。
  L1 文件 compaction 后**互不重叠**。

### 归并顺序：从旧到新

`CompactToBottom` 用 `map<user_key, MemEntry>` 归并，**先灌 L1（最旧），再灌 L0 的 front→back（旧→新）**：

```
for table in level1_:         merged[user_key] = entry   // 最旧打底
for table in level0_ (旧→新):  merged[user_key] = entry   // 后写覆盖先写
```

后写覆盖先写，最终每个 user_key 只剩**最新版本**（值或墓碑）。顺序错了会用旧值覆盖新值。

### 墓碑只在最底层回收

到达最底层（本 mini 版 L1 即最底层）时，其下不再有可能被遮蔽的旧值，墓碑已完成使命：

```
if entry.type == kValue: 保留
else (kDeletion):        丢弃   // 空间真正回收
```

**注意**：只有确定是最底层才能丢墓碑。若还有更低层，过早丢弃会让更低层的旧值复活——这就是墓碑必须
「一路下沉到底」才回收的原因（见 [[199|编号 199]]）。

### 单调文件号 + MANIFEST-free 恢复

本 mini 版**不落 MANIFEST**，而是把 level 与 file number 编进文件名：

```
sst_L{level}_{number:06}.sst      // 如 sst_L0_000007.sst
```

- 写文件用**单调递增** `next_file_number_`（不再硬编码 `000001.sst`），避免新旧文件同名互相覆盖。
- `Recover()` 扫描目录：`ParseSSTableFileName` 解析出 level/number → `Load` 且 `valid()` 才纳入
  （半写/损坏文件因 footer magic 缺失被跳过）→ 按 number 升序放回 L0/L1，`next_file_number_` 取最大值 +1。

文件名即最小化的元信息，省掉一个易错的 MANIFEST 组件，同时保住「重开库能重建完整分层视图」。旧文件在
compaction 写出新文件后统一 `remove` 删盘。

### 验证

- `CompactionReclaimsTombstonesAtBottomLevel`：写入 + 删除若干后 `CompactToBottom()`，断言墓碑对应 key
  彻底消失、活跃 key 仍在、`Level0FileCount()==0`。
- `RecoversAcrossFlushAndCompaction`：flush 与 compaction 交错后重开库，全部键值正确重建。
