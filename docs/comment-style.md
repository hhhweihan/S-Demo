# 注释规范（Comment Style）

这个仓库的注释经历过一次全量重写：从"逐行翻译代码在做什么"改为"只解释为什么"。
本文记录约定，供后续新增代码遵循。

## 核心原则：写 why，不写 what

代码本身已经说明了 *做了什么*。注释的价值在于代码无法表达的东西：
**意图、权衡、约束、以及"为什么不那样写"**。

反例（噪音，删除）：

```cpp
++size_;                          // 更新节点数量
current = current->left;          // 移动到左子节点
if (!parent) root_ = node;        // 树原本为空时新节点成为根
```

正例（有信息量，保留）：

```cpp
// insert() 是 upsert：已存在的 key 会被覆盖。这里只在 key 缺失时才默认构造，
// 否则会把已有值清成 Value{}。
if (auto* node = tree_.find_node(key)) return node->value;
```

## 什么时候该写注释

- **为什么用这个方案**：例如"用离散事件模拟而非真线程，因为要可复现"。
- **非显然的正确性约束**：例如 hazard pointer 的 retire 列表为什么会无界增长。
- **边界与陷阱**：例如"5 节点集群最多容忍 2 个故障，第 3 个会失去多数派"。
- **对外契约与不变量**：例如 Raft 的六条安全性属性在哪里被断言。
- **平台限制**：例如 io_uring 仅限 Linux。

## 什么时候不该写注释

- 复述控制流（`// 循环遍历数组`）。
- 复述类型或签名（`// 返回 int`）。
- 被注释掉的死代码——直接删，git 里有历史。

## 语言

- 中文注释用于业务/教学解释；英文注释用于贴近标准库术语的技术点。两者都可以，
  重点是**信息密度**，不是语言。
- 新写的测试统一用英文简短注释（和 GoogleTest 生态一致）。

## 格式

- 全仓统一由根目录 `.clang-format`（Google base，4 空格缩进，100 列）约束。
- 提交前跑：`clang-format -i $(find CPP-Practice -name '*.h' -o -name '*.cpp' | grep -v build)`。
