# 《程序员的自我修养：链接、装载与库》读书笔记

> 来源：`Note/C++-Note/程序员的自我修养—链接、装载与库--书签目录.pdf`。该 PDF 为扫描版，未包含可直接提取的正文文本层；本笔记以 PDF 书签目录为章节骨架，结合本书主题知识整理，避免大段摘录原文。

## 总览

这本书讲的是一个程序从源代码变成可运行进程的完整链路：编译器如何把源代码翻译成目标文件，链接器如何把多个目标文件和库组合成可执行文件，操作系统如何把可执行文件装载成进程，动态链接器如何在运行时解析共享库，运行库又如何在 `main` 前后完成初始化、内存管理、I/O、系统调用封装和 C++ 全局对象处理。

整本书的主线可以压缩成一句话：程序不是从 `main` 开始的，也不是编译完就结束的；真正的执行路径跨越了编译、汇编、链接、装载、动态链接、运行库初始化、系统调用和进程内存管理。

最应该抓住的重点有四组：

- 文件视角：源文件、目标文件、静态库、共享库、可执行文件，本质上都是不同阶段的二进制组织形式。
- 地址视角：编译期地址、链接期地址、装载地址、运行时虚拟地址，需要通过重定位、符号解析、页映射、PIC、PLT/GOT 等机制串起来。
- 符号视角：函数和变量最终以符号形式成为模块之间的接口；强弱符号、符号修饰、导入导出、动态符号表决定了链接行为。
- 运行视角：进程栈、堆、运行库、线程局部存储、系统调用共同组成了用户程序真正依赖的执行环境。

## 章节地图

- 第 1 部分 简介：第 1 章，从操作系统、内存、线程等基础出发，建立后续链接/装载知识的底座。
- 第 2 部分 静态链接：第 2-5 章，讲编译链接过程、目标文件、ELF、静态链接、Windows PE/COFF。
- 第 3 部分 装载与动态链接：第 6-9 章，讲进程装载、动态链接、Linux 共享库组织、Windows DLL。
- 第 4 部分 库与运行库：第 10-13 章，讲内存布局、栈/堆、CRT、系统调用、Mini CRT 实现。
- 附录：字节序、ELF 常见段、常用工具命令参考。

## 第 1 章 温故而知新

### 本章讲什么

本章从 `Hello World` 出发，重新建立程序运行所依赖的基础模型：硬件、操作系统、CPU、内存、I/O、进程、线程、虚拟内存。它不是单纯复习操作系统，而是在为后文解释“为什么需要链接、装载和运行库”铺路。

### 重点

- 程序执行不是一条孤立的机器指令流，而是运行在操作系统管理的进程环境中。
- CPU、内存、磁盘、外设之间速度差异巨大，操作系统需要调度 CPU、管理内存、抽象设备。
- 虚拟内存解决了进程隔离、地址统一、按需装入、内存扩展等问题。
- 线程共享进程资源，但拥有自己的执行流和栈；这带来性能，也带来同步和线程安全问题。

### 关键概念

- 进程：资源分配单位，拥有独立虚拟地址空间。
- 线程：执行调度单位，共享进程地址空间，拥有自己的寄存器上下文和栈。
- 分段：按逻辑意义划分地址空间，例如代码段、数据段、堆、栈。
- 分页：按固定大小页进行虚拟地址到物理地址映射，是现代虚拟内存的核心。
- 上下文切换：保存当前线程/进程的寄存器状态，恢复另一个执行流的状态。

### 细节整理

- `Hello World` 背后有编译、链接、装载、运行库初始化、系统调用输出等多个阶段。
- 操作系统不只是“让程序跑起来”，还要协调 CPU 时间片、内存保护、设备访问和文件系统。
- 虚拟地址空间使每个进程都像独占一大片连续内存，真实物理内存由页表映射完成。
- 分页让系统可以只在需要时把页面装入物理内存，即按需分页。
- 线程共享全局变量、堆、打开文件等资源；局部变量通常在线程自己的栈上。
- 线程安全问题来自共享状态的并发访问，典型手段包括锁、原子操作、条件变量、线程局部存储。

### 易错点

- 不要把“程序文件”与“运行中的进程”混为一谈。前者是磁盘上的二进制文件，后者是操作系统创建的运行实体。
- 不要把虚拟地址直接理解成物理地址。用户程序看到的地址通常是虚拟地址。
- 多线程不等于多个进程。线程共享地址空间，进程之间默认隔离。

### 实践抓手

- 用 `gcc -v hello.c` 或 `clang -### hello.c` 观察编译驱动实际调用的阶段。
- 在 Linux 上用 `cat /proc/<pid>/maps` 看进程虚拟地址空间布局。
- 用调试器观察 `main` 之前的调用栈，理解入口函数和运行库初始化。

## 第 2 章 编译和链接

### 本章讲什么

本章拆开从源代码到可执行文件的流程：预处理、编译、汇编、链接。它解释了编译器前端/后端大致做什么，也说明链接器为什么独立存在。

### 重点

- 编译驱动命令看似一步完成，内部其实分为多个阶段。
- 预处理处理宏、条件编译、头文件展开。
- 编译把源代码变成汇编，内部包含词法分析、语法分析、语义分析、中间表示、优化和目标代码生成。
- 汇编把汇编代码变成目标文件。
- 链接把多个目标文件和库组合起来，解决符号引用和地址重定位。

### 关键概念

- Translation Unit：预处理后的单个源文件，是编译器处理的基本单位。
- Symbol：模块之间引用函数、变量的名字，是链接器的接口。
- Relocation：目标文件中的地址尚未最终确定，链接器需要修正这些地址。
- Static Linking：链接期把目标文件和静态库内容合并成一个可执行文件。

### 细节整理

- 预编译输出通常可用 `gcc -E` 查看，它展开头文件和宏，但不会生成机器码。
- 编译输出可用 `gcc -S` 查看，它生成汇编文件。
- 汇编输出可用 `gcc -c` 查看，它生成 `.o` 目标文件。
- 链接阶段处理未定义符号、合并段、分配地址、执行重定位、加入启动代码和库代码。
- 编译器只看单个编译单元，链接器负责跨模块拼装。
- C/C++ 的声明与定义差异在链接阶段很重要：声明只告诉编译器符号存在，定义才真正提供存储或实现。

### 易错点

- 头文件不是被“链接”的，而是在预处理阶段被文本展开进源文件。
- 编译成功不代表链接成功。函数声明存在但没有定义，常见结果是链接时报 undefined reference/unresolved external symbol。
- 链接器不理解 C++ 语法级语义，它主要处理目标文件、段、符号和重定位。

### 实践抓手

- 分别执行 `gcc -E`、`gcc -S`、`gcc -c`、`gcc`，保存每个阶段产物。
- 用 `nm` 查看 `.o` 里的符号，用 `objdump -r` 查看重定位项。
- 故意只声明不定义一个函数，观察编译和链接报错的区别。

## 第 3 章 目标文件里有什么

### 本章讲什么

本章进入目标文件内部，重点围绕 ELF 格式解释代码段、数据段、BSS 段、段表、重定位表、字符串表、符号表、调试信息等结构。

### 重点

- 目标文件不是一坨机器码，而是由多个段和元数据表组成。
- ELF 文件头描述整个文件的基本属性和关键表位置。
- 段表描述每个 section 的名字、类型、偏移、大小、地址、对齐等信息。
- 符号表是链接的核心接口，函数和变量都以符号形式参与解析。
- 重定位表记录哪些位置需要链接器修正。

### 关键概念

- `.text`：代码段，保存机器指令。
- `.data`：已初始化的全局变量和静态变量。
- `.bss`：未初始化或初始化为 0 的全局/静态变量，文件中通常不占实际内容，只记录大小。
- `.rodata`：只读数据，如字符串常量、只读常量表。
- `.symtab`：符号表。
- `.strtab`：字符串表，用于保存符号名、段名等字符串。
- `.rel.*` / `.rela.*`：重定位表。

### 细节整理

- BSS 的设计节省磁盘空间：未初始化数据不需要把一堆 0 写进目标文件。
- ELF 文件头中会记录魔数、机器架构、字长、字节序、入口地址、段表偏移等信息。
- 段名通常不是直接放在段表项里，而是通过字符串表偏移引用。
- 符号表项包含符号名、地址/偏移、大小、绑定属性、类型、所在段等。
- C++ 函数重载需要符号修饰，因为链接器层面只按符号名区分函数。
- `extern "C"` 的意义是告诉 C++ 编译器按 C 方式导出/引用符号，避免 C++ 名字修饰影响链接。
- 强符号与弱符号影响重复定义时的选择：函数和初始化全局变量通常是强符号，弱符号可被强符号覆盖。
- 调试信息一般放在专门 section 中，调试版本目标文件会更大。

### 易错点

- section 与 segment 不完全相同。section 更偏链接视图，segment 更偏装载视图。
- `.bss` 不等于不存在，它在运行时仍然占内存，只是文件中不保存实际 0 数据。
- 符号的“值”在目标文件中常常不是最终运行地址，而是段内偏移或待链接地址。

### 实践抓手

- 用 `readelf -h` 看 ELF 文件头。
- 用 `readelf -S` 看段表。
- 用 `readelf -s` 或 `nm` 看符号表。
- 用 `objdump -s -j .data` 查看数据段内容。
- 修改一个全局变量是否初始化，观察它落在 `.data` 还是 `.bss`。

## 第 4 章 静态链接

### 本章讲什么

本章讲链接器如何把多个目标文件合并成一个可执行文件：空间与地址分配、符号解析、重定位、COMMON 块、C++ 特性、静态库链接、链接脚本等。

### 重点

- 静态链接的核心是两件事：地址与空间分配，符号解析与重定位。
- 链接器会把相似段合并，例如多个目标文件的 `.text` 合并为输出文件的代码段。
- 符号解析决定每个引用最终指向哪个定义。
- 重定位把目标文件里暂时未知或不准确的地址修正成最终地址。
- 静态库是目标文件的集合，链接器通常只抽取被需要的成员。

### 关键概念

- VMA：Virtual Memory Address，运行时虚拟地址。
- LMA：Load Memory Address，装载地址，在普通系统上常与 VMA 接近，在嵌入式场景会更明显区分。
- COMMON：早期 C 语言未初始化全局变量的一种处理方式，链接器会为其分配空间。
- Linker Script：控制输出文件布局、段地址、入口符号等的脚本。
- ABI：应用二进制接口，规定调用约定、对象布局、符号修饰、异常处理等二进制兼容规则。

### 细节整理

- 链接器先统计各输入段大小和对齐要求，再为输出段分配地址。
- 相似段合并减少碎片，也让同类内容集中，便于装载和权限控制。
- 符号解析需要处理全局符号、局部符号、强符号、弱符号、未定义符号。
- 重定位项会指明需要修正的位置、引用的符号、重定位类型和附加值。
- 指令修正方式依赖 CPU 架构，例如绝对地址、相对地址、PC-relative 寻址的处理不同。
- C++ 模板、内联函数、虚函数表、全局构造析构都会引入链接层面的复杂性。
- 重复代码消除依赖编译器和链接器协作，把相同模板实例或内联函数弱符号合并。
- 全局构造函数不是 `main` 里显式调用的，而是由运行库和链接器生成的初始化段/表共同触发。
- 链接脚本可以控制段顺序、地址、入口点，在裸机、内核、嵌入式程序中尤其关键。

### 易错点

- 静态库的链接顺序会影响解析结果，尤其在 GNU ld 中常见。
- “链接了静态库”不代表整个库都进入可执行文件，通常只选取需要的目标文件成员。
- C++ ABI 不统一会导致不同编译器/版本之间二进制不兼容。

### 实践抓手

- 用 `ar` 创建静态库，再用 `nm` 看库成员符号。
- 调换链接命令中目标文件和库的顺序，观察 undefined reference 是否出现。
- 写一个简单 linker script，指定 `.text` 的起始地址，观察输出文件变化。

## 第 5 章 Windows PE/COFF

### 本章讲什么

本章把视角切到 Windows 平台，介绍 COFF 与 PE 文件格式，以及 PE 的数据目录、符号表、调试信息、链接指示信息等。

### 重点

- Windows 可执行文件和 DLL 使用 PE/COFF 格式。
- PE 可以看作 COFF 的扩展，带有 DOS 头、PE 头、可选头、节表和数据目录。
- PE 的数据目录是理解导入表、导出表、资源、重定位、TLS 等结构的入口。
- Windows 下也有符号表和调试信息，但实际调试信息常放在 PDB 文件中。

### 关键概念

- PE：Portable Executable，Windows 可执行文件格式。
- COFF：Common Object File Format，目标文件格式基础。
- RVA：Relative Virtual Address，相对于模块装载基址的虚拟地址。
- Data Directory：PE 可选头中的目录表，指向导入、导出、资源、重定位等结构。
- PDB：Program Database，MSVC 常用调试信息文件。

### 细节整理

- PE 文件开头保留 DOS 头，随后通过偏移找到真正的 PE 头。
- 节表类似 ELF section 表，描述 `.text`、`.data`、`.rdata`、`.bss`、`.idata`、`.edata` 等节。
- 导入表记录程序依赖哪些 DLL 和哪些导入符号。
- 导出表记录 DLL 对外提供哪些函数或变量。
- 重定位信息用于模块没有装载到首选基址时修正地址。
- 链接指示信息可由编译器写入目标文件，影响链接器行为，例如默认库依赖。

### 易错点

- PE 中“可选头”对可执行文件并不是真的可选，它包含装载必需的信息。
- RVA 不是文件偏移，需要通过节表转换。
- PDB 与 PE/OBJ 是分离关系，发布程序时常去掉 PDB 但保留可执行文件。

### 实践抓手

- 用 `dumpbin /headers` 查看 PE 头和节表。
- 用 `dumpbin /imports` 查看导入表。
- 用 `dumpbin /exports` 查看 DLL 导出表。
- 对照 ELF 的 `readelf`，比较两个平台文件格式的共同点和差异。

## 第 6 章 可执行文件的装载与进程

### 本章讲什么

本章讲可执行文件如何从磁盘文件变成进程地址空间中的映射：虚拟地址空间、覆盖装入、页映射、进程建立、页错误、堆栈布局、ELF 装载、PE 装载。

### 重点

- 装载不是把整个文件一次性读入内存，而是把文件映射到进程虚拟地址空间。
- 现代系统主要依靠页映射和按需分页完成装载。
- ELF 的链接视图以 section 为主，执行视图以 segment 为主。
- 进程启动时，栈上会放置参数、环境变量和辅助信息。
- 装载器创建进程地址空间、建立映射、设置入口地址，然后把控制权交给入口代码。

### 关键概念

- Virtual Address Space：每个进程看到的独立虚拟地址空间。
- Page Fault：访问尚未映射或尚未调入的页面时触发的异常，由操作系统处理。
- Program Header：ELF 中描述如何装载 segment 的表。
- Segment：执行视图中的装载单元，例如可读可执行代码段、可读写数据段。
- Stack Initialization：进程初始栈包含 `argc`、`argv`、环境变量、auxiliary vector 等。

### 细节整理

- 覆盖装入是早期内存不足时的技术，程序员手动把不会同时使用的代码覆盖到同一内存区域。
- 页映射把文件内容和虚拟页联系起来，真正访问时才触发磁盘读入。
- 进程创建通常包括分配进程控制块、创建地址空间、映射可执行文件、设置寄存器和栈。
- ELF 的 section 用于链接，segment 用于装载；多个 section 可以合并到同一个 segment。
- 堆向高地址增长，栈通常向低地址增长，中间是共享库映射、mmap 区等。
- 段对齐是为了满足页映射和权限设置要求，例如代码页只读可执行，数据页可读写。
- Linux 内核装载 ELF 时会读取 ELF 头和 program header，映射 PT_LOAD 段，并启动解释器或入口点。
- 动态链接程序的真正入口通常先进入动态链接器，再进入程序入口函数。

### 易错点

- 可执行文件的入口点通常不是 `main`，而是运行库入口或动态链接器相关入口。
- 文件偏移、虚拟地址、物理地址是三个不同概念。
- 进程地址空间“看起来连续”，不代表物理内存连续。

### 实践抓手

- 用 `readelf -l a.out` 查看 program header。
- 用 `/proc/<pid>/maps` 对照可执行文件和共享库映射。
- 在 GDB 中从 `_start` 开始单步，观察进入 `main` 前的调用路径。

## 第 7 章 动态链接

### 本章讲什么

本章是全书核心之一，讲动态链接为什么存在、共享对象如何被装载、地址无关代码如何工作、PLT/GOT 如何支持延迟绑定，以及动态链接器的自举、符号解析、重定位和运行时装载接口。

### 重点

- 动态链接把库代码从可执行文件中分离出来，在装载或运行时解析。
- 共享库节省磁盘和内存，便于更新，但引入版本、符号冲突和装载时开销。
- 地址无关代码让共享对象可以装载到不同地址而无需大规模修改代码段。
- GOT 保存运行时地址，PLT 支持函数调用的延迟绑定。
- 动态链接器本身也需要先完成自举，然后才能装载和重定位其他共享对象。

### 关键概念

- Shared Object：Linux 下的共享对象，通常 `.so`。
- PIC：Position Independent Code，地址无关代码。
- GOT：Global Offset Table，全局偏移表，保存全局变量和外部符号运行时地址。
- PLT：Procedure Linkage Table，过程链接表，用于外部函数调用跳转和延迟绑定。
- Lazy Binding：首次调用外部函数时才解析真实地址。
- `.interp`：记录动态链接器路径。
- `.dynamic`：记录动态链接所需元信息。
- `.dynsym`：动态符号表。
- `dlopen/dlsym/dlclose/dlerror`：运行时显式装载和查询动态库的接口。

### 细节整理

- 固定装载地址会导致共享库地址冲突；装载时重定位会修改代码/数据，影响共享和启动性能。
- PIC 的核心思想是避免在代码段写死绝对地址，通过相对寻址和表间接访问运行时地址。
- 对模块内部函数调用，可以使用相对跳转，不依赖绝对装载地址。
- 对模块外部函数调用，通常经由 PLT；第一次调用触发动态链接器解析，随后 PLT/GOT 记录结果。
- 对全局变量访问，通常通过 GOT 获取地址，因为变量可能在其他模块中。
- 数据段地址无关比代码段更复杂，因为数据中可能含有指针，需要动态重定位。
- 动态链接器要读取 `.dynamic`，找到字符串表、符号表、重定位表、依赖库列表等。
- 装载共享对象时要处理依赖关系，并把所有模块加入全局符号搜索范围。
- 全局符号介入意味着后装入/先装入模块中的同名全局符号可能影响绑定结果，这既是特性也是风险。
- 显式运行时链接适合插件系统、可选功能、按需加载模块。

### 易错点

- 动态链接不是完全没有链接；编译/链接阶段仍会生成动态链接所需的符号和重定位信息。
- PIC 与 PIE 不同：PIC 常用于共享库，PIE 是位置无关可执行文件。
- 延迟绑定只针对函数调用常见，变量地址通常需要更早处理。
- `dlsym` 查到的是符号地址，函数指针类型转换要小心平台差异。

### 实践抓手

- 用 `ldd` 查看可执行文件依赖的共享库。
- 用 `readelf -d` 查看 `.dynamic` 信息。
- 用 `readelf -r` 查看动态重定位。
- 用 `objdump -d -j .plt` 查看 PLT。
- 写一个 `.so`，用 `dlopen` 和 `dlsym` 手动调用函数。

## 第 8 章 Linux 共享库的组织

### 本章讲什么

本章从工程管理角度讲 Linux 共享库：版本兼容、命名规则、SO-NAME、符号版本、库搜索路径、环境变量、共享库创建和安装。

### 重点

- 共享库不仅是技术机制，也是系统级部署和兼容性问题。
- SO-NAME 用来标识二进制兼容版本，而不是单纯文件名。
- 符号版本可以让同一个共享库同时提供多个版本的符号。
- 动态链接器按一定规则搜索共享库，路径配置错误会导致运行时加载失败。
- 共享库发布需要考虑 ABI 兼容、符号可见性、安装位置和缓存更新。

### 关键概念

- SO-NAME：共享库的逻辑名字，例如 `libfoo.so.1`。
- Real Name：真实库文件名，常包含完整版本号，如 `libfoo.so.1.2.3`。
- Link Name：链接时使用的名字，如 `libfoo.so`。
- `LD_LIBRARY_PATH`：运行时库搜索路径环境变量。
- `ldconfig`：更新共享库缓存和符号链接的工具。
- Symbol Versioning：符号版本机制，用于 ABI 演进。

### 细节整理

- 源码兼容不等于二进制兼容；结构体布局、函数签名、调用约定、符号名变化都可能破坏 ABI。
- 主版本号通常表示 ABI 兼容边界，破坏 ABI 时需要提升主版本。
- Linux 共享库常通过一组符号链接维护：`libfoo.so -> libfoo.so.1 -> libfoo.so.1.2.3`。
- 程序运行时依赖的是 ELF 动态段中的 `NEEDED` 项和 SO-NAME。
- 搜索路径通常包括 RPATH/RUNPATH、`LD_LIBRARY_PATH`、系统缓存、默认目录等。
- `LD_PRELOAD` 可以预先加载库并拦截符号，常用于调试、hook、兼容层。
- 创建共享库时要使用 `-fPIC` 和 `-shared`，安装后可能需要运行 `ldconfig`。
- 构造/析构函数可以在共享库加载/卸载时执行，但应避免复杂副作用。

### 易错点

- 不要在生产环境随意依赖 `LD_LIBRARY_PATH`，它容易造成不可控的库覆盖。
- 修改导出函数签名即使源码能重新编译，也可能破坏已有二进制程序。
- `strip` 清除符号信息可以减小体积，但调试和诊断会受影响。

### 实践抓手

- 用 `gcc -fPIC -shared` 构建共享库。
- 用 `readelf -d libfoo.so` 查看 `SONAME` 和 `NEEDED`。
- 用 `ldconfig -p` 查看系统库缓存。
- 用 `LD_PRELOAD` 写一个简单函数拦截实验。

## 第 9 章 Windows 下的动态链接

### 本章讲什么

本章讲 Windows DLL 的装载、使用、导入导出表、导入函数调用、基址重定位、序号导出、绑定导入、C++ 与 DLL 兼容，以及 DLL Hell 问题。

### 重点

- DLL 是 Windows 动态链接的核心载体。
- DLL 可隐式链接，也可通过 `LoadLibrary/GetProcAddress/FreeLibrary` 显式运行时链接。
- PE 导入表和导出表支撑 DLL 函数解析。
- DLL 首选基址冲突时需要重定基，影响装载性能和共享。
- C++ 跨 DLL 边界会受到 ABI、运行库、异常、对象所有权等限制。
- DLL Hell 本质是版本冲突、搜索路径混乱和共享组件替换导致的兼容性灾难。

### 关键概念

- Import Table：记录程序从哪些 DLL 导入哪些函数。
- Export Table：记录 DLL 向外导出的符号或序号。
- Import Address Table：导入地址表，装载器填入真实函数地址。
- Ordinal：按序号导出/导入，可减少名字查找但可读性和兼容性较差。
- Base Relocation：模块未装载到首选基址时进行地址修正。
- DEF 文件：模块定义文件，用于控制导出符号等。

### 细节整理

- 隐式链接通常需要 `.lib` 导入库，编译链接时确定依赖，运行时由装载器加载 DLL。
- 显式链接适合插件、可选组件和延迟加载。
- 导入库不一定包含函数实现，它可能只是告诉链接器导入符号来自哪个 DLL。
- IAT 中的函数指针在装载时被填好，调用导入函数时实际通过 IAT 间接跳转。
- 导出重定向可让一个 DLL 的导出函数转发到另一个 DLL。
- 重定基会修改需要绝对地址的地方，可能导致页面无法共享。
- 绑定导入把 DLL 函数地址提前写入程序以优化装载，但 DLL 更新后可能失效。
- C++ 类、STL 对象、异常、内存分配跨 DLL 边界要特别谨慎，最好导出 C 接口或稳定 ABI。

### 易错点

- `.lib` 既可能是静态库，也可能是导入库，需要看内容和链接方式。
- DLL 导出 C++ 函数名会有名字修饰，不同编译器之间不稳定。
- 在一个 DLL 中分配内存、另一个 DLL 中释放，如果运行库实例不同，可能出问题。

### 实践抓手

- 用 `dumpbin /imports app.exe` 查看导入表。
- 用 `dumpbin /exports foo.dll` 查看导出表。
- 写一个 DLL，分别用隐式链接和 `LoadLibrary` 调用。
- 用 DEF 文件控制导出名，比较 `extern "C" __declspec(dllexport)` 的效果。

## 第 10 章 内存

### 本章讲什么

本章讲进程内存布局、栈、调用惯例、函数返回值、堆管理，以及 Linux/Windows 下堆的实现和常见堆分配算法。

### 重点

- 程序运行时内存通常分为代码段、数据段、BSS、堆、栈、共享库映射、内核映射等区域。
- 栈用于函数调用、局部变量、参数传递、返回地址和寄存器保存。
- 调用惯例规定参数如何传递、栈由谁清理、返回值放在哪里、寄存器如何保存。
- 堆用于动态内存分配，运行库在系统调用之上实现用户态分配器。
- 堆分配器需要在速度、碎片、空间利用率和线程安全之间权衡。

### 关键概念

- Stack Frame：一次函数调用对应的栈帧，包含返回地址、旧帧指针、局部变量等。
- Calling Convention：调用惯例，如 cdecl、stdcall、fastcall、thiscall、x64 ABI 等。
- Heap：动态分配区域，由 `malloc/free` 或 `new/delete` 管理。
- Fragmentation：内存碎片，包括内部碎片和外部碎片。
- Free List：空闲链表，堆分配器常用结构。

### 细节整理

- 栈增长方向与架构/系统相关，x86/x64 常见为向低地址增长。
- 函数调用通常包含参数入栈/寄存器传参、保存返回地址、建立栈帧、执行函数、恢复栈帧、返回。
- 返回值可能通过寄存器返回，也可能由调用方传入隐藏指针接收大对象返回值。
- cdecl 由调用方清理栈，支持可变参数；stdcall 常由被调用方清理栈。
- `malloc` 通常不是每次都直接调用系统调用，而是维护用户态堆，批量向操作系统申请内存。
- Linux 下经典堆扩展可通过 `brk/sbrk`，大块分配也可能使用 `mmap`。
- Windows 进程堆由系统提供 Heap API，CRT 的 `malloc` 可建立在其上。
- 常见分配算法包括空闲链表、位图、伙伴系统、slab/对象池等。

### 易错点

- 栈变量生命周期随函数返回结束，不应返回局部变量地址。
- 堆内存泄漏不是“内存还在变量里”，而是程序失去释放它的路径。
- `new/delete` 与 `malloc/free` 不可混用；前者还涉及构造/析构。
- 调用惯例不匹配会导致栈破坏或参数解释错误。

### 实践抓手

- 在调试器里查看函数调用时栈指针/帧指针变化。
- 写不同调用惯例的函数，观察汇编和符号名差异。
- 用工具观察 `malloc` 小块和大块分配是否触发不同系统接口。

## 第 11 章 运行库

### 本章讲什么

本章回答“程序从 main 开始吗”：运行库入口函数如何初始化环境、调用全局构造、设置 I/O、多线程支持、TLS、最后调用 `main` 并处理退出。还比较 C 标准库、glibc、MSVC CRT，并以 `fread` 为例分析运行库函数实现。

### 重点

- `main` 只是用户代码入口，不是进程最初执行的入口。
- 运行库负责在 `main` 前初始化堆、I/O、环境变量、全局对象、线程支持等。
- C 标准库定义接口，具体运行库实现依赖平台。
- 多线程让运行库必须处理全局状态、errno、I/O 缓冲、锁和线程局部数据。
- C++ 全局构造/析构依赖链接器生成的初始化/终止表和运行库遍历调用。

### 关键概念

- `_start` / entry point：程序真正入口，通常由启动文件和运行库提供。
- CRT：C Runtime，C/C++ 程序运行时基础库。
- `atexit`：注册程序退出时调用的函数。
- TLS：Thread Local Storage，线程局部存储。
- Buffering：I/O 缓冲，减少系统调用次数。

### 细节整理

- 入口函数通常解析初始栈，准备 `argc/argv/envp`，初始化运行库，再调用 `main`。
- `main` 返回后，运行库负责调用 `exit` 流程、执行 `atexit` 函数、调用全局析构、刷新 I/O 缓冲。
- glibc 和 MSVC CRT 在入口函数、初始化表、线程支持、I/O 实现上有平台差异。
- `errno` 在多线程下不能是一个简单全局变量，通常通过 TLS 实现每线程一份。
- 全局构造函数需要在 `main` 前调用，析构函数需要在程序退出时调用。
- `fread` 不是简单系统调用封装，它涉及参数检查、锁、缓冲区、文本/二进制换行转换、底层 `_read/read`。
- 文本模式下的换行转换是跨平台 I/O 差异的典型例子，Windows 中 `\r\n` 与 `\n` 会发生转换。

### 易错点

- `printf`、`malloc`、`fread` 等不是内核直接提供的系统调用，它们是运行库函数。
- 多线程 CRT 与单线程 CRT 的差异可能影响全局状态和库函数安全性。
- 全局对象构造顺序跨翻译单元不可靠，容易出现初始化顺序问题。

### 实践抓手

- 用 `gcc -nostdlib` 尝试链接最小程序，观察缺少入口和运行库时的问题。
- 在 GDB 中断在 `_start`、`__libc_start_main`、`main`，观察调用链。
- 写全局对象打印构造/析构，观察执行时机。
- 对比文本模式和二进制模式读取文件的行为。

## 第 12 章 系统调用与 API

### 本章讲什么

本章讲用户程序如何请求内核服务：系统调用概念、Linux 系统调用机制、特权级和中断、传统 `int 0x80` 与新型机制，以及 Windows API 与子系统模型。

### 重点

- 用户态程序不能直接执行内核特权操作，必须通过系统调用进入内核。
- 系统调用是用户态与内核态的边界，涉及特权级切换和上下文保存。
- 经典 Linux 可通过软中断 `int 0x80` 进入内核，新机制使用更高效的专用指令。
- API 不等于系统调用。运行库和操作系统 API 可能在系统调用之上再封装多层。
- Windows API 是面向应用的稳定接口，内部可能经由子系统、NTDLL、内核服务等层次。

### 关键概念

- User Mode / Kernel Mode：用户态和内核态。
- Privilege Level：特权级，限制普通程序执行敏感指令。
- Interrupt / Trap：从用户态进入内核的机制之一。
- System Call Number：系统调用号，用于区分请求的内核服务。
- Win32 API：Windows 面向普通应用的 API 层。
- Native API：更底层的 NT 接口，通常由 `ntdll.dll` 暴露。

### 细节整理

- 文件读写、进程创建、内存映射、网络 I/O 最终通常需要内核参与。
- 系统调用有成本：用户态/内核态切换、参数检查、上下文处理都比普通函数调用重。
- 传统 `int 0x80` 使用中断门进入内核，参数通过寄存器传递。
- 新型机制如 `sysenter/syscall` 减少进入内核的开销，但需要更严格的约定。
- C 标准库函数可能合并、缓冲或转换请求，不一定一一对应系统调用。
- Windows API 提供更高层抽象，比如 `ReadFile` 不是简单等价于某条机器级系统调用。
- 子系统模型使 Windows 能支持不同应用环境，Win32 子系统是最常见的一层。

### 易错点

- API、运行库函数、系统调用、内核函数不是同一层。
- 系统调用号和参数约定是平台相关的，不同架构和内核版本可能不同。
- 频繁小 I/O 如果每次都触发系统调用，会有明显性能开销，所以缓冲很重要。

### 实践抓手

- 在 Linux 用 `strace ./a.out` 观察程序实际系统调用。
- 对比 `fread` 和 `read` 的调用次数差异。
- 在 Windows 用 Process Monitor 观察文件/注册表/API 行为。

## 第 13 章 运行库实现

### 本章讲什么

本章通过实现 Mini CRT，把前面关于入口函数、堆、I/O、字符串、格式化输出、C++ `new/delete`、全局构造析构、`atexit`、stream/string 等知识串起来。它是全书的实践收束。

### 重点

- 运行库不是神秘黑盒，可以用一组基础系统调用和约定实现一个最小版本。
- Mini CRT 的核心模块包括入口函数、堆分配、文件 I/O、字符串处理、格式化输出。
- C++ 运行库还要支持 `new/delete`、全局构造析构、`atexit`、基础 stream/string。
- 实现最小运行库能反向理解标准库、链接器脚本、启动文件和系统调用边界。

### 关键概念

- Mini CRT：用于教学的最小 C/C++ 运行库实现。
- Heap Allocator：在系统申请的大块内存上实现 `malloc/free`。
- File Descriptor / Handle：文件抽象，Linux 与 Windows 命名和接口不同。
- Formatter：格式化字符串处理，如 `printf` 家族的核心。
- Placement / Operator new：C++ 动态对象创建背后的内存分配接口。

### 细节整理

- 入口函数需要自己准备参数、初始化堆和 I/O，再调用用户 `main`。
- 堆实现通常需要维护内存块头部，记录大小、空闲状态、链表关系。
- 简单分配器可以从空闲链表中寻找合适块，必要时分裂；释放时尝试合并相邻空闲块。
- 文件操作要屏蔽 Linux 文件描述符和 Windows HANDLE 的差异。
- 字符串函数如 `strlen/strcmp/strcpy` 看似简单，但边界和性能细节很多。
- 格式化字符串需要解析 `%d/%s/%c/%x` 等格式，并把不同类型转换为文本输出。
- `new` 通常调用 `operator new` 分配内存，再调用构造函数；`delete` 先析构再释放。
- C++ 全局构造需要链接器收集构造函数指针，入口函数遍历调用。
- `atexit` 维护退出函数列表，程序退出时按规则调用。

### 易错点

- 最小 CRT 可以教学，但不能替代工业级运行库；线程安全、异常、locale、宽字符、安全检查都复杂得多。
- `malloc` 只负责字节内存，`new` 还负责对象构造。
- 格式化字符串实现要警惕缓冲区溢出和类型不匹配。

### 实践抓手

## 全书重点串联

### 1. 从源代码到进程的路径

1. 源代码经过预处理，形成编译单元。
2. 编译器生成汇编，汇编器生成目标文件。
3. 目标文件包含 section、符号表、重定位表等信息。
4. 链接器合并目标文件和库，解析符号并修正地址。
5. 可执行文件在装载时映射到虚拟地址空间。
6. 动态链接器装载共享库，处理动态符号和重定位。
7. 运行库入口初始化环境，调用 `main`。
8. 程序通过运行库和系统调用访问操作系统服务。

### 2. 链接的本质

链接的本质是把多个独立编译的模块拼成一个可以执行的整体。它要解决两个问题：

- 名字问题：某个引用到底对应哪个定义，即符号解析。
- 地址问题：代码和数据最终放在哪里，所有引用地址如何修正，即地址分配与重定位。

### 3. 装载的本质

装载的本质不是复制文件，而是建立“文件内容、虚拟地址、内存页、访问权限”之间的映射关系。现代操作系统通过页映射和按需分页，让程序只在访问某页时才真正把数据调入内存。

### 4. 动态链接的本质

动态链接把库的确定时机从静态链接阶段推迟到装载期或运行期。它用动态符号表、重定位表、GOT、PLT、动态链接器等机制，在灵活性、共享性和启动/调用开销之间取平衡。

### 5. 运行库的本质

运行库把操作系统提供的粗粒度能力包装成 C/C++ 程序习惯使用的执行环境。`main` 之前和之后发生的事情，大量都由运行库负责：初始化、构造析构、堆、I/O、线程局部状态、退出清理。

## 一句话记忆

- 编译：把一个源文件翻译成目标文件。
- 链接：把多个目标文件和库拼成可执行整体。
- 重定位：把暂时未知的地址修正为最终地址。
- 装载：把可执行文件映射进进程虚拟地址空间。
- 动态链接：运行前后再解析共享库符号和地址。
- 运行库：在操作系统和用户程序之间提供 C/C++ 执行环境。
