# 12-系统调用与 API

## 这一章的核心问题

程序想读文件、写屏幕、申请内存、创建线程、发送网络数据，最终都需要操作系统帮忙。

问题是：用户程序不能随便进入内核乱操作，那它怎么请求内核服务？

答案就是系统调用。

## 用户态和内核态

现代操作系统会把 CPU 执行状态分成不同权限级别。

简单理解：

- 用户态：普通程序运行的地方，权限低。
- 内核态：操作系统内核运行的地方，权限高。

用户态不能直接操作硬件、页表、调度器等敏感资源。否则一个普通程序就能把整个系统搞崩。

## 系统调用是什么

系统调用就是用户程序向内核请求服务的正式入口。

比如：

- 读文件。
- 写文件。
- 创建进程。
- 映射内存。
- 创建线程。
- 网络收发。

用户程序通过特定指令切换到内核态，内核检查参数和权限，执行对应服务，再返回用户态。

## 系统调用和普通函数调用有什么区别

普通函数调用只是在用户态内部跳转，成本相对低。

系统调用要跨越用户态/内核态边界，涉及：

- 保存用户态上下文。
- 切换特权级。
- 进入内核入口。
- 检查系统调用号和参数。
- 执行内核逻辑。
- 返回并恢复用户态。

所以系统调用比普通函数调用重得多。

这也是为什么运行库要做缓冲，比如 `printf` 不会每个字符都系统调用一次。

## int 0x80 是什么

在早期 x86 Linux 中，用户程序可以通过软中断 `int 0x80` 进入内核。

大致流程是：

1. 把系统调用号放到指定寄存器。
2. 把参数放到约定寄存器。
3. 执行 `int 0x80`。
4. CPU 切到内核态。
5. 内核根据系统调用号分发。
6. 返回结果。

这是经典机制，但开销相对大。

## 新型系统调用机制

后来 CPU 提供了更快的指令，比如：

- `sysenter/sysexit`
- `syscall/sysret`

它们专门用于快速进入/退出内核，减少传统中断机制的开销。

但不管底层指令怎么变，本质还是用户态请求内核服务。

## API、运行库函数、系统调用的区别

这三个层次一定要分清。

### API

API 是提供给应用程序调用的接口。比如 Windows 的 `ReadFile`，POSIX 的 `read`。

### 运行库函数

运行库函数是 C/C++ 标准库或运行库提供的函数，比如 `fread`、`printf`。

它们可能在内部调用 API 或系统调用，也可能先做缓冲和转换。

### 系统调用

系统调用是进入内核的真正边界。

比如 Linux 的 `read` 最终会进入内核读取文件描述符。

关系大致是：

```text
fread -> 运行库缓冲逻辑 -> read -> 系统调用 -> 内核
```

但不是每个平台都这么简单一一对应。

## Windows API 怎么看

Windows 程序常调用 Win32 API，比如：

- `CreateFile`
- `ReadFile`
- `WriteFile`
- `CreateProcess`
- `VirtualAlloc`

这些 API 通常在 DLL 中导出，比如 `kernel32.dll`。再往下可能调用 `ntdll.dll` 中的 Native API，最后进入内核。

所以 Windows API 不是简单等于系统调用。它是更稳定、更面向应用的接口层。

## 为什么系统调用有弊端

系统调用很强大，但有成本：

- 性能成本：用户态/内核态切换慢。
- 安全检查：内核必须验证用户指针和权限。
- 接口稳定性：系统调用 ABI 要谨慎维护。
- 调试复杂度：跨越用户态和内核态。

所以高性能程序会尽量减少系统调用次数，比如批量 I/O、缓冲、异步 I/O、内存映射等。

## 本章最重要的 takeaway

用户程序不能直接支配系统资源，它必须通过 API、运行库和系统调用这些层次向操作系统请求服务。理解这条边界，你才能理解为什么 I/O 慢、为什么缓冲重要、为什么 `printf` 不是系统调用。

## 建议动手实验

Linux 下：

```bash
strace ./app
```

观察：

- 程序启动时加载了哪些文件。
- `printf` 最后触发了什么写操作。
- `malloc` 是否触发 `brk` 或 `mmap`。

Windows 下可以用 Process Monitor 观察文件、注册表和进程行为。
