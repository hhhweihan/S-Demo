## 一、这周到底在干嘛？

Week 08 表面上是在补两个同步原语，再把本月内容收个尾；但如果只把它看成“最后一周把零碎功能补上”，会低估这一周真正的价值。

这一周真正解决的是一个非常关键的问题：

> 前三周学到的并发工具，能不能被重新压回一套更完整、更可解释的系统协议里。

Week 05 的重点是任务交接，Week 06 的重点是任务执行框架，Week 07 的重点是内存模型和无锁边界。到了 Week 08，问题变成了：

- 如果只用互斥锁，能不能表达读多写少场景？
- 如果只用原子计数和条件变量，等待全部任务完成是否足够清晰？
- 线程池除了能提交任务，还能不能表达暂停、恢复、收尾这些运行阶段？
- 这个月做出来的东西，到底有没有形成完整的工程闭环？

所以这一周真正做的，不是补几个 API，而是在做 Month 02 的协议收口：

```text
互斥控制
  -> mutex
  -> RWMutex

阶段同步
  -> condition_variable
  -> CountDownLatch

执行框架
  -> ThreadPool
  -> await_termination
  -> pause / resume

性能与验证
  -> stress test
  -> benchmark
  -> sanitizer 环境检查
```

如果说前几周是在逐步把并发知识点变成代码，那么 Week 08 做的就是把这些代码重新组织成一套更稳定的工程语言。

## 二、七天任务全景

### Day 50 — RWMutex：第一次把“互斥”细分成读共享和写独占

这一天下来最大的收获，不是手写出一个读写锁类，而是更明确地理解了“互斥”并不是只有一种粒度。

普通 `std::mutex` 的语义非常简单：

- 有线程进临界区，其他线程全等
- 不区分读操作和写操作

这个模型非常稳，但在读多写少场景里会明显保守。Day 50 的 `RWMutex` 之所以值得单独做，不是为了重复造轮子，而是为了把下面这件事亲手实现一遍：

> 多个只读线程彼此并不冲突，真正需要排他的只有写入路径。

这次实现还刻意做了写者优先，避免读流量一直不断时写线程被长期饿死。这个点非常值得记住，因为并发原语不只是“能用”，还必须回答公平性和饥饿问题。一个读写锁如果只顾着放开读者并发，却完全不管写者是否永远抢不到执行机会，那它在工程上就是不完整的。

通过 4 个读线程和 1 个写线程的压力测试，这一天下来真正建立起来的不是一个类，而是一条判断规则：

- 共享读可以并发
- 写入必须独占
- 公平性策略要提前想清楚

### Day 51 — CountDownLatch：把“等所有任务完成”从技巧变成原语

`CountDownLatch` 这个原语非常适合拿来做复盘，因为它把一类常见需求压得很清楚：

- 我不需要一个复杂队列
- 我也不需要返回值模型
- 我只是想等一组工作全部完成

以前遇到这种需求时，很容易直接上原子计数加条件变量，功能上当然也能做，但写法经常是一次性的。Day 51 自己实现 latch 之后，最重要的收获是：

> 阶段同步应该优先抽象成明确协议，而不是每次临时拼一个等待逻辑。

这次实现除了 `count_down()`、`wait()` 和 `wait_for()`，还补了 `count_up()`。这个改动看似超出了题面，实际上非常务实，因为它让 latch 不只是适合“预先知道任务总数”的场景，也能接回线程池这种运行期动态提交任务的系统。

这一天最大的认知提升，是开始更清楚地区分：

- 互斥原语解决的是谁能进入临界区
- 同步原语解决的是阶段什么时候推进

读写锁和 CountDownLatch 放在同一周复盘，正好能把这两个责任切得更开。

### Day 52 — 接回线程池：执行器终于具备了阶段控制能力

Week 06 写线程池时，核心任务是把提交、执行、返回值、关闭协议跑通。到了 Day 52，线程池开始补上另一个非常像“系统组件”的能力：运行阶段控制。

这一天真正做的有两件事：

1. 用 CountDownLatch 重做 `await_termination()`
2. 给线程池增加 `pause()` / `resume()`

第一件事的价值在于把“等待全部任务完成”从一个分散在原子计数和条件变量里的技巧，整理成一个单独可解释的协议。提交任务时 `count_up()`，任务完成时 `count_down()`，等待收尾时 `wait()`，这条链在语义上非常直接。

第二件事更像是一次工程化升级。一个只能不停接任务、不能暂停的线程池，其实更像 demo；而能表达暂停、恢复、等待清空的线程池，才更接近真实系统里需要的执行框架。`pause()` 的意义不是“让线程休息一下”，而是让系统具备流控和阶段切换能力。比如压测时切分阶段、平滑停机前阻断新任务、做配置切换时暂缓提交，这些都需要线程池知道自己现在处于什么状态。

所以 Day 52 的价值，不在于接口数量增加了两个，而在于线程池开始具备了“运行期治理”的语义。

### Day 53 — TSan 全面扫描：第一次认真面对工具链边界

这一天下来最有价值的，不是跑出了多少 sanitizer 报告，而是把“验证并发正确性”这件事和“当前机器工具链能做到什么”分开了。

题面要求非常清楚：

- 用 `-fsanitize=thread -g` 编译
- 跑测试
- 修复 race
- 重跑到零报告

但当前环境是 Windows + MSVC，而且机器上没有 `clang++`。这意味着在本机上无法直接完成 TSan 这一项。这里真正需要建立的工程意识是：

> 不能因为当前环境跑不了，就把验证这件事假装成已经完成；也不能因为工具链受限，就放弃记录一条可执行的后续路径。

所以这一天最后形成的不是“TSan 已过”这种不严谨结论，而是三层更准确的结论：

- 当前环境下不可执行 TSan，这是客观阻塞，不是代码结论
- 当前所有改动已经通过可执行压力测试和构建验证
- 一旦切到 Linux / WSL + clang，可以直接沿记录好的命令补跑 TSan

这个判断方式本身就是复盘价值的一部分。工程里比“工具全都有”更常见的场景，其实是“工具链有边界，但你仍然要把验证计划说清楚”。

### Day 54 — 整月 benchmark：把 Month 02 的几类能力放到同一张表上

这一天下来最关键的，不是又多拿到几个数字，而是终于能把 Month 02 的几类主要组件放到同一个性能语境里看：

- BlockingQueue
- SPSCQueue
- ThreadPool

这几类组件表面上都在处理“任务/数据交接”，但实际上服务的目标完全不同：

- BlockingQueue 重点是正确阻塞和关闭协议
- SPSCQueue 重点是在强约束场景下减少同步成本
- ThreadPool 重点是任务调度和执行治理

因此 benchmark 的真正意义，并不是得出一个“谁最强”的简单结论，而是帮助建立更准确的性能直觉：

- 在 1P1C 场景里，SPSCQueue 明显更适合追求吞吐
- BlockingQueue 的代价来自锁、条件变量和更通用的语义
- ThreadPool 的成本则更多来自任务封装、调度和同步协议，不应该拿它去和纯队列直接比高低

这一点非常重要，因为到了 Week 08，Month 02 已经不只是“写了几个组件”，而是开始知道它们分别适合什么问题、付出了哪些代价。

## 三、本周最核心的五条收获

### 1. 同步原语的价值，不在接口数量，而在责任边界清晰

Week 08 很适合把一个月的并发原语重新分类：

- `mutex` / `RWMutex` 负责互斥访问
- `condition_variable` / `CountDownLatch` 负责等待与阶段同步
- 原子和 memory order 负责可见性与顺序

一旦按这个方式去看，并发代码会比以前清楚很多。因为你不再只是“挑一个能用的工具”，而是在明确：这段逻辑到底是在保护临界区，还是在推进阶段，还是在建立跨线程观察顺序。

### 2. 线程池真正走向工程化，靠的是状态治理而不是线程数量

Week 06 写出了线程池骨架，Week 08 则把它继续往工程组件方向推了一步。最重要的不是多了几个 worker，而是线程池开始明确表达自己的运行状态：

- 正在接受任务
- 暂停接受任务
- 等待全部任务收尾
- 进入关闭流程

没有这些状态语义，线程池就只是个执行容器；有了这些语义，它才开始具备治理能力。

### 3. 等待所有任务完成，本质上是阶段同步问题

`await_termination()` 这个接口很容易被看成线程池内部细节，但这周重新做完之后会更清楚：它本质上是在解决阶段同步，而不是普通互斥。

这条判断非常重要，因为它能帮助以后更快选对工具。凡是“等一批事做完再继续”的需求，首先该想到的是 latch、barrier、条件变量谓词这种同步协议，而不是无差别往互斥锁上堆逻辑。

### 4. benchmark 的真正意义，是建立取舍感，不是赢数字

Week 08 把整月 benchmark 放到一起之后，最有价值的收获不是“哪个数字更大”，而是更能接受一个工程事实：

- 不同组件面对的是不同问题
- 同一类性能指标不能脱离语义直接比较
- 更高吞吐通常来自更强约束和更窄适用范围

这套取舍感，比单一性能数字更重要。因为工程里真正难的不是跑一个 benchmark，而是知道什么时候该为性能付复杂度，什么时候不该。

### 5. 复盘不是重抄结果，而是把验证边界和后续路径写清楚

Day 53 的 TSan 环境检查其实很能说明复盘的意义。复盘不是把“做了什么”重新列一遍，而是把下面三件事写清楚：

- 什么已经被验证
- 什么当前无法验证
- 后续要用什么条件补齐验证

只有这样，复盘才不是形式化打卡，而是真正能接给下一次工程动作的记录。

## 四、本周对整个月的收口作用

如果说 Week 05 到 Week 07 分别在回答：

- 任务怎么安全交接
- 任务怎么组织执行
- 锁去掉之后哪些问题会暴露

那么 Week 08 回答的是最后一个总问题：

> 这些能力能不能被重新放回一套更完整的并发工程框架里。

答案是可以，而且这次收口已经很清楚：

- 任务交接靠 BlockingQueue / SPSCQueue
- 执行框架靠 ThreadPool
- 细粒度互斥靠 RWMutex
- 阶段同步靠 CountDownLatch 和条件变量
- 正确性验证靠压力测试、构建检查和后续 sanitizer 计划

到了这里，Month 02 的价值已经不只是“学过了并发基础”，而是确实攒下了一套可以继续演进的组件骨架和分析框架。

## 五、下个月进入模板泛型前，最该保留的东西

Month 03 会进入模板与泛型，但我觉得最应该带过去的，不是某个并发技巧，而是这个月形成的分析习惯：

- 先分清组件责任
- 再分清同步责任

这套顺序非常重要。因为模板一旦学深，很容易只盯着技巧和表达力；但真正有价值的模板抽象，最终还是服务于已经清楚的组件边界。这个月线程池、队列、锁、latch 的设计过程，正好给下个月打了一个很好的工程底座。

Week 08 作为收尾周，真正完成的不是“把最后几天打卡补齐”，而是把 Month 02 从零散练习收成了一套更稳定的并发工程认知。
