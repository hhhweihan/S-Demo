## 一、这周到底在干嘛？

这一周看起来像是在“手写智能指针”，但如果只把它理解成接口练习，其实会学偏。

Week 3 真正做的事情，是把 C++ 中最核心的一类问题重新拆清楚：

> 资源到底由谁拥有，什么时候释放，多个对象共享时怎么记账，观察者又该怎么存在。

所以这一周的主线，并不是三个类名，而是一条完整的所有权演化路径：

```text
unique_ptr
  -> 独占所有权

shared_ptr
  -> 共享所有权
  -> 控制块 + use_count

weak_ptr
  -> 非拥有型观察者
  -> weak_count + lock()

enable_shared_from_this
  -> 对象内部安全回到原控制块
```

再往后两天：

- Day 19 把教学版和 libc++ 工业实现对上
- Day 20 把“shared_ptr 是否线程安全”这个高频误区拆开说清楚

这一周的关键，不是多记了几个接口，而是开始真正理解**生命周期管理的结构化设计**。

## 二、七天任务全景

### Day 15 — 手写 unique_ptr

这一天下来最重要的结论很简单：

`unique_ptr` 的本质不是“自动 delete 的指针”，而是“独占所有权对象”。

我重点理清了：

- 为什么必须禁拷贝
- 为什么 move 后源对象必须置空
- `get()`、`release()`、`reset()` 名字相近但语义完全不同

这里真正建立的是一个很重要的资源管理直觉：

> 能在类型系统里禁止的错误，就不要留到运行时再赌不会发生。

例如拷贝构造直接 `= delete`，比“靠约定不拷贝”强得多。

---

### Day 16 — 手写 shared_ptr

从这一天开始，智能指针不再只是一个 `T*` 包装壳，而是正式进入“控制块模型”。

核心理解有两个：

1. 多个 `shared_ptr` 真正共享的不是某个裸指针变量，而是**同一个控制块**
2. 对象销毁与控制块销毁不是同一个时刻

教学版里我先保留了：

- `use_count`
- `weak_count`
- `destroy_object()`

哪怕 Day 16 当天还没实现 `weak_ptr`，这也是必要的。因为如果不把控制块当成独立生命周期实体，后面几天都会写乱。

这一天下来，`shared_ptr` 的模型总算和“多个人共享一份资源，谁最后走谁关灯”真正对上了。

---

### Day 17 — 手写 weak_ptr

`weak_ptr` 是这一周第一个真正体现“设计补丁”价值的组件。

如果只有 `shared_ptr`，循环引用根本无解：

- A 拥有 B
- B 又拥有 A
- 外部都释放后，内部仍彼此持有

所以必须有一种关系：

> 我能看见你，但我不拥有你。

这就是 `weak_ptr`。

这一天最关键的点：

1. `weak_ptr` 只增减 `weak_count`，绝不改 `use_count`
2. `lock()` 的含义不是“把自己变强”，而是“如果对象还活着，就申请一次临时共享所有权”
3. 对象死了以后，控制块可以继续活着，直到最后一个 `weak_ptr` 也消失

如果说 Day 16 建的是骨架，Day 17 才真正把控制块生命周期模型闭环了。

---

### Day 18 — enable_shared_from_this

这一天解决的是一个非常实际、也非常容易踩坑的问题：

> 对象内部如果想把“自己”作为 `shared_ptr` 传出去，应该怎么办？

错误做法是：

```cpp
SharedPtr<T>(this)
```

因为它会再造一套控制块。

正确做法是：

- 在对象内部保存一个 `WeakPtr<T> weak_this_`
- 当外部第一次用 `SharedPtr` 接管这个对象时，把 `weak_this_` 接到原控制块上
- 以后对象内部调用 `shared_from_this()`，本质上是 `weak_this_.lock()`

这一天最大的收获，是我终于彻底想明白了：

> `shared_from_this()` 返回的不是“重新包装 this 的智能指针”，而是“同一控制块上的新共享句柄”。

---

### Day 19 — 对比 libc++

这一天下来，最大的价值不是记住几个内部类名，而是验证自己前几天搭的教学版模型没有跑偏。

libc++ 至少有两条典型路径：

- `__shared_ptr_pointer`
- `__shared_ptr_emplace`

我对它们的理解是：

1. `__shared_ptr_pointer` 负责“对象在外面，控制块单独管理”，适用于 `shared_ptr<T>(new T)` 和自定义 deleter 路径
2. `__shared_ptr_emplace` 负责 `make_shared / allocate_shared` 路径，把对象直接构造在控制块内部存储区里

这一天我第一次比较明确地意识到：

> 标准库的复杂，不是因为它的核心思想和教学版完全不同，而是因为它把教学版模型工程化了。

比如：

- 支持 deleter
- 支持 allocator
- 支持 `make_shared` 单次分配
- 有更完整的异常安全处理

---

### Day 20 — 线程安全性验证

这是这一周最容易被“口头总结”误导的一天。

很多人会说：

> `shared_ptr` 是线程安全的。

但这句话必须拆开。

我最后把它整理成下面三条：

1. **控制块引用计数的增减是线程安全的**
2. **不同 `shared_ptr` 句柄共享同一控制块时，并发拷贝/析构通常是安全的**
3. **并发修改同一个 `shared_ptr` 变量对象不是线程安全的**

此外还有一个常见误区：

> `shared_ptr` 线程安全不等于被管理对象线程安全。

它只保证生命周期管理那层，不保证你并发改 `*sp` 的业务状态不出问题。

这一天最重要的价值不是记结论，而是学会区分：

- 控制块层面的同步
- 智能指针变量对象本身的并发访问
- 被管理对象内部状态的并发访问

这三件事必须分开说。

---

### Day 21 — 周总结

最后一天不是“凑个总结”，而是把前面所有零散知识统一回一个模型。

总结完以后，我觉得这一周真正留下来的，不是实现细节，而是下面这几条：

1. 智能指针首先是所有权模型，不是语法糖
2. `shared_ptr` 的关键是控制块，不是“多个指针共享一个裸地址”
3. `weak_ptr` 把观察者和拥有者彻底分开，这是模型自洽的关键
4. `enable_shared_from_this` 是同一控制块回流机制，不是“this 再包装”
5. 标准库是在教学版之上做工程扩展，不是完全不同的一套思路

## 三、本周最关键的知识图谱

### 3.1 所有权分层

```text
UniquePtr
  -> 独占所有权
  -> 拷贝禁用，move 转移

SharedPtr
  -> 共享所有权
  -> 控制块 + use_count

WeakPtr
  -> 不拥有，只观察
  -> weak_count
  -> lock() 申请临时共享所有权
```

### 3.2 控制块的生命周期

控制块至少管理两件事：

- 对象是否还活着
- 还有没有观察者挂在上面

所以会出现两个阶段：

1. `use_count == 0`：对象析构
2. `use_count == 0 && weak_count == 0`：控制块析构

这条两阶段模型，是我这周最大的结构性收获之一。

### 3.3 `shared_from_this()` 的真实语义

`shared_from_this()` 做的不是：

- 新建一套控制块

而是：

- 通过 `weak_this_` 回到原控制块
- 再从原控制块拿一个新的共享句柄

这是理解标准库相关行为的关键。

## 四、和标准库相比，我现在的教学版差在哪

如果只看本周实现思路，我已经掌握了基础模型；但和标准库相比，至少还差这些：

1. **自定义 deleter 支持**
2. **`make_shared/allocate_shared` 的单次分配路径**
3. **更完整的模板约束、类型转换和异常安全处理**
4. **更严谨的多线程细节与原子语义**
5. **更多接口，如 aliasing constructor、`owner_before`、`get_deleter` 等**

不过这些差距并不是“方向错了”，而是“工程细节还没补”。

## 五、本周最容易踩坑的点

1. `unique_ptr` move 后不把源对象置空，会双重释放。
2. `shared_ptr` 拷贝忘了加 `use_count`，会过早释放对象。
3. `weak_ptr::lock()` 如果自己新建控制块，整个语义就崩了。
4. `shared_from_this()` 如果写成 `SharedPtr<T>(this)`，会制造第二套控制块。
5. 以为“引用计数线程安全”就等于“同一个 shared_ptr 变量并发写安全”，这是错的。
