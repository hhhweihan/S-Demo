## 一、这周到底在干嘛？

Week 07 表面上是在学“无锁数据结构”，但如果把这周理解成“再学几个 `std::atomic` 接口”，会完全偏题。

这一周真正解决的是一个并发学习路径里最容易混淆的问题：

> 原子、同步、可见性、内存回收和性能，这五件事彼此相关，但绝不是同一件事。

前两周的阻塞队列和线程池，核心思路都是把复杂度包进锁、条件变量和生命周期协议里。到了 Week 07，这层保护被拿掉之后，很多过去默认成立的事情都必须重新明确：

- 为什么“原子”不等于“线程间看见顺序正确”
- 为什么 CAS 成功不等于数据结构一定正确
- 为什么地址没变，不代表对象还是原来那个对象
- 为什么无锁结构经常难在内存回收，而不是难在接口设计

所以这周最重要的收获，不是写出了一个多复杂的容器，而是建立了无锁编程的基本心智模型：

```text
原子更新
  -> CAS / load / store

同步语义
  -> memory_order

结构正确性
  -> 栈 / 队列状态转换

内存回收
  -> ABA / tagged pointer / 延迟回收

性能收益
  -> 只在合适场景下成立
```

如果说 Week 05 和 Week 06 的重点是“怎么把并发系统做稳”，那么 Week 07 的重点就是“理解锁拿走之后，哪些责任会重新压回程序员自己身上”。

## 二、七天任务全景

### Day 43 — `memory_order`：第一次把“原子”和“同步”彻底拆开

这一天下来最重要的认知非常基础，但也非常关键：

> 原子操作只解决单次访问不可撕裂，不自动解决跨线程观察顺序。

`memory_order_relaxed` 看上去很安全，因为它“还是原子”。但它缺的是同步边，不是原子性。也正因为这个区别，才有下面这条最核心的判断：

- 没有数据竞争
- 不等于逻辑同步一定正确

Day 43 还顺手纠正了一个常见误解：

TSan 更擅长抓未同步的普通共享访问，不会自动替你证明 memory order 设计正确。看到 TSan 安静，只能说明你未必有裸数据竞争，不能说明你的发布-订阅语义就是对的。

---

### Day 44 — 无锁栈：第一次看到 CAS 成功也可能有坑

无锁栈的 push/pop 骨架并不复杂，难点也不在 API，而在边界条件。

这一天下来真正看清楚的是：

- CAS 只是把头指针更新动作做成原子
- 它不自动保证旧节点仍然活着
- 它也不自动告诉你中间有没有发生过“取走又放回”的历史

也就是说，锁被拿掉之后，原来由互斥区隐式保护的“结构一致性 + 生命周期安全”不再天然成立，必须单独设计。

---

### Day 45 — SPSCQueue：第一次遇到真正适合入门的无锁结构

如果直接从通用 MPMC 队列入手，无锁编程很容易学成一堆技巧碎片。SPSC 是这周最重要的落脚点，因为它约束足够强：

- `head_` 只有消费者写
- `tail_` 只有生产者写
- 两边只需要观察对方的索引，而不需要竞争修改同一状态

这使得 SPSC 的正确性明显更容易证明，也让 release/acquire 的用途第一次变得非常具体：

- 生产者先写槽位，再 release 发布 `tail_`
- 消费者 acquire 读到 `tail_` 变化后，再安全读取槽位数据

这一点比死记定义更重要，因为它把 memory order 从概念变成了数据交接协议。

---

### Day 46 — ABA：第一次真正理解“地址一样”为什么不够

ABA 的关键不在于“值从 A 变成 B 又变回 A”这句话本身，而在于：

> CAS 只能看到当前值，默认看不到中间历史。

如果一个节点被弹出、释放、复用、再回到同一地址，另一个线程看到的仍然可能是“A”，但这已经不是原来的那个 A。

所以 ABA 不是“比较错了”，而是“比较维度不够”。tagged pointer 的价值就在这里：

- 地址相同不够
- 还要比较版本号

不过本周也明确了一件事：tagged pointer 只是在比较阶段补上历史信息，不等于自动解决内存释放时机问题。

---

### Day 47 — 性能对比：第一次把“无锁更快”说完整

“无锁更快”这句话只在特定上下文里成立，脱离场景就是空话。

本周把这个前提压得很明确：

- 单生产者
- 单消费者
- 数据交接负载很轻
- 同步路径本身是瓶颈

在这个语境下，SPSCQueue 通常比 BlockingQueue 更有优势，因为它减少了：

- 互斥锁竞争
- 条件变量挂起唤醒
- 共享状态上的 cache line 抖动

但如果把场景换成更复杂的共享状态、更弱的约束、或者需要长期阻塞等待的业务逻辑，锁结构未必更差，甚至更稳。

---

### Day 48 — 读书：第一次看到“无锁更新”和“安全回收”必须拆开

阅读《C++ Concurrency in Action》第 7 章最大的收获，不是新学了一个实现技巧，而是把 Week 07 的很多零散点串起来了。

书里反复强调的一件事，本周非常值得单独记住：

> 数据结构更新协议和内存回收协议是两套问题，不能混成一个问题来想。

这也是为什么书中会使用 `shared_ptr` 或延迟回收路径，而不是只盯着 CAS。本质上，它是在告诉你：

- 抢更新只是第一步
- 什么时候能安全释放旧节点，才是无锁结构真正容易出错的地方

---

### Day 49 — 总结：第一次建立“什么时候不用无锁”的判断力

这一周最成熟的结尾不是“我学会了几种 memory order”，而是终于能比较稳地回答：

- 什么场景适合用锁
- 什么场景值得无锁

这个判断比技巧更重要。因为工程里真正危险的，不是不会写无锁，而是在不该上的地方硬上无锁，把复杂度和维护成本引进来。

Week 07 的结论很明确：

> 能用锁先用锁；只有当热点路径被锁开销明确卡住、状态模型又足够简单时，才值得考虑无锁。

## 三、本周最重要的四个模型

### 3.1 原子性模型：原子不等于同步

本周要先把这条链记住：

```text
原子操作
  -> 保证单次读写不可撕裂
  -> 不自动建立线程间顺序

同步语义
  -> 由 memory_order 和同步边决定
```

这意味着分析并发程序时，至少要分两层问：

1. 这里会不会有数据竞争？
2. 即使没有数据竞争，另一个线程能否在正确时刻看到正确内容？

很多无锁 bug 都不是第一层错，而是第二层错。

### 3.2 发布-订阅模型：release/acquire 是本周主角

Week 07 最实用的同步模型，其实不是 `seq_cst`，而是 release/acquire：

```text
生产者线程
  -> 写共享数据
  -> release store 发布门铃变量

消费者线程
  -> acquire load 观察门铃变量
  -> 读取共享数据
```

只要 acquire 读到了对应 release 写出的值，就建立了可靠同步边。这种模式几乎就是 SPSC、单向发布标志、就绪通知这些场景的标准答案。

### 3.3 ABA 模型：问题不在“现在是什么”，而在“中间发生过什么”

ABA 可以压成一句话：

> 当前值恢复成原样，掩盖了中间历史。

因此它通常出现在：

- 多线程竞争修改同一个指针
- 节点可能被移除、复用、再放回
- CAS 只比较指针值而不比较版本信息

这也是为什么链式无锁结构往往比数组索引型结构难很多。

### 3.4 SPSC 状态模型：两个单写者索引让问题突然简单很多

SPSCQueue 可以把共享状态压得非常小：

- `head_`：只有消费者写
- `tail_`：只有生产者写
- `buffer_`：按照索引区间交接数据

它的关键路径就是：

```text
生产者写 buffer_[tail]
  -> release store tail_

消费者 acquire load tail_
  -> 读 buffer_[head]
  -> release store head_
```

这套模型之所以适合作为无锁入门，不是因为它“最酷”，而是因为它共享状态少、角色边界清晰、证明成本低。

## 四、本周的知识图谱

### 4.1 Week 07 主线图

```text
memory model
  -> atomicity
  -> visibility
  -> ordering

memory_order
  -> relaxed
  -> release / acquire
  -> acq_rel
  -> seq_cst

lock-free stack
  -> compare_exchange
  -> ABA
  -> tagged pointer
  -> memory reclamation

SPSC queue
  -> ring buffer
  -> single writer head/tail
  -> release / acquire handoff

engineering judgment
  -> benchmark context
  -> lock vs lock-free
  -> correctness first
```

### 4.2 本周的判断矩阵

| 维度 | 更适合用锁 | 更适合无锁 |
| --- | --- | --- |
| 共享状态 | 多字段、多阶段、一致性约束重 | 少量状态，可拆成单步原子更新 |
| 并发角色 | MPMC、更通用 | SPSC/SPMC 等受限模型 |
| 正确性成本 | 更重视维护性与可排障性 | 团队能承担内存模型和回收复杂度 |
| 性能诉求 | 吞吐不是同步瓶颈 | 热点路径明确卡在锁竞争或唤醒成本 |
| 生命周期 | 节点回收复杂 | 数据交接边界清晰、释放模型可控 |

最核心的一行是：

> 如果你还说不清共享状态模型和回收模型，就先别上无锁。

### 4.3 后续落地建议

## 五、本周真正带走的东西

Week 07 不是教你“以后尽量无锁”，恰恰相反，它更像是在帮你建立一种工程克制：

- 锁会把复杂度收进互斥区
- 无锁会把复杂度拆成原子更新、同步语义、缓存行为和回收协议

所以无锁真正珍贵的地方，不是“快”，而是你终于开始知道并发正确性到底靠什么支撑。

本周最值得长期记住的结论只有四条：

1. 原子性不等于同步。
2. CAS 成功不等于结构正确。
3. ABA 本质是历史被掩盖，不是当前值判断失误。
4. SPSC 是理解无锁编程最好的第一站，因为它让复杂问题先缩成一个可证明的小模型。
