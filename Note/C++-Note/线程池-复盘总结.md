## 一、这周到底在干嘛？

Week 06 表面上是在写一个 `ThreadPool`，但如果只把它看成“开几个线程 + 扔任务进去”的容器封装，就会把最关键的部分完全看漏。

这一周真正解决的是一个并发工程里的核心问题：

> 如何把任务提交、结果回收、线程退出、扩缩容和状态观测，整理成一个可以长期演进的执行框架。

所以本周的重点不是 `class ThreadPool` 这个名字，而是一整套执行模型：

```text
任务提交
  -> submit(std::function<void()>)
  -> submit(F&&, Args&&...) -> future

任务执行
  -> BlockingQueue<Task>
  -> worker_loop

结果回传
  -> packaged_task + future

关闭收口
  -> await_termination
  -> shutdown
  -> 哨兵任务 + queue shutdown

运行期治理
  -> 动态扩缩容
  -> snapshot_stats()
  -> benchmark + 设计对比
```

如果说 Week 05 解决的是“任务如何安全交接”，那么 Week 06 是把这件事往前和往后都接上：

- 往前接提交接口和返回值语义
- 往后接 worker 生命周期和关闭协议
- 中间再加上扩缩容和统计信息，让线程池从 demo 走向真正可观察的组件

所以这一周不是在做一个“会跑的线程池”，而是在建立线程池最小可用版本的完整骨架。

## 二、七天任务全景

### Day 36 — 固定线程池：先把最小闭环跑通

这一天下来最重要的，不是把 `vector<thread>` 写出来，而是建立线程池最基本的执行闭环：

- 主线程提交任务
- 任务进入阻塞队列
- worker 线程持续消费任务
- 所有任务都能被完整执行

这个阶段最关键的判断标准不是“代码看起来像线程池”，而是有没有形成稳定的协议：

- worker 线程是否持续存活，而不是一次性线程
- 任务是否通过统一队列进入执行路径
- 主线程与 worker 是否通过同一个共享结构交接任务

Week 05 的 `JoiningThread` 和 `BlockingQueue` 到这里第一次真正拼起来了。也正因为 Week 05 先把线程回收和阻塞等待踩实，Day 36 才能把关注点集中在线程池框架本身，而不是重新陷入底层同步细节。

---

### Day 37 — future 返回值：线程池不再只是 fire-and-forget

如果 Day 36 的线程池还只是“投递任务然后不管结果”，那它只能算半个执行器。真正让线程池开始像现代异步组件的是 Day 37：

- `submit` 开始支持任意可调用对象
- 返回 `std::future<T>`
- 调用方可以同步等待，也可以延后取结果

这一层的核心不是语法模板，而是语义分工：

- `packaged_task` 负责把“执行任务”和“回填结果”绑到一起
- `future` 负责把结果交给调用方
- worker 线程不用关心结果类型，只需要执行包装后的任务

这一步非常关键，因为它把线程池从“任务分发器”升级成了“异步调用执行器”。

也正是在这里，本周第一次把 `future / promise / packaged_task` 这三个概念真正落回代码，而不是停留在书面定义。

---

### Day 38 — 优雅关闭：线程池真正的难点开始出现

线程池最容易写出一个能跑的版本，但最容易出问题的也恰恰是关闭路径。

Day 38 的核心任务不是新增一个 `shutdown()` 函数，而是定义线程池的收口协议：

- 什么时候不再接收新任务
- 已经在队列里的任务是否必须执行完
- worker 线程什么时候退出
- 主线程如何确认“真的结束了”

本周的实现用了两层收口手段：

1. `await_termination()` 等待 `pending_tasks_ == 0`
2. `shutdown()` 停止接收任务，并通过哨兵任务和 `queue_.shutdown()` 让 worker 退出

这里最重要的工程意识是：

> 线程池的关闭，不是简单“停掉线程”，而是一个先排空、再退出的协议问题。

如果这个协议没定义清楚，线程池要么丢任务，要么卡死，要么在边界情况下出现偶发 race。Day 38 开始，问题已经从“功能是否存在”升级成“生命周期协议是否自洽”。

---

### Day 39 — 动态扩缩容：线程池开始具备治理能力

固定线程数版本可以工作，但还不够工程化。Day 39 的目标，是让线程池根据任务积压情况自己调整 worker 数量。

这一步真正引入的是运行期控制逻辑：

- 队列长度超过阈值，且当前线程数未到上限，就增 worker
- 队列空闲，且线程数高于下限，就缩 worker
- 用 `active_count_` 和 `target_worker_count_` 追踪“当前活跃状态”和“目标规模”

这一天的收获不是“线程变多了”，而是第一次感受到线程池本质上是一个动态系统：

- 任务量在变化
- 队列积压在变化
- 线程数也应该是可以治理的变量

从这个节点开始，线程池已经不再只是并发容器，而是在向执行器和调度器的方向靠近。

---

### Day 40 — 压力测试：把吞吐和设计代价量化出来

本周的压力测试非常直接：

- 100 万个轻量任务
- 单线程作为基准
- 4 线程和 8 线程线程池分别测试

这组数据最有价值的地方，不是某个漂亮数字，而是它非常清楚地暴露了简单线程池的真实行为：

| 配置 | 总耗时 | QPS |
|------|--------|-----|
| 单线程基准 | 1.995 ms | 501177767.754 |
| 4 线程 | 232.562 ms | 4299930.470 |
| 8 线程 | 1380.359 ms | 724449.429 |

这组结果说明了一个非常重要的工程事实：

> 对于极轻任务，线程池不一定比单线程快；线程更多也不一定吞吐更高。

原因并不神秘：

- `std::function` 包装有成本
- 阻塞队列有锁竞争
- 线程切换和唤醒有调度成本
- 8 线程在这个实现里进一步放大了队列争用

这类 benchmark 的真正意义，不是证明线程池“很强”，而是帮助建立性能直觉：

- 线程池更擅长解决任务并发管理，而不是免费加速所有工作负载
- 轻任务下，同步开销很容易压过并发收益
- 设计取舍必须和任务粒度一起看

### Day 41 — 和 folly 对比：开始从“能写”走向“会比较”

这一天下来最大的价值，不是模仿 industrial 实现，而是把自己的线程池放回更大的对比框架里。

和 folly 对比后，本周至少看清了三件事：

1. **任务队列类型不同。**
   我的实现是单 FIFO `BlockingQueue<std::function<void()>>`，目标是先把语义写对；folly 常用的是带优先级、针对并发调度优化过的专用队列。

2. **worker 退出方式不同。**
   我的实现把退出逻辑塞回任务队列，用哨兵任务 + shutdown 收口；folly 会把线程停止数量、退出流程和 join 路径分开建模。

3. **统计信息层次不同。**
   我的版本补了 `snapshot_stats()`，但还是偏池级统计；folly 的统计会更细，覆盖任务等待时间、运行时间和更多 executor 内部状态。

这一对比的意义非常大，因为它会逼着自己承认：

- 简单实现的优势是语义直观、易于验证
- 工业实现的优势是更强的吞吐、调度能力和可观测性
- 中间差出来的，不是“高级语法”，而是大量生命周期、性能和状态治理细节

### Day 42 — 概念收口：把线程池和异步结果模型压成一套清晰语言

Day 42 的任务看起来偏文档，但它的意义其实非常务实：

- 整理压力测试结果

这一步的价值在于，把 Week 06 从“代码写完了”推进到“我能清楚说清楚自己到底写了什么”。

## 三、本周最核心的六条收获

### 1. 线程池的本质不是线程集合，而是任务执行协议

把几个线程放到 `vector` 里并不难，但那还不构成线程池。

线程池真正的核心是下面几件事有没有统一起来：

- 任务如何提交
- 任务在哪里排队
- worker 如何持续执行
- 结果怎么返回
- 池如何关闭

只有这些协议稳定了，线程池才是组件；否则它只是“多线程跑任务”的 demo。

### 2. `packaged_task + future` 是线程池返回值语义最自然的组合

本周一个很重要的实际认知是：

- `promise` 更适合手动生产结果
- 线程池里更自然的是把任务本身包成 `packaged_task`

这样做的好处是：

- worker 只负责执行任务
- 返回值和异常自动写入 `future`
- 提交侧接口统一，不需要手写结果桥接逻辑

这也是为什么现代 C++ 线程池实现几乎都会沿着这条路走。

### 3. 关闭路径比执行路径更容易出真实问题

执行路径通常比较线性：

- submit
- push
- pop
- run

但关闭路径永远更复杂：

- 还有没有新任务进来
- 队列里剩余任务怎么处理
- 正在阻塞的 worker 如何退出
- 有没有线程会永远等下去

本周实际就踩到了一个非常典型的问题：

> `shutdown()` 一开始按 `active_count_` 发送退出哨兵，会因为 worker 启动时序导致哨兵数不足，进而出现挂住风险。

最后修复思路是：

- 不依赖瞬时活跃计数
- 改为基于 `workers_.size()` 这个更稳定的 worker slot 数量发退出信号
- 再配合 `queue_.shutdown()` 收口

这一点非常值得记住，因为它说明：

> 并发关闭逻辑里，瞬时状态往往不如结构性状态可靠。

### 4. 动态扩缩容的难点不在“多开几个线程”，而在状态同步

扩容本身很容易理解，但缩容、目标线程数、实际线程数、退出 token 这几者之间的关系如果没定义清楚，逻辑就会很快混乱。

本周实现里真正重要的是把这些量区分开：

- `active_count_`：当前活跃 worker
- `target_worker_count_`：当前目标线程规模
- `worker_exit_tokens_`：待消费的退出配额

也就是说，线程池扩缩容不是单变量问题，而是一个小型状态机问题。

### 5. 可观测性不是锦上添花，而是验证动态行为的前提

如果没有 `snapshot_stats()`，Day 39 和 Day 40 很多结论都只能靠猜：

- 线程到底有没有扩起来
- 提交数和完成数是否一致
- 队列是否排空
- 当前是队列积压还是 worker 不够

这说明一个很现实的问题：

> 没有统计接口的线程池，即使功能正确，也很难调试和迭代。

所以本周补统计，不是“加点信息看看”，而是在为后面真正的性能分析和行为验证打底。

### 6. 线程池是否值得，必须结合任务粒度一起判断

本周压测数据已经非常说明问题：

- 任务非常轻时，线程池可能明显慢于单线程
- 线程数增加过多时，吞吐可能进一步恶化

所以线程池不是“默认更快”的工具，而是：

- 当任务够重
- 或任务存在 I/O 等待
- 或需要统一调度/限流/隔离执行时

它才真正体现价值。

这条认知很关键，因为它能避免以后把线程池用成“看到并发需求就先套一个池”的机械反应。


### 4.2 本周线程池的状态模型

本周这个实现里，线程池至少维护了下面几类状态：

- 是否仍在运行：`running_`
- 是否仍接收新任务：`accepting_`
- 当前活跃 worker 数：`active_count_`
- 目标 worker 数：`target_worker_count_`
- 待退出 worker token 数：`worker_exit_tokens_`
- 已提交任务数：`submitted_tasks_`
- 已完成任务数：`completed_tasks_`
- 已拒绝任务数：`rejected_tasks_`
- 未完成任务数：`pending_tasks_`

这说明线程池从 Day 36 起就已经不是一个简单容器，而是一个带内部状态治理的并发系统。

### 4.3 关闭协议模型

本周可以把线程池关闭协议压成下面这几步：

```text
停止接收新任务
  -> 等待 pending tasks 清零（可选）
  -> 停止监控线程
  -> 按 worker slot 数发退出 token
  -> 通过哨兵任务唤醒 worker
  -> queue shutdown 让阻塞 pop 退出
  -> join / clear workers
```

这是整个 Week 06 最需要真正内化的一段逻辑，因为线程池是否稳定，很大程度就取决于这条路径是否自洽。

## 五、本周最容易犯错的点

### 1. 用“当前活跃线程数”替代“应该退出的线程槽位数”

这是本周实际踩到的坑。

`active_count_` 是运行期瞬时状态，不适合作为 shutdown 时发退出信号的唯一依据。因为如果某些 worker 线程已经创建但尚未完成活跃计数递增，就可能出现低估，最后让关闭路径卡住。

### 2. 只实现 `shutdown()`，却没有明确 `await_termination()` 的语义

如果不先定义：

- 是立刻停
- 还是先跑完当前任务再停

那么线程池接口对调用方就是模糊的。Week 06 里把 `await_termination()` 单独拉出来，就是为了把“排空后关闭”这个语义明确成独立能力。

### 3. 把动态扩缩容理解成纯性能优化

扩缩容的意义不只是快一点，它本质上是在调整资源投入和排队延迟之间的平衡。

如果只想着“线程多一点更快”，很容易忽视：

- 额外线程带来的锁竞争
- monitor loop 的决策滞后
- 缩容时退出协议的复杂性

### 4. 没有统一统计出口，就开始分析线程池行为

没有统计时，很多讨论其实只是猜测：

- 队列长是因为任务太多，还是线程太少
- 线程没扩起来是监控周期太长，还是阈值设置不合适
- 提交慢是队列竞争，还是包装任务太重

所以“先观测，再判断”是这周很值得保留的工程习惯。

### 5. 看到 8 线程更慢，就误判线程池设计完全失败

这组 benchmark 更准确的解释是：

- 当前实现对轻任务不友好
- 当前队列模型在高争用下成本偏高
- 线程池的收益高度依赖任务粒度和同步策略

它说明的是设计边界，而不是线程池这个方向本身没有价值。

## 八、当前最务实的落地建议

如果要在这个版本基础上继续迭代，最值得优先做的不是盲目加功能，而是继续沿着下面顺序推进：

1. 先把 `ThreadPool` 从单头文件版本稳住，确保关闭协议和扩缩容测试都持续可回归。
2. 再考虑把任务队列从单 FIFO 结构升级，观察轻任务场景下的锁竞争改善空间。
3. 补更细的统计，比如任务等待时间、平均执行时间、峰值队列长度。
4. 最后再引入更复杂的调度策略，例如优先级、不同任务队列或 stealing。

这个顺序的核心原因是：

- 线程池先要语义稳定
- 再要状态可观测
- 最后才谈性能增强和调度复杂化

不要把顺序反过来。线程池这类组件，一旦关闭路径和状态模型没稳住，后面功能越多越难收。
